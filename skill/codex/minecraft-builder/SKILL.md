# minecraft-builder v1.1

> [!abstract] 定位
> 用于 Minecraft 建筑、建筑群、聚落、园林、景观与环境改造的通用空间设计原则。它约束“怎样思考、设计、施工和检查”，不绑定具体施工工具、Mod、版本或某个项目状态。
>
> 用户负责表达目标、题材、严谨程度与关键偏好；Codex 应自行完成必要研究、场地理解、规划、设计、施工与检查。用户当前明确要求与项目事实永远优先于本 Skill。

## 1. 一次专注一个主要设计目标

复杂任务默认拆开做深，不要一次粗糙铺开多个需要独立思考的主要系统。城堡、村落、港口、修道院、园林等都可以属于同一世界，但应优先逐个严谨完成，再处理它们之间的关系。

如果用户要求分阶段施工，应先形成整体空间方案，再按逻辑阶段实施；不得把“分步施工”误解成“边做边临时拼布局”。

## 2. 先判断任务属于哪一种空间类型

设计前先判断主要任务类型：

- `BUILDING`：单体建筑或建筑主体；
- `SETTLEMENT`：村落、街区、城镇、建筑群与基础空间网络；
- `LANDSCAPE`：园林、公园、庭园、自然化景观、山水环境；
- `MIXED_ENVIRONMENT`：建筑、地形、水体、植被共同构成主要体验的综合项目。

不同类型不能默认套用同一套“建筑先行”流程。

对于 `LANDSCAPE` / `MIXED_ENVIRONMENT`：

> **Terrain / Water / Rock / Structural Vegetation / Circulation / Architecture 都是一等空间系统。**

山、水、植物不是建筑完成后的装饰层。

## 3. 所有设计都必须有逻辑支撑

任何建筑、道路、院落、山水、植被、聚落和幻想结构都应能回答“为什么会这样”。形态、位置、尺度、材料、交通、防御、生产、宗教、身份、生态、景观功能或世界观至少应提供真实因果，而不是只因为“看起来像这种风格”。

允许超现实，但不允许无因果。

同样，开放空间与留白也必须成立：

- 广场、水面、草坡、庭院、空地、视线走廊可以主动留空；
- 但不得留下大面积意义不明、尺度失控、既不形成构图也不服务功能的空旷区域；
- “没有放东西”本身不能作为设计理由。

目标不是填满场地，也不是刻意留白，而是让**实体与空白共同形成有效空间关系**。

## 4. 先理解题材原型与世界规则

历史 / 写实题材应主动参考可靠的真实历史、考古、遗址、建筑史、园林史、景观史、博物馆或文化遗产资料，理解真实空间为何形成，而不是只模仿外观名词。

幻想 / 架空题材也应先明确文化、使用者、环境、材料、技术或魔法规则，并可借鉴现实建筑、园林与自然结构作为支撑。混合题材以现实逻辑为骨架，再有意识地加入幻想元素。

研究后要识别该题材**不可缺少的空间系统**。例如若现实原型依赖山水、地形起伏、林冠、视线控制，则不能只复刻建筑平面和材料。

## 5. 不要无意识套用现代规划思维

设计布局前先判断空间是如何形成的。历史、传统、自然式或有机生长型环境尤其不要默认使用：

- 方正规则路网；
- 等距对象；
- 均质地块；
- 统一退界；
- 镜像复制；
- 规则绿化网格；
- 现代郊区式均匀疏散布局。

道路、水源、地形、宗教、权力、市场、生产、长期通行、视线与自然条件应共同塑造空间。

规则秩序只有在题材本身有真实理由时才使用，例如仪仗轴线、果园、行道树、规则庭院、防风林等。

## 6. 自然地形应顺应；人工平板不是必须保留的地形

真实自然场地中的山坡、脊线、河流、台地、缓坡等地形骨架是设计条件，不是施工前应被抹平的障碍。优先通过地基、台阶、挡土墙、顺坡建筑和有限整地适应环境，避免无理由大面积推平或规则切台。

但对于 `superflat`、测试画布、人工平整区等**本身没有自然地形设计价值**的场地：

> 如果目标原型依赖地形、水系、山体、台地、洼地或垂直层次，必须主动设计并创建这些地形，而不是把基础标高当作必须保留的自然事实。

“尊重地形”不能被解释成“永远保持超平坦”。

施工范围内已有的随机草、作物、树木等植被默认可清除；需要植物时，应依据最终空间逻辑重新设计。

## 7. 复杂设计必须同时思考 Plan / Section / Sequence

大型或复杂项目不能只做顶视平面规划。

### Plan｜平面关系

至少理解：

- 功能和空间在哪里；
- 道路、水体、建筑、山体、植被如何相互组织；
- 主次空间与碰撞关系。

### Section｜剖面与垂直构图

至少理解：

- 地形高低；
- 水面与岸线；
- 山体 / 台地 / 洼地高度；
- 建筑基座、檐口、屋顶；
- 乔木树冠；
- 前景 / 中景 / 背景的垂直关系。

对于依赖地形与景观层次的题材，若绝大多数有效场地最终仍停留在单一标高，且没有原型或功能理由，应视为设计警报并重新评估。

### Sequence｜移动与观看序列

至少理解主要进入和游览路径：

- 进入时先看到什么；
- 什么被遮挡；
- 什么逐渐显露；
- 哪里开敞、哪里收紧；
- 哪里登高、回望、框景或借景；
- 玩家移动时空间是否连续而有变化。

不要求制作专业 CAD，但设计必须真实考虑 X / Y / Z，而不是只做二维占地图。

## 8. 功能逻辑优先于表面装饰

建筑首先必须“能成立”：入口、道路、院落、门、楼梯、楼层和主要功能区应真实可达；建筑之间不得无意重叠。

复杂建筑应理解功能空间关系，不要把房间当作填充物。完整家具内饰默认不是重点，除非用户要求；但基本内部空间、交通和结构逻辑必须正确。

不得出现楼梯尽头是墙、门洞堵死、楼层不可达、道路突然中断、建筑互相穿插等错误。

对于景观，同样要求“能成立”：路径可走、山水关系合理、主要观景点有对象可看、植被不会无意堵死所有路线或重要视线。

## 9. Structural Vegetation 与 Detail Vegetation 必须分开

植物不能统一归为最后阶段的微细节。

### Structural Vegetation｜结构性植被

包括但不限于：

- 大型乔木 / 古树；
- 大冠幅树；
- 竹林；
- 林带；
- 小树林；
- 水岸林；
- 林缘组合；
- 具有明显体量的灌木群。

它们可承担：

- 空间围合；
- 遮挡；
- 框景；
- 借景关系；
- 背景 / 前景；
- 路径引导；
- 水岸软化；
- 高低过渡；
- canopy / skyline；
- 视觉焦点。

因此 Structural Vegetation 属于 Macro / Meso 阶段，应与山体、水体和建筑共同规划。

### Detail Vegetation｜细节植被

花、草、小灌木、荷叶、藤蔓、地被、小型点景植物等可在后期 Micro 阶段补充。

## 10. 自然式植被必须是“受约束的不规则”，不是网格，也不是纯随机

自然式园林、森林、河岸、山地植被默认禁止无理由的：

- 等间距种植；
- 行列网格；
- 对称复制；
- 统一株高；
- 统一冠幅；
- 同一树型高频重复；
- 直线切割式林缘。

但“随机撒点”同样不是合格设计。

自然式植被应优先通过以下关系形成：

- cluster / 丛聚；
- density gradient / 疏密渐变；
- irregular edge / 不规则林缘；
- opening / 局部开口；
- hierarchy / 主树、副树、林下层级；
- overlap / 树冠叠合；
- asymmetry / 偏心与不对称；
- terrain response / 顺应坡地、水岸和建筑；
- sightline response / 为遮挡、框景或留出视线服务。

只有果园、行道树、宫殿礼仪轴线、规则庭院等题材有明确人工秩序时，才主动使用规则排列。

## 11. 景观植被的尺度必须与空间职责匹配

Minecraft 原生小树不是默认景观树答案。

如果一棵树承担遮挡、背景、框景、树冠天际线或空间围合作用，应根据周边建筑和地形主动确定需要的高度、冠幅、主干、分枝、倾斜和树冠不对称程度。

对于重要景观场景，优先使用或设计足够大的 custom vegetation asset；原生树仅在其尺度和形态确实合适时使用。

尺度检查至少考虑：

```text
player scale
→ building scale
→ terrain / landscape scale
→ canopy / skyline scale
```

不得因为“Minecraft 默认树长这样”就接受明显失衡的景观比例。

## 12. 植被与其它高价值资产优先复用蓝图库；不足时先生成候选，不自动入库

可以积极复用 Litematica、Blueprint 或已有资产库，但“能放进去”不等于“应该放进去”。资产必须满足当前项目的：

- 功能；
- 尺度；
- 地形接口；
- 风格；
- 空间职责；
- 视觉权重。

对于大型乔木、古树、竹丛、林带、林缘组合等高价值景观资产：

1. 先查询已有蓝图库 / 参考库；
2. 有合适资产时选择合适 variant，而不是高频复制同一对象；
3. 没有合适资产时，可以为当前任务自行设计新的候选资产；
4. 候选资产可保存在**本任务临时 / candidate 产物**中用于当前场景验证；
5. **不得因为模型自行设计完成，就自动写入正式资产库。**

### Owner Approval Gate｜资产入库必须真人批准

完成存档编辑任务后，最终输出中应增加：

> **推荐入库资产候选清单**

仅列出本轮确实具有重复使用价值的候选，例如：

- 大型景观树；
- 古树；
- 特殊竹林 / 林带组合；
- 假山模块；
- 亭 / 桥 / 小型构筑物；
- 其它高质量可复用资产。

每个候选至少说明：

- 候选名称 / 临时 ID；
- 当前存档中的位置或预览入口；
- 尺寸；
- 主要用途 / spatial roles；
- 推荐入库理由；
- 是否已有类似资产。

随后由 Owner 进入 Minecraft 真人观看审核。

只有 Owner 明确同意的候选，后续任务才允许正式转换、登记或保存进资产库。未批准候选不得成为 canonical library asset。

## 13. Macro → Meso → Micro 应按空间系统理解

### Macro

优先解决：

- 场地与地形骨架；
- 大水体；
- 主次空间；
- 总体高度关系；
- 大型 Structural Vegetation；
- 建筑主次体量；
- 主要视觉焦点。

### Meso

再解决：

- 道路 / 游廊 / 桥；
- 次级山水；
- 建筑之间关系；
- 林带、竹林、树群；
- 屋顶 / 立面 / 梁柱；
- 视线与空间开合。

### Micro

最后处理：

- 门窗细节；
- 栏杆；
- 活板门；
- 花草；
- 小灌木；
- 铺地变化；
- 小型点景。

不得在 Macro / Meso 尚未成立时，用大量 Micro 装饰掩盖平板、空旷、网格化或比例失衡等问题。

## 14. 统一设计语言，同时避免复制感

同一项目中的建筑、景观和资产应有家族相似性：共享时代 / 文化、材料、结构、比例与环境逻辑；不同用途和等级再产生合理差异。

不要把不同作者、不同体系下只因为都标为“medieval”“fantasy”“tree”或“garden”的资产机械混用。

也不要连续复制同一建筑或同一树蓝图。优先使用真实 variant，并通过朝向、地形关系、组合方式和上下文产生变化。不得依赖简单重复制造规模感。

## 15. 小修补与整体重构采用不同策略

门窗、材料、局部屋顶、单株植物等小修改可以原地修补。

若城堡内院、村庄核心、园林山水骨架、主水体、空间序列或植被围合关系发生根本变化，应优先有边界地清空后重构：

1. 明确保留范围；
2. 明确拆除范围；
3. 基于清空后的状态重新规划；
4. 施工前检查新旧结构和新对象彼此碰撞。

不要持续在根本不合适的旧布局上叠加补丁。

## 16. 逐阶段施工必须逐阶段自检，但自检不能只看施工成功

用户要求分阶段建造时，每一阶段完成后应检查与该阶段目标相关的设计质量。

“方块成功写入 / samples 全通过”只证明施工执行成功，不等于空间设计成功。

复杂项目的阶段检查可根据现有工具选择：

- top view；
- height / contour view；
- section / profile；
- oblique / perspective view；
- 玩家关键视点；
- 主要游览路线；
- skyline；
- 碰撞 / 可达性。

不得只用顶视图判断三维景观是否成功。

## 17. Final Spatial Review｜最终必须检查玩家实际体验

大型 / 复杂 / Landscape / Mixed 项目在交付前至少检查以下问题：

### Anti-Flatness

- 是否因为方便而把大部分空间压在同一标高？
- 原型要求的山、水、高差和树冠层次是否真实存在？

### Anti-Grid

- 道路、地块或自然式植被是否出现无理由的方正、等距、对称和机械重复？

### Space Use

- 是否存在大面积意义不明、空旷但没有构图或功能价值的留白？
- 是否也存在为了“丰富”而过度填充的问题？

### Vegetation Structure

- 大型植被是否真的形成围合、遮挡、框景、背景或 skyline？
- 是否主要依赖尺度明显不足的原生小树？
- 是否有疏密、层级、林缘和树冠变化？

### Scale

- player / building / terrain / vegetation 尺度是否匹配？

### Sequence

- 从主要入口和移动路线看，空间是否有明确的开合、藏露和焦点变化？

若这些问题暴露 Macro / Meso 结构失败，应优先重构，而不是继续加小装饰。

## 18. 自主完成，不要过度工程化

用户通常只需要说明目标、题材、严谨程度和关键偏好。Codex 应自行决定研究资料、设计方法、资产选择、规划、施工手段和必要自检，并以最终空间质量为目标。

不要把普通建造任务扩张成庞大的基础设施或验收工程。只有遇到真实技术 blocker、存档风险或无法自行消解的重大设计歧义时，才停下来处理或请求用户决策。

## 默认工作顺序

```text
理解单一目标与题材
→ 判断 BUILDING / SETTLEMENT / LANDSCAPE / MIXED_ENVIRONMENT
→ 必要时研究真实原型 / 建立世界规则
→ 读取场地与地形
→ 识别题材不可缺少的空间系统
→ 形成 Plan + Section + Sequence
→ 建立 Terrain / Water / Structural Vegetation / Architecture 的 Macro 骨架
→ 校准 player / building / landscape 尺度
→ 处理 Meso 空间、道路、植被群落与建筑关系
→ 分阶段施工，并在每阶段自检
→ 处理 Micro 细节
→ Top + Section + Perspective / Route 综合验收
→ 必要时有边界重构
→ 完成存档任务
→ 输出推荐入库资产候选清单
→ Owner 真人进存档审核
→ 仅 Owner 批准的候选后续正式进入资产库
```

成功标准不是“放置了很多方块”，也不是“顶视图看起来填满或复杂”，而是成品从玩家视角、三维空间、题材原型和使用逻辑上都成立，并且能够解释：

**它为什么在这里、为什么这样高低起伏、为什么这样组织、为什么这里有建筑 / 山水 / 植被或留白。**
