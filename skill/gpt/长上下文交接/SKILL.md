# 项目长线程交接与上下文恢复 SKILL

## 1. 目的

本 SKILL 用于：

- 当前聊天过长，需要在同一项目下新建聊天；
- 更换 GPT / Planner / Reviewer；
- 项目中断后恢复；
- 当前有 Codex、前端 Agent 或外部任务正在执行；
- 必须保留重要决策、阶段状态、冻结成果和未决 blocker；
- 避免新线程重新规划、重复发任务、误用历史结论或丢失 Git / 审核现场。

目标不是复制全部聊天，而是形成一份**可验证的项目现场快照**：

```text
项目事实源
+
当前 Git / 实现事实
+
阶段状态
+
冻结成果
+
当前活动任务
+
未决问题与证据
+
下一步决策树
+
协作偏好
```

---

# 2. 触发条件

出现以下任一情况时使用：

1. 当前聊天已经很长；
2. 新聊天需要直接接管当前任务；
3. 当前有未完成的 Codex / Grok / Review 工作；
4. 历史中存在多次修订，容易把旧方案误认为现行方案；
5. 用户明确要求“交接”“新线程接手”“不要丢记忆”；
6. 当前阶段结束前不能安全依赖聊天自然记忆。

---

# 3. 输入

交接生成前，尽量取得：

- 当前项目正式事实源；
- 当前聊天中的最新用户裁决；
- 当前仓库路径；
- 当前 branch / HEAD / status；
- 当前正式阶段与任务 ID；
- 最新实现报告或审核包；
- 当前正在执行、等待返回或刚发出的 Agent 指令；
- 已冻结成果；
- 已废止或被覆盖的旧方案；
- 当前 P0 / P1 / P2；
- 下一阶段依赖；
- 用户长期协作偏好。

如果某项拿不到，必须写：

`UNKNOWN / 需在新线程验证`

不得猜测。

---

# 4. 双重事实源模型

交接必须区分两类事实源。

## 4.1 产品、规则与路线事实

优先级：

1. 用户最新明确裁决；
2. 当前项目正式事实源；
3. 当前正式路线、架构、合同与不变量；
4. 最新已批准审核结论；
5. 历史资料与旧聊天；
6. Agent 推断。

## 4.2 实现与运行事实

优先级：

1. 当前仓库实际 branch / HEAD / status；
2. 当前工作树 diff；
3. 当前代码与测试；
4. 最新审核包；
5. 实现 Agent 报告；
6. 历史聊天。

原则：

> 文档决定“应该是什么”；Git 和代码决定“现在实际是什么”。

两者冲突时，不得静默调和。新线程必须先指出冲突，再根据权威关系处理。

---

# 5. 交接生成流程

## 5.1 恢复当前项目身份

确认：

- 项目名称；
- 仓库路径；
- 当前主线；
- 当前产品目标；
- 当前正式阶段；
- 当前正式任务 ID；
- 当前阶段退出条件。

## 5.2 建立“项目记忆账本”

必须分为六类。

### A. 当前事实

已经由项目源、Git、代码、测试或用户确认。

### B. 已冻结成果

已经完成、审核通过，除非出现真实证据不得重做。

### C. 当前活动工作

已经发给 Agent、正在执行、尚未返回或刚返回待审核。

### D. 当前未决问题

仍然阻塞推进，必须附证据和分级。

### E. 已废止 / 被覆盖方案

曾经讨论或实现，但已被新裁决取代。必须明确写“不要恢复”。

### F. Future / 阶段后事项

有价值但不属于当前任务，不得自动扩展范围。

## 5.3 检查是否存在“正在执行的外部任务”

如果已经向 Codex / Grok 发出指令：

- 交接中必须写明该指令已经发出；
- 新线程不得重复发同一指令；
- 若结果已经返回，直接审核；
- 若尚未返回，不重新规划同一能力；
- 只有真实新证据才允许产生修订指令。

## 5.4 提炼冻结不变量

至少提炼：

- 状态 owner；
- 权限 / 授权边界；
- 数据、事务和安全；
- 模型与程序职责；
- UI / DTO 边界；
- 当前阶段禁止提前建设的能力；
- 已验证的真实 Provider / UAT 结论。

## 5.5 记录 Git 现场

必须包含：

- repo path；
- branch；
- last known HEAD；
- HEAD 是否只是参考；
- 工作树是否干净；
- 是否存在未提交实现；
- 是否存在 staged 变更；
- 是否已 commit；
- 是否 push；
- 受保护未跟踪目录；
- 新线程开始时必须执行的 Git 检查。

如果当前工作树有未提交实现，必须醒目标注：

> 不得 reset / stash / clean / checkout 覆盖。

## 5.6 定义新线程的第一动作

交接必须给出决策树，而不是模糊写“继续推进”。

示例：

```text
如果 Codex 结果已返回
→ 审核实际 patch、tests、HEAD、status
→ 判断 PASS / Rework / Blocked

如果结果尚未返回
→ 不重复发任务
→ 只确认现场并等待结果输入

如果实际 Git 与交接不一致
→ 以实际 Git 为准
→ 先解释差异
→ 不 reset
```

# 6. 新线程接管流程

新线程收到交接后必须按顺序执行。

## 6.1 先读项目源

读取当前项目中的：

- 产品 / 核心总纲；
- 路线图；
- AI 协作偏好；
- 架构 / 合同 / 不变量；
- Legacy / Reference 标记。

不得仅凭交接文本替代项目源。

## 6.2 确认交接类型

判断当前是：

- 等待实现结果；
- 审核结果；
- 生成修订任务；
- 真人 UAT；
- 阶段关闭；
- 阶段末项目源维护；
- 下一阶段讨论。

## 6.3 验证当前现场

如果能访问仓库或审核包：

- 核对 branch / HEAD / status；
- 核对工作树与交接是否一致；
- 核对最新结果是否属于当前 HEAD；
- 核对最新测试是否覆盖当前代码；
- 核对是否有未提交修改；
- 核对是否有重复任务风险。

如果不能访问仓库：

- 使用用户提供的 Codex 返回与审核包；
- 明确哪些 Git 事实仍需 Codex 验证；
- 不伪造当前状态。

## 6.4 不重新讨论已关闭阶段

除非最新证据显示 P0：

- 不重开已关闭阶段；
- 不重新设计已冻结架构；
- 不因新 GPT 偏好改写已通过成果；
- 不重新发送已发出的任务指令。

## 6.5 按当前 Gate 审核

审核必须使用当前任务真正的退出条件。

不得：

- 用测试数量替代真实目标；
- 把安全的模型语义差异当 P0；
- 为偶发模型误解重构整个架构；
- 为让结果变绿降低世界完整性或玩家代理权。

# 7. 必须包含的交接结构

每份正式交接至少包含以下章节。

## 7.1 项目身份

- 项目；
- 仓库；
- 主分支；
- 当前产品路线；
- 当前阶段。

## 7.2 权威阅读顺序

列出新线程必须优先读取的项目源，并说明：

- 哪些是 current；
- 哪些是 candidate；
- 哪些是 legacy reference。

## 7.3 当前阶段状态

- 已完成阶段；
- 当前阶段；
- 当前正式任务；
- 当前 Gate；
- 阶段退出条件。

## 7.4 Git / 实现现场

- last known HEAD；
- 当前工作树；
- commit / push；
- 开始前核验命令；
- 保护要求。

## 7.5 已冻结成果

只写会影响后续判断的核心成果。

## 7.6 当前活动任务

- 已经发给谁；
- 指令名称；
- 目标；
- 当前是否等待结果；
- 不得重复发送。

## 7.7 当前未决问题

每项必须说明：

- 事实证据；
- 根因；
- P0 / P1 / P2；
- 当前推荐处理；
- 哪些错误处理方式被禁止。

## 7.8 已被覆盖的旧方案

明确标记：

- 已废止；
- 不能恢复；
- 为什么被取代。

## 7.9 下一步决策树

按“结果已返回 / 未返回 / PASS / FAIL / Git不一致”分别说明。

## 7.10 协作偏好

包括：

- 任务粒度；
- Codex / Grok 分工；
- Git；
- 用户 UAT 负担；
- 项目源维护频率；
- 报告与审核包格式。

## 7.11 不要做

列出最容易在新线程中误做的事情。

# 8. 项目记忆压缩原则

## 8.1 保留什么

优先保留：

- 用户明确裁决；
- 当前路线；
- 当前任务；
- 已验证不变量；
- 当前 Git 状态；
- 最新 P0 / P1；
- 已发出的指令；
- 最新审核结论；
- 不要重做的成果；
- 下一步 Gate；
- 项目源待更新事项。

## 8.2 不保留什么

不需要在交接中复制：

- 每次中间尝试的全部细节；
- 已经被覆盖的每条 Prompt；
- 大量测试计数历史；
- 所有旧 commit；
- 原始 Provider 输出；
- 私密 reasoning；
- 无关聊天；
- 已经解决的局部 Bug 全过程。

## 8.3 如何保留被覆盖历史

只保留：

```text
旧方案：
为什么失败：
被什么方案取代：
禁止恢复什么：
```

---

# 9. 防止记忆丢失的关键规则

1. **永远记录当前正式任务 ID。**
2. **永远记录最后已知 HEAD，但注明实际 Git 优先。**
3. **永远标记是否存在未提交工作树。**
4. **永远记录已发出但尚未返回的 Agent 指令。**
5. **永远区分“实现通过”和“真人 UAT通过”。**
6. **永远区分模型语义质量与世界安全。**
7. **永远记录被废止的旧架构，防止新线程恢复旧方案。**
8. **永远记录阶段结束后需要更新的项目源候选。**
9. **永远给出下一步决策树。**
10. **不得把旧聊天历史置于当前项目源和实际 Git之上。**

---

# 10. 质量检查

输出交接前检查：

- [ ] 当前项目源已读取；
- [ ] 当前阶段与任务准确；
- [ ] 已完成与未完成分开；
- [ ] 最新 Agent 指令状态准确；
- [ ] 没有重复发任务；
- [ ] Git现场明确；
- [ ] 未提交工作树有保护说明；
- [ ] P0/P1/P2分级清楚；
- [ ] 模型语义质量与安全分开；
- [ ] 已废止方案已标记；
- [ ] 下一步决策树可直接执行；
- [ ] 没有把推断写成事实；
- [ ] 没有泄露凭据、raw response、reasoning或私人数据；
- [ ] 用户无需重新解释整个项目。

---

# 11. 新线程首条回复要求

新线程收到交接后：

- 不复述整个项目历史；
- 用简短文字确认当前阶段、当前任务和下一动作；
- 如果结果附件已经存在，直接开始审核；
- 如果结果尚未返回，明确“不重复发任务”，等待用户提供结果；
- 若发现项目源、交接和Git冲突，先说明冲突再处理；
- 不自动启动下游阶段。

# 13. 完成标准

一份交接只有在新线程能够无需重新询问以下问题时才算合格：

- 这是什么项目？
- 当前在哪个阶段？
- 当前正式任务是什么？
- 哪些已经完成不能重做？
- 当前 Git /工作树是什么状态？
- 哪个 Agent 指令已经发出？
- 当前真正 blocker 是什么？
- 哪些旧方案已经作废？
- 下一步拿到结果后该做什么？
- 什么时候可以进入下一阶段？
