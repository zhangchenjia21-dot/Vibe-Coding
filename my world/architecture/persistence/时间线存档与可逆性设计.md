# 时间线、存档与可逆性设计

## 0. 定位

本文件是 `MY_WORLD_架构_CURRENT.md` 的 Persistence / Reversibility 深度设计。

它冻结第一代 Save / Restore / Timeline 的具体产品语义，但不拥有 Current Task，也不预选 SQLite Schema。

正式原则：

> **Reversibility over prevention does not mean frictionless arbitrary rewind.**
>
> **局部错误应低成本纠正；重大历史恢复必须表达明确玩家意图。**
>
> **Timeline is first a Runtime capability, not automatically a player-facing debugger.**

---

## 1. Player owns the timeline 的正式解释

`Player owns the timeline` 继续有效：玩家不会因为一次模型/游戏错误而永久被锁死；玩家对最终保留、继续和恢复哪段游戏历史拥有最终决定权。

它不意味着：

- 每个 GM Turn 都显示 `回到这里`；
- 点击任意旧消息立即替换当前进度；
- 所有游戏后果都随时零成本撤销；
- 每个内部 Timeline Node 都成为公开 Load Point；
- 玩家像操作调试器一样管理游戏历史。

玩家主权与“无摩擦任意回档”不是同一个产品目标。

---

## 2. 可逆能力分级

### Cancel

```text
active AI generation
→ stop
→ return to usable state
```

风险低、应直接暴露，不等于 Load/Restore。

### Regenerate / Retry latest generation

```text
same latest player input
→ supersede latest unsatisfactory generation
→ generate again
```

局部纠错、低摩擦，只针对最近生成。

### Edit latest input & retry

这是局部修正，不等于任意历史 Rewind。只有 G2-04 Turn Domain 与 G3 persistence boundary 能保证一致时才正式进入产品。

### Save Point

Save Point 表达明确玩家意图：

> **这个进度对我重要，我以后可能希望回来。**

它应有玩家能理解的名称和上下文，是长期可管理恢复点。

### Load / Restore Save

读取旧存档会改变 active future，是高影响操作。

产品必须让玩家清楚：

- 正在读取哪个 Save；
- 当前进度会停止作为 active current timeline；
- 是否存在未显式保存的新进度；
- 当前未来是否仍可恢复。

> **Load 是明确意图，不是 Narrative 旁边易误触的快捷动作。**

### Timeline Node

Runtime 可以拥有比 Save Point 更细的 durable turn / commit / checkpoint / snapshot anchor。

> **Timeline Node != Player Save Point.**

技术上可恢复不代表 UI 必须公开为一键 Load。

### Arbitrary Historical Rewind

从任意旧 Turn 一键 `回到这里`：

> **DEFERRED / NOT DEFAULT FIRST-GENERATION PRODUCT BEHAVIOR**

只有长局 UAT 证明它的真实价值明显高于误触、选择重量下降和状态复杂度后才重开讨论。

---

## 3. Narrative Host 操作边界

近期中央 Narrative 只暴露：

```text
active generation → 取消生成
latest generation → 重新生成
```

以后可评估 latest-turn `修改输入并重试`。

历史 Turn 默认：

```text
read / scroll / inspect
```

不默认提供：

```text
每条历史内容
→ 回到这里
→ 从这里分支
```

---

## 4. Save / Timeline Surface

World Surface Host 未来可以承载 Save / Timeline，但第一代优先顺序是：

```text
Save
→ Load Save
→ 当前 Game / active progress 状态
→ 必要 recovery 信息
→ 真实需要后再增加高级 Timeline 浏览
```

产品要让玩家理解“我保存了什么、当前在哪、要加载哪个”，而不是暴露 Event Log、Snapshot、Commit ID、任意 Turn DAG。

---

## 5. Restore 本身也尽量可恢复

正式方向：

> **切换到旧 Save 时，不立即物理销毁当前未来。**

G3 应选择最小可靠方式，例如：

- automatic recovery checkpoint；
- retained old current head；
- internal branch / detached future；
- 其它等价且简单的恢复标记。

不在本文件预选具体 Schema，但语义目标固定：

```text
Load old save
!=
irreversibly delete everything after it immediately
```

这让误读档本身也可恢复，比给所有普通动作添加 Confirmation 更符合 Recovery-first。

---

## 6. Save Point 不等于完整世界副本

内部时间线粒度和完整存档文件数量不是同一概念。

G3 可以评估：

```text
transactional authoritative state
+ durable mutations / event records where useful
+ periodic snapshot / checkpoint where useful
```

因此：

```text
internal timeline granularity
!=
full-save-file count
```

磁盘空间通常不是首要风险；真正难点是 Restore correctness、future-memory isolation、recovery/branch semantics、Context rebuild、migration 与玩家是否理解当前进度。

---

## 7. G3 优先级

```text
1. reliable current Game / World persistence
2. reopen / resume current game
3. explicit player Save Point
4. explicit Load / Restore Save
5. Restore 后 Agent Context / Conversation future isolation
6. Load 前后的 current-future recoverability
7. Retry / Regenerate / latest-turn correction 与 persistence 对齐
8. internal branch semantics only as needed for correctness / recovery
9. arbitrary historical rewind only if later Product UAT proves it necessary
```

G3 不以“任意 Turn 回到这里”为首要产品目标。

---

## 8. 与 UI Host 的关系

UI Host 只能提供这些 Domain 能力的 projection / request intent：

```text
Cancel
Regenerate
Save
Load
Open Save/Timeline Surface
```

它不自己拥有 Timeline，不直接修改 authoritative state，也不把内部节点变成第二套存档数据库。

---

## 9. 第一代成功标准

第一代 Save / Timeline 成功更看重：

1. 生成错误可以快速 Cancel / Regenerate；
2. 重要进度容易 Save；
3. Load 语义明确且状态正确；
4. 误读档不会导致无法挽回的当前未来丢失；
5. Restore 后 AI 不泄漏未来记忆；
6. 玩家理解当前处于哪个进度；
7. 游戏选择仍有心理重量，不因任意无成本回档变成调试器。

总结：

> **局部纠错要近、快、低成本；历史恢复要明确、有意识、可恢复。**
