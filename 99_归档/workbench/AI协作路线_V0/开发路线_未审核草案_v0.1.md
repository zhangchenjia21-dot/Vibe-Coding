# 2. Route-level Judgments

以下只冻结**顺序原则**，不冻结具体技术栈。

## RJ-01｜TV-01～TV-03 是否必须最早做 feasibility？

**DECIDED：是。**

理由：TV-01（现有 ChatGPT Experience）、TV-02（任意 Selected Text）、TV-03（current conversation Review Handoff）直接决定产品 core loop 是否可成立。若这些 seam 在目标平台上不可行，先完成 Codex runtime、数据库或完整桌面壳只会制造沉没成本。

顺序要求：

```text
Reference evidence
→ minimal real prototype where documents are insufficient
→ Owner focused UAT
→ only then host/route commitment
```

TV-01 可先由 02 做文档/平台证据审计；TV-02/03 最终必须落到真实 ChatGPT 页面/当前 conversation 的 Spike。

## RJ-02｜ChatGPT → Selected Text seam 是否必须先于 Codex production execution 验证？

**DECIDED：feasibility proof 必须先；production implementation 不必先做完整。**

即：

- Route Freeze 前先证明至少一条真实 host path 能完成 Selected Text 与 Review Handoff；
- 不在此时建设完整 ChatGPT shell；
- Route Freeze 后 Codex runtime spine 可先独立用受控 input 跑通；
- 第一完整纵向时再把已验证的 ChatGPT seam 接入 production path。

这样同时避免两种错误：

1. 先造完整 desktop shell，最后发现 ChatGPT seam 不可用；
2. 只做 Codex backend 很久，最后才发现核心 `Select → Send` 交互不可实现。

## RJ-03｜Codex real execution 与 Execution Observability 是否拆开？

**DECIDED：最小 observability 与 real execution 同阶段；rich observability 后置。**

第一次真实 Codex spine 至少一起证明：

```text
launch
+ correct project context
+ stable Run identity
+ Running / Completed / Failed
+ expandable raw log/evidence
+ cancellation
+ abnormal exit visibility
```

不接受“黑盒运行成功，以后再补状态”。

后置能力：丰富日志检索、长历史、性能 analytics、复杂 resume/retry UI。

## RJ-04｜GitHub Ready-for-Review evidence 多早进入？

**DECIDED：紧跟 Codex runtime spine，且必须先于 First Usable。**

第一个完整产品纵向不能把 `Codex Completed` 当成 `Ready for Review`。因此 Git evidence 是第二个实现 Stage 的核心 Gate，不是 release polish。

## RJ-05｜第一个完整 `Select → Codex → GitHub → GPT Review` 在哪里出现？

**DECIDED：TA-3｜First Usable End-to-End Vertical。**

它是 Route Freeze 后第三个 implementation Stage；此前只有最小 runtime 与 Git evidence 两层基础。第一次真实完整纵向不得继续向后拖延。

## RJ-06｜First Reality Gate / First Usable 多早出现？

**DECIDED：**

- **Earliest Critical Reality Gate = TA-0**：Route Freeze 前，真实验证 ChatGPT selection/review seam，并对 Codex/Git feasibility 做最低限度 reality check。
- **First Runtime Reality Gate = TA-1**：真实 Codex 在真实 repo 上执行。
- **First Git Reality Gate = TA-2**：真实 implementation push 后由 Git/GitHub facts 进入 Ready-for-Review。
- **FIRST USABLE / FIRST FULL PRODUCT REALITY GATE = TA-3**：完整 `Select → Codex → GitHub → GPT Review` + Owner UAT。

## RJ-07｜First Usable 前哪些 reliability / recovery REQUIRED？

**DECIDED：只要求保护 core truth 与 Owner control 的最低可靠性；完整 durability 后置。**

TA-3 前必须有：

1. 正确 project binding，不能把任务发到错误 repo；
2. stable Run identity + immutable selected-text/input snapshot；
3. Running / Completed / Failed 可区分；
4. Cancel 有真实 process effect；
5. raw execution evidence 可展开；
6. Codex completion 不会误升 Ready-for-Review；
7. GitHub repo/ref/commit evidence 校验；
8. push fail / branch mismatch / no Git evidence 会停在非 Review-ready 状态；
9. host/restart 遇到 stale `Running` 时至少采用 conservative `Interrupted/Unknown/Reconciling`，不得假装已恢复；
10. secrets 不进入普通日志/持久化；
11. V0 只允许 single active run，避免未证明的并发状态复杂度。

TA-3 前**不要求**：完整 process reattach、自动 resume、复杂 retry engine、并行 run、rich task history、长期日志 analytics。

## RJ-08｜哪些只能在第一个真实纵向之后再建设？

**DECIDED：**

- durable restart/reconciliation 的完整版本；
- richer rework/history UX；
- multi-project repeatability/productization；
- packaging/update polish；
- long-session/stress；
- second agent consumer；
- stable generalized Agent abstraction；
- routing/orchestration/SDK/plugin/protocol。

原因：这些需要 first consumer / first vertical 的现实行为才能设计正确。

## RJ-09｜Project Workspace shell 先做完整还是最薄？

**DECIDED：只做足以承载第一条 vertical 的最薄 shell。**

First Usable 前只需要让 Owner：

```text
进入/确认当前 Project
→ 使用真实 ChatGPT seam
→ 选文并 Send
→ 看必要状态 / 展开日志
→ 看 Completion Report / Ready for Review
→ 一键 Review
```

不提前建设 Today / Plan / Tracks / Knowledge / Dashboard，也不为未来模块做大量空壳。

## RJ-10｜DSH 在何时评估？

**DECIDED：在 G0.4 Reference Audit 中评估，Route Freeze 前完成定位；不先绑定。**

顺序：

```text
First Vertical capability matrix
→ audit DSH current reality
→ compare Build / Fork / Extend / Reference / Reject
→ only if evidence remains ambiguous: same-capability comparison Spike
→ G0.5 architecture decision
```

DSH 不是默认 base，也不是默认 reject。

# 4. First Usable Definition

**FIRST USABLE = TA-3。**

First Usable 不是“窗口能打开”或“Codex 能运行”，而是 Owner 可真实完成：

```text
Discuss
→ Select
→ Execute
→ Push
→ Review
→ Fix / Accept
```

其中：

- TA-0 是最早 feasibility / product seam Reality Gate；
- TA-1/TA-2 是 engineering reality gates；
- TA-3 才是第一次产品价值 Reality Gate。

这一区分防止把技术 spike 或 backend capability 误报为“产品可用”。

# 5. Route Reopen Triggers

以下任一发现成立，Draft Task Axis 必须重排，不能继续按原路线硬做：

1. 没有任何可接受 host path 能保留 Owner 现有 ChatGPT workflow；

3. current conversation One-click Review Handoff 只能退化成 Owner 不接受的手工 copy/paste；
4. Codex 在 Windows 无法形成可靠可控的 real execution/status/cancel contract；
5. GitHub Ready-for-Review 无法可靠绑定预期 repo/ref/commit；
6. DSH 的真实边界与 First Vertical 严重冲突，或相反已经提供被忽略的高价值能力；
7. credential/session policy 使候选 host 或 runtime 不可接受；
8. dirty-tree / branch semantics 证明 worktree/branch isolation 必须前置；
9. restart/process behavior 证明 First Usable 前必须加入更多 durability；
10. Owner focused UAT 证明 seam 虽技术可行但体验仍不优于 simple baseline。

# 6. Reference Audit Handoff to 02

> 02 的任务不是替当前路线找支持材料，而是主动证明下面的假设为什么可能是错的。

## 6.1 最需要被攻击的 10 个假设

### H-01｜存在一条可维护的 ChatGPT host path

**HYPOTHESIS**：至少一种 embedded/companion/browser integration 路径能保留 login/session、Projects、upload、conversation continuity，并允许 V0 seam。

**攻击方式**：寻找平台政策、session 隔离、WebView/automation 限制、cookie/SSO、上传/Projects 失真、维护脆弱性证据。

### H-02｜Exact Selected Text 可以成为稳定产品 seam

**HYPOTHESIS**：Owner 对 GPT 回复任意文本 selection 能被可靠捕获，不要求 GPT 输出特定格式。

**攻击方式**：代码块、复杂 DOM、iframe/shadow DOM、虚拟化内容、长回复、页面更新、selection focus 丢失。

### H-03｜One-click 可以可靠命中“当前 conversation”

**HYPOTHESIS**：Review Request 可以在不要求 Owner 手工复制提醒的情况下送入当前 ChatGPT conversation。

**攻击方式**：conversation identity、focus/tab ambiguity、navigation、message composer API/DOM 稳定性、政策限制。

### H-04｜Codex 可以作为可监督的 Windows child runtime

**HYPOTHESIS**：Workbench 能获得足够 machine-observable lifecycle，而不需要解析脆弱自然语言。

**攻击方式**：auth prompts、TTY/PTY dependence、shell wrapper、exit semantics、child process、resume、interrupt、Windows-specific behavior。

### H-05｜Ready-for-Review 可以由 Git/GitHub facts 足够可靠地推导

**HYPOTHESIS**：repo identity + expected ref + commit SHA + remote visibility 等可形成稳定 Gate。

**攻击方式**：force push、detached HEAD、multiple remotes、dirty tree、Agent no-op、commit already existed、branch mismatch、push race。

### H-06｜Single active Run 足以证明 V0 value

**HYPOTHESIS**：不做 queue/parallelism 不影响首条真实 core loop。

**攻击方式**：回溯 Owner 是否经常同时跑多个 coding agents/tasks；若并发是高频主流程，应回 01/Owner，而不是 03 自行假定。

### H-07｜完整 restart recovery 可以放在 First Usable 之后

**HYPOTHESIS**：TA-3 前 conservative Interrupted/Unknown 足以保护 truth。

**攻击方式**：如果候选 host 生命周期天然频繁重启/失联，或 Codex 会脱离 parent 继续运行，则部分 durability 可能必须前置。

### H-08｜最薄 Project identity 不需要复杂 task/project management

**HYPOTHESIS**：stable project binding + stable run identity 足以支撑 V0；Selected Text 不需要升级为复杂 Task entity。

**攻击方式**：真实 rework/history/review evidence 是否无法在不建 Task entity 时可靠关联。

### H-09｜DSH 不应默认成为 base

**HYPOTHESIS**：按 First Vertical evidence 比较后再决定 DSH；历史投资不构成 architecture authority。

**攻击方式**：既要寻找 DSH 不适配的证据，也要寻找“DSH 已经稳定解决大部分 hard seams、重写反而浪费”的证据。

### H-10｜First Vertical 可以在薄 shell 中完成，不需要先做完整 Workspace framework

**HYPOTHESIS**：只做 current project + ChatGPT + run status + review action 即可证明产品价值。

**攻击方式**：检查是否存在一个被忽略的 formal product entry/lifecycle prerequisite，没有它 selection/execution 会成为孤立 demo。
