## 1. Product Vision

Personal Workbench 的长期方向，是成为 Owner 的个人 AI 工作台：把已经成熟、各自擅长的 AI 与开发工具组织进一个统一工作环境，减少人工搬运和上下文切换，让 Owner 把注意力集中在目标、判断、授权与验收上。

第一阶段不追求建设庞大的多 Agent 平台，也不以功能数量为价值证明。

当前只优先证明一个真实产品命题：

> **能否把 Owner 已经在使用的 ChatGPT → Coding Agent → GitHub → ChatGPT Review 工作流，收敛成一个明显更顺畅、仍由 Owner 控制的闭环。**

---

## 2. Primary Purpose

Personal Workbench 第一版存在的首要理由，是消除 Owner 在 AI Coding 协作中的机械协调劳动，而不是提供一个“更聪明的新 AI”。

当前最需要消除的人工环节包括：

- 从 ChatGPT 复制 Coding Instruction；
- 切换到 Agent / Terminal；
- 找到正确项目并粘贴任务；
- 分散查看 Agent 是否仍在运行、是否失败、是否完成；
- Agent 完成后再切回 ChatGPT；
- 手工输入“完成了，请去审核 GitHub 最新代码”之类的提醒。

Workbench 应把这些机械操作压缩为同一项目工作区中的直接交接与状态闭环。

---

## 3. Target User

当前唯一核心用户：**Owner 本人**。

这是一个 Personal Workbench，而不是面向团队、企业管理员或公共 SaaS 用户的通用平台。

因此 V0 优先优化 Owner 的真实高频工作流，不为了假想多人协作场景增加权限、组织、审批或复杂项目管理能力。

---

## 4. Job To Be Done

> 当我已经在 ChatGPT 中讨论出一条需要 Coding Agent 执行的指令时，我希望不离开当前项目工作区，就能选中 GPT 回复中的任意一段文字，直接交给我选择的 Agent 执行；执行期间只看必要状态、需要时展开详情；Agent 完成并把代码推送到 GitHub 后，我可以一键让当前 ChatGPT 对话基于 GitHub 最新代码独立审核，从而减少复制、切换、启动、观察和提醒等机械操作，同时保留我对任务、Agent 与 Review Gate 的最终控制。

---

## 5. Current Alternative / Simple Baseline

当前现实基线：

```text
ChatGPT Web
+ GitHub
+ Codex / Grok / Kimi 等外部 Coding Agent
+ Owner 人工协调
```

典型链路：

```text
Owner 提出需求
→ ChatGPT 讨论 / 架构 / 生成任务
→ Owner 人工复制任务
→ 切换到 Agent / Terminal
→ 找到项目并粘贴执行
→ 分散观察执行状态
→ Agent 完成、commit / push
→ Owner 切回 ChatGPT
→ 手工发送“完成了”
→ ChatGPT 读取 GitHub 最新代码 / commit / diff
→ Review
→ 若需返工，再次复制任务进入 Agent
```

Workbench 必须相对于这条简单基线产生明显体验收益，否则产品价值不成立。

---

## 6. Core Value

V0 的 Core Value：

> **把 ChatGPT 的思考与指令生成、本地 Coding Agent 的执行、GitHub 的实现事实以及 ChatGPT 的独立 Review 串成一个低摩擦、可观察、由 Owner 控制的项目级闭环。**

责任边界：

```text
ChatGPT
= 讨论 / 规划 / 生成指令 / Review / Debug

Owner
= 判断哪段内容具有执行意图 / 选择 Agent / 决定何时进入 Review / 最终验收

Workbench
= Project Context / Handoff / Agent Execution / Status / Review Handoff

GitHub
= 实现结果与 Review 的事实层

Coding Agent
= 在当前项目中执行实现任务
```

## 7. Confirmed Product Principles

### P1. ChatGPT 是核心组成部分，不是被替代对象

Workbench 不应默认自研一个 ChatGPT replacement。

产品要求是：Owner 能在 Workbench 工作环境中继续使用其现有 ChatGPT 工作流，并尽量避免为了规划、执行、查看结果和发起审核而频繁切换环境。

具体是内嵌 `chatgpt.com`、Browser / WebView、Companion 模式还是其它实现，属于技术验证与架构选择，不在产品定义阶段冻结。

### P2. Selected Text Defines Execution Intent

GPT 的整条回复不自动等于 Task。

由 Owner 通过鼠标选中文字，明确哪一段内容具有执行意图，然后执行 `Send to Agent`。

V0 不要求 GPT 使用特殊 Task 格式，也不要求 Workbench 自动理解回复语义。

### P3. Project-scoped Workspace

Owner 进入某个 Project Workspace 后，该工作区默认绑定当前项目。

ChatGPT 使用、Agent Handoff、执行状态与结果都围绕当前项目展开；每次发送任务时不重复选择 Project。

### P4. Human-controlled Routing

V0 由 Owner 选择目标 Agent，不自动 Routing。

第一版采用 **Codex-first vertical slice**：先只接通 Codex，完整验证纵向闭环；Grok、Kimi 等其它 Agent 在闭环稳定后横向扩展。

### P5. Progressive Execution View

Agent 执行时默认只显示必要状态，例如：

```text
Codex ● Running   02:14
```

需要时可展开查看完整执行日志 / Terminal Output。

完成后直接显示 Completion Report。

### P6. GitHub-mediated Review

Completion Report 是 Agent 的执行报告，不是最终事实证明。

Agent 完成并 Push GitHub 后，ChatGPT Review 应重新读取 GitHub 最新代码、commit / diff 并独立审核。

### P7. Review Handoff Should Remove Manual Reminder

Workbench 检测到任务已经达到 `Ready for Review` 后，V0 至少提供一键动作，例如：

```text
[让 GPT 审核]
```

由 Workbench 向当前 ChatGPT 对话发送类似“任务已完成并推送 GitHub，请审核最新代码 / commit / diff”的审核请求。

完全自动发送可作为后续增强，不要求成为首个可用版本的必要条件。

### P8. Design for Expansion, Do Not Build Empty Platform

AI Collaboration 是未来 Personal Workbench 的 **CORE** 区域之一。

UI / 信息架构应允许未来增加其它功能区，但 V0 不为了“以后可能会做”而提前实现 Today / Plan / Tracks / Knowledge / Dashboard 等未验证能力，也不应堆放大量 `Coming Soon` 占位功能。

> 设计上可扩展，产品上不占位。

## 8. Core Journey / Core Loop

V0 的首要真实纵向：

```text
进入 Project Workspace
        ↓
在 Workbench 工作环境中使用 ChatGPT
        ↓
与 GPT 讨论 / 规划 / 生成执行指令
        ↓
Owner 鼠标选中 GPT 回复中的任意一段文字
        ↓
Send to Codex
        ↓
Codex 在当前项目中真实执行
        ↓
Workbench 默认显示简洁运行状态
        ↓
需要时展开完整执行详情
        ↓
Codex 完成 + Completion Report
        ↓
最新实现 / commit Push GitHub
        ↓
Workbench 显示 Ready for Review
        ↓
Owner 一键“让 GPT 审核”
        ↓
当前 ChatGPT 对话读取 GitHub 最新代码 / commit / diff
        ↓
独立 Review
        ↓
通过 / 发现问题
        ↓
若需修复：Owner 选中 GPT 新的修复指令 → Send to Codex
```

核心循环可概括为：

> **Discuss → Select → Execute → Push → Review → Fix / Accept**

## 9. V0 Scope

### REQUIRED / Must-have

1. **Project-scoped Workspace**
   - 进入工作区时已经绑定当前项目；
   - Handoff 时不重复选择 Project。

2. **ChatGPT in Workbench Working Environment**
   - Owner 能在 Workbench 工作环境中继续现有 ChatGPT 讨论 / 规划流程；
   - 具体承载方式待技术验证。

3. **Selected Text Handoff**
   - 能选中 GPT 回复中的任意文字；
   - 直接发起 `Send to Codex`；
   - 不要求整条回复发送；
   - 不要求特殊 GPT 输出格式。

4. **Codex Real Execution**
   - 点击 Run 后必须真正让 Codex 在当前项目中执行，而不是只生成提示词或模拟状态。

5. **Execution State**
   - 至少可靠区分 `Running / Completed / Failed`；
   - 默认简洁；
   - 需要时可展开执行日志。

6. **Completion Report**
   - 至少帮助 Owner快速判断：做了什么、测试情况、Git / commit / push 情况、剩余风险或阻塞。

7. **GitHub / Ready-for-Review Gate**
   - Agent 进程结束不自动等于 Ready for Review；
   - 最新实现应已进入 GitHub 后才能进入 Review Handoff。

8. **One-click GPT Review Handoff**
   - Ready for Review 后，无需 Owner 手工切回并重新输入提醒；
   - 一键向当前 ChatGPT 对话发起基于 GitHub 最新实现的 Review 请求。

9. **Rework Loop**
   - GPT Review 给出修复指令后，可以再次通过选中文字 → Send to Codex 进入下一轮执行。

### First-agent Boundary

V0 / First Usable 只要求接通 **Codex**。

```text
ChatGPT
→ Selected Text
→ Codex
→ GitHub
→ ChatGPT Review
```

这是开发顺序和产品验证策略，不代表未来只能支持 Codex。

## 10. Deferred / Future

以下能力当前不阻塞 V0 产品价值验证：

- Grok / Kimi / 其它 Agent 接入；
- 自动 Agent Routing；
- 根据成本、能力、速度、额度自动选 Agent；
- Multi-Agent 自动编排；
- Agent-to-Agent delegation；
- 自动任务拆分；
- 全自动 Review → Fix → Re-review 循环；
- Review Ready 后默认自动给 GPT 发消息；
- Agent Quota / Usage Dashboard；
- Cost / Performance Analytics；
- 复杂 Task History / Project Management；
- Today / Plan / Tracks 等规划模块；
- Knowledge Base / Obsidian replacement；
- Personal Dashboard 或其它个人工作台功能区。

这些能力未来必须重新通过真实需求与 Product Discovery，而不是因为 UI 为其预留空间就自动进入 Roadmap。

---

## 11. Non-scope for V0

V0 不负责：

- 替代 IDE / Code Editor；
- 替代 GitHub；
- 自研 Coding Agent；
- 自研 ChatGPT replacement；
- 完整项目管理软件；
- 完整个人知识管理系统；
- 面向团队 / 企业的权限与组织系统；
- 为未来平台预建大规模通用 Agent Orchestration Platform。

## 12. Product Success Criteria

V0 不以“功能列表已经实现”作为唯一成功标准，必须跑通真实纵向。

### Functional Success

至少能用一个真实 Coding Task 完成：

```text
1. 打开 Personal Workbench
2. 进入一个真实 Project Workspace
3. 在 Workbench 工作环境中与 ChatGPT 讨论真实需求
4. GPT 给出 Coding Instruction
5. Owner 选中其中需要执行的一段文字
6. Send to Codex
7. Codex 在当前项目真实执行
8. Workbench 显示 Running
9. 需要时可展开查看执行过程
10. Codex 完成并产生 Completion Report
11. 最新实现 / commit Push GitHub
12. Workbench 进入 Ready for Review
13. Owner 点击“让 GPT 审核”
14. 当前 ChatGPT 对话收到 Review Request
15. GPT 读取 GitHub 最新代码 / commit / diff
16. GPT 给出独立审核结果
17. 若有问题，可再次选中修复指令并进入 Codex
```

其中任一关键交接仍需要恢复到原有大段人工复制 / 切换流程，都需要重新评估 V0 是否真正成立。

### Product Value Success

V0 应产生以下可感知变化：

1. **明显减少窗口切换**：核心 Coding Loop 主要发生在一个 Project Workspace 中；
2. **基本消灭 GPT → Agent 的 Copy / Paste**：高频交接变为 `Select → Send to Codex`；
3. **消灭 Agent 完成后的手工 GPT 提醒**：至少通过一键 Review Handoff 完成；
4. **不制造新的表单负担**：不能用复杂 Task 管理流程替代原本两次复制粘贴；
5. **保留关键 Human Gate**：Owner 决定执行什么、何时执行、何时 Review、最终是否 Accept；
6. **真实愿意持续使用**：经过连续真实 Coding Tasks 后，Owner 自然倾向于从 Workbench 跑任务，而不是回到旧人工流程。

---

## 13. Product Failure Conditions

出现以下情况之一时，即使 UI 或功能模块很多，也不能轻易判定 V0 Product PASS：

- ChatGPT 与 Agent 之间仍需频繁 Alt+Tab；
- GPT Instruction 仍主要靠手工复制 / 粘贴；
- `Send to Codex` 需要填写大量表单与重复配置；
- Workbench 无法可靠判断 Agent 是 Running、Failed 还是 Completed；
- Agent 结束被错误等同于 GitHub 已存在可审核的新实现；
- GPT Review 仍依赖 Owner 每次手工输入“完成了”；
- 大量未来模块 / Dashboard / Coming Soon 抢占 V0 开发资源；
- 界面看起来像完整平台，但一个真实 Coding Task 的纵向闭环无法顺畅跑通。

## 14. UI / Information Architecture Intent

Owner 提供的外部 Workbench 效果图仅作为未来整体视觉与信息架构参考，当前吸收的重点是：

- 模块化一级导航；
- `CORE` 与未来其它功能区的层级感；
- 中央主工作画布；
- Project / Workspace 概念；
- 卡片、状态灯与渐进式状态表达；
- 为未来功能区留下可扩展的信息架构。

这些参考图中的 Today / Plan / Tracks / 项目轨道 / Dashboard 等具体功能 **不自动构成 V0 Requirement**。

当前唯一需要完整打磨的核心区域是：

> **CORE → AI Collaboration**

V0 应看起来像最终 Personal Workbench 中第一个成熟区域，而不是一个未来准备被废弃的临时 Demo；但不得因此提前建设完整未来平台。

## 15. Needs Technical Validation

以下是产品要求对应的技术可行性问题，不在本文件中冻结实现方案：

### TV-01｜Existing ChatGPT Experience in Workbench

验证 Windows Workbench 中承载 Owner 已登录的现有 `chatgpt.com` 工作流的可行性、稳定性、登录 / Session、Projects、文件上传与相关能力边界。

需要比较但不预先批准：Embedded Browser / WebView / Companion / API-based fallback 等路径。

### TV-02｜Selected Text → Workbench Action

验证在所选 ChatGPT 承载方式下，Workbench 是否可以可靠获得 Owner 选中的 GPT 文本并触发 `Send to Codex`。

### TV-03｜Programmatic Review Handoff

验证 Workbench 是否能可靠地向当前 ChatGPT conversation 填充 / 发送 Review Request；若完全自动发送不稳定，至少验证一键发送的可行路径。

### TV-04｜Codex Real Execution + Status

验证 Workbench 如何在绑定项目上下文中真实启动 Codex，并可靠获取执行状态、日志、结束状态与 Completion Report 所需信息。

### TV-05｜GitHub Ready-for-Review Evidence

验证 Workbench 如何可靠判断最新实现已经 commit / push 到预期 GitHub repository / ref，而不是仅根据 Agent 自述宣布 Ready for Review。

这些问题应由 `02｜参考审计与技术研究` / `03｜架构与开发路线` 处理，并把结果带回 Product / Architecture Gate；研究结果不得自行改写产品目的。
