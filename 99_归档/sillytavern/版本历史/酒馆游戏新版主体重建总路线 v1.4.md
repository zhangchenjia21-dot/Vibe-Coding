# 2. 总体开发顺序

新版游戏严格按以下阶段推进：

```text
G1 真实模型兼容性
↓
G2 最小世界运行内核
↓
G3 正式世界能力垂直扩展
↓
G4 程序判定与 Dice
↓
G5 长期世界连续性
↓
G6 Save / Continue / Restore
↓
G7 Crash / Resume / Recovery
↓
G8 网页产品化
↓
G9 资产生态接入
↓
G10 Provider 扩展
↓
G11 Alpha / 全系统验收
↓
G12 Windows Release
```

核心原则：

> 先证明纵向真实运行链成立，再增加横向能力。

任何阶段的下游工作不得建立在尚未通过真实验证的上游能力之上。

工具总倾向：

- G1：Codex 主力，Grok Build 不参与正式工作；
- G2–G7：Codex 负责运行核心，Grok Build 负责持续演进的最小 Playtest Shell；
- G8：Grok Build 成为正式前端主力，Codex 负责 Contract、真实集成、安全和最终审核；
- G9：Codex 负责资产 / Runtime 协议与 Adapter，Grok Build 负责动态声明式 UI 的表现层；
- G10–G12：按后端 / 前端职责继续分配。

# G1｜真实模型兼容性

## 目标

在没有正式游戏、数据库和网页的情况下，用真实 DeepSeek 证明：

1. 模型能够稳定使用我们的最小语义协议；
2. 程序能够稳定解析模型输出；
3. 模型语义错误不会突破 Program Judge；
4. 协议适合真实模型，而不是只适合人工 Fixture。

## 内容

建立最小 CLI / Spike：

```text
Scenario
→ Player Input
→ Model-safe Context
→ DeepSeek
→ Semantic Proposal
→ Schema Validation
→ Program Judge
→ Result Report
```

第一版只支持极少语义，例如：

- move；
- item_transfer；
- npc_reaction；
- no_change / clarification。

必须测试：

- 明确行动；
- 否定；
- 条件；
- 愿望；
- 询问；
- “给某人看”；
- “交给某人”；
- 歧义实体；
- 不存在 Ref；
- 隐藏信息；
- 旧项目真实失败形状的脱敏抽象。

## 禁止提前建设

- Next.js；
- SQLite；
- Save；
- Restore；
- Dice；
- Memory；
-复杂 Relationship；
-多 Provider；
-资产协议；
-正式游戏 UI。

## 退出条件

必须取得真实模型实验数据，至少证明：

- 结构化输出高度稳定；
- 明确正常语义达到可接受正确率；
- Program Judge 对未授权世界变化错误接受数 = 0；
- Schema 合法但 Judge 大量拒绝的情况不存在；
- 重复运行具有可接受稳定性。

如果协议不可靠：

停留 G1，修改协议。

不得带着“以后再修”的模型接口进入 G2。

# G2｜最小世界运行内核

## 目标

建立新版第一次真正的游戏 Turn。

最小世界只需要：

- 一个玩家；
- 一个 Scene；
- 一个 NPC；
- 一个 Item；
- 一个简单时间值；
- 少量公开 / 隐藏事实。

最小正式链：

```text
Player Input
→ Capability
→ Model Context
→ Semantic Proposal
→ Program Judge
→ Formal State Change
→ Atomic Commit
→ Narrative
```

## 重要限制

第一版：

- 不需要 Dice；
- 不需要 Save；
- 不需要 Recovery；
- 不需要复杂 Event / Memory；
- 不需要多 Provider；
- 不建设正式产品级网页。

运行核心可以先通过 CLI / API Harness 建立，但 G2 在进入真人验收前必须同步建立一个最小 **Playtest Shell**。

Playtest Shell 的职责不是产品化，而是让项目所有者能够以真实玩家路径完成 Turn。最少包含：

- 对话 / 叙事流；
- 玩家输入框与发送；
- loading / submitting 状态；
- 基础错误提示；
- 当前 Scene / Place；
- 玩家可见人物；
- 玩家可见物品；
- 必要的最小玩家安全状态摘要。

不得为了 G2 Playtest Shell 提前建设：

- 首页；
- 游戏库；
- 正式创建流程；
- 完整人物详情；
- Save Center；
- 设置中心；
- 完整 Design System；
- 复杂动画；
- Runtime UI Contribution；
- 资产安装 UI。

G2 Playtest Shell 应保持代码干净、可演进，但不构成 G8 正式产品 UI 的冻结承诺。

## 最关键退出条件

**真实 DeepSeek 必须连续完成一批真正 committed 的 Turn。**

不是 deterministic Provider。

不是 Fake SDK。

不是人工 Fixture。

必须证明真实模型环境下：

- Turn 能提交；
- 世界状态正确；
- 玩家代理权正确；
- 模型错误只能被拒绝；
- 没有半提交；
- 项目所有者可以通过 Playtest Shell 完成真实玩家 Turn；
- Playtest Shell 只读取玩家安全投影，不接触隐藏状态。

G2 未通过前，不允许开始横向扩展。

## 目标

逐领域增加 World OS 正式能力。

严格一个领域一个领域推进。

推荐顺序从简单能力开始，例如：

4. Relationship；
5. Item 状态；
6. Event；
7. Time；
8. Memory；
9. Clue / Knowledge。

具体顺序可以根据实际依赖调整。

## 每个领域必须走完整竖切

例如 Position：

```text
真实玩家表达
→ Capability
→ DeepSeek Semantic Proposal
→ Program Judge
→ Position State
→ Atomic Commit
→ Narrative
```

Item Transfer 同理。

## 硬规则

某一领域：

**真实 DeepSeek 竖切没有通过**

则：

**不开发下一个领域。**

从 G2 开始维护同一个可持续演进的 Playtest Shell。G3 每增加一种玩家可感知能力，都必须同步增加最小人工可观察 / 可操作路径，例如：

# G4｜程序判定与 Dice

## 目标

在无骰 Turn 已经稳定以后加入正式判定。

正式链：

```text
Semantic Proposal
→ Program Judge
→ Resolution Plan
→ Program RNG / Dice
→ Program Outcome
→ Final Adjudication

→ Narrative
```

## 冻结原则

- Dice 由程序控制；
- Outcome 由程序决定；
- Dice 后模型不能重新决定正式世界；
-模型只负责叙事；
-结果 vocabulary 只有真实玩法需要时才扩展。

第一版不要追求：

-万能判定 DSL；
-世界包可编程判定引擎；
-十档结果体系。

从最小可靠机制开始。

## Playtest 要求

G4 必须把正式判定结果接入现有 Playtest Shell，以最小但清晰的方式显示玩家应当知道的信息，例如：

- 是否发生判定；
- 公开 Dice 结果（若规则要求公开）；
- Program Outcome；
- 最终叙事。

具体产品视觉可以留到 G8，但真人 UAT 必须能够确认程序到底裁定了什么。

- Relationship continuity；
- Event continuity；
- Memory；
- 长期时间推进；

- 必要任务 / 承诺 / 计划。

## 已完成并冻结的关键能力

- Character Knowledge 成为正式权威状态；
- World Truth / NPC Knowledge / Player Knowledge 分离；
- Pending Commitment；
- Pending World Action；
- Background Progression；
- bounded Continuity Context：recent Turns `<= 4`、relevant Events `<= 6`，不发送完整 transcript；
- Semantic private context 与 Narrative player-safe context 分离；

- read_only_query 不形成 Formal Turn；
- Dialogue / Observation / Inner Expression 可以形成 Formal Turn；
- No Phantom World Change；
- 玩家主动世界变化采用 Program deterministic Direct Fast Path + Model Candidate 受控 fallback；
- Model semantic result 本身不拥有正式世界提交权；
- Hard Safety 与安全 semantic variation 分开统计。

## G5 最终 Gate 解释

以下继续作为硬 Gate：

- Player Agency violations = 0；
- Phantom World Changes = 0；
- Hard Safety failures = 0；
- Hidden Knowledge 不泄露；
- Capability 不可绕过；
- Formal Outcome 与 Narrative 一致；
- Atomic Commit。

以下安全差异不再单独阻塞阶段：

- Dialogue / Read-only 的合理语义差异；
- 偶发多一次 Confirmation；
- 生僻表达 clarification；
- 不常见 paraphrase 未走 Direct Fast Path。

## 授权架构止损

G5 关闭后，不再为单个自然语言句式持续增加 Regex、确认规则或重构授权链。

# G6｜Save / Continue / Restore

> 状态：**PASS / CLOSED（2026-08-15）**  
> 正式收口依据：`12_酒馆游戏_G6_SaveContinueRestore收口裁定_v1.0_2026-08-15.md`

## 目标

在正常运行链稳定后建立完整权威状态的 Save / Continue / Restore / Branch 语义。

## 已完成并冻结的关键能力

- Save 只保存 stable committed state；
- canonical snapshot 是不可变恢复材料，不是第二套实时事实源；
- Snapshot 完整覆盖隐藏状态、Knowledge、Commitment、Pending World Action、Event / Formal history、Dice / Resolution 与 G5 continuity structures；
- Provider raw、reasoning、Prompt、context cache、stale Confirmation、read-only ephemeral response 不进入 Save authority；
- Continue 从当前 committed authoritative state 重新构建 player-safe projection 与 bounded context；
- Restore 原子、fail closed、Provider calls = 0；
- Restore 本身不形成 Formal Turn、不推进 worldTime、不创建普通 Event；
- Restore 可以恢复旧领域世界，但执行 revision 保持单调；
- `revision` 不是 Timeline identity；
- Branch 只在 canonical divergence 后的第一次成功新 Formal Turn 创建；
- 第一次 divergent Restore 冻结 immutable original future；
- 连续 Restore 只是 timeline navigation，不覆盖 origin；
- 回到 original future 会取消 pending，不产生 Branch；
- read-only / failed execution 不消费 pending；
- Timeline metadata 与世界恢复处于同一原子事务；
- raw Snapshot / private state 不发送浏览器。

## 最终 Gate

最终 review-03：`g6:test` 15 tests PASS；`g6:check` 438 tests PASS；68 corpus valid；lint / typecheck / build / disclosure / launcher PASS；DeepSeek `deepseek-v4-pro` Smoke PASS；Restore Provider calls = 0；exact restore / Commitment restore / Branch navigation PASS；项目所有者真人 UAT PASS。

## 阶段止损

G6 关闭后，不因 Archive GC、完整 Timeline Manager/UI、正式 Save Center、Undo/Re-input、Crash/Response-loss Recovery 重开。只有正式状态恢复错误、Branch 误判、Atomic Restore 破坏、隐藏状态泄露、Snapshot 成为第二事实源或恢复绕过权限等硬问题才允许重开。

## G8 新增正式体验收口：自然输入、撤回与多动作

G5 真人体验确认了两个不阻塞 G5、但应在正式产品化阶段解决的问题：

1. **减少过度 Confirmation**：普通低风险自然输入不应频繁显示“我理解为：本回合只执行【...】”。可以更信任模型的自然语言理解，但 Program 继续拥有 Capability、Judge、Formal Outcome 与 Atomic Commit 权限。
2. **玩家可见撤回 / 重新输入**：当模型理解与玩家意图不符时，优先提供低摩擦纠错体验。撤回能力必须建立在 G6 Save / Restore 与 G7 Recovery / idempotency 已经稳定的基础上，不允许静默改写世界历史。
3. **受控多动作自然输入**：支持“返回酒馆，并睡到第二天”这类顺序明确的高频表达。目标不是万能 Multi-action Planner，而是一个玩家输入内的受控顺序动作；不得 partial commit，最终仍是一个 Formal Turn 的原子结果。

这些属于 Player Product UX，不回头阻塞 G5、G6 或 G7。

# G8 的重要架构要求：Runtime-extensible UI

新版网页从第一天必须：

**asset-ready / runtime-extensible**

Core UI 不能假定：

- HP；
- MP；
-力量；
-敏捷；
-等级；
-金币；
-固定右栏栏目。

页面由：

```text
Core UI Surfaces
+
Runtime UI Contributions
```

组成。

例如未来安装魔法拓展包后，可以声明：

- 人物属性栏增加 HP；
-人物属性栏增加 MP；
-右侧增加“魔法”栏目；
-增加法术列表；
-增加魔法状态显示。

但是：

拓展包不能：

-执行任意 JS；
-注入任意 React；
-修改 DOM；
-执行 eval；
-直接修改 Game State。

未来采用声明式 UI Contribution：

```text
Expansion / Runtime Definition
→ UI Contribution
→ Game UI Host
→ Game-owned safe components
```

UI Action 只能产生 Action Intent / Capability。

不能直接修改正式世界。

# 3. 全阶段共同硬约束

## 3.1 真实模型优先

任何新的模型语义能力：

自动化通过后，

必须尽早通过真实 DeepSeek 垂直验证。

不得拖到最终真人 UAT 才第一次接触真实输出。

---

## 3.2 Model Output 永远不是 Formal World State

模型只负责：

-理解；
-语义建议；
-NPC /世界推演；
-叙事。

程序负责：

-身份；
-授权；
-规则；
-版本；
-时间；
-RNG；
-Dice；
-状态；
-因果；
-最终提交。

---

## 3.3 不兼容早期实现时优先删除，不优先兼容

新版未发布阶段：

错误设计应：

**删除 / 重写**

而不是形成：

v1  
→ v2  
→ v3  
→ legacy adapter  
→ compatibility adapter

只有真正存在发布用户数据以后才建立严格迁移兼容政策。

---

## 3.4 垂直验证优先于横向建设

不得再次发生：

- UI 已完成但 Turn 不工作；
- Save 已完成但模型接口没跑通；
- Recovery 已完成但第一条真实 Turn 没提交；
-多个 Provider 已支持但主要 Provider 没稳定。

---

## 3.5 测试必须包含真实模型失败语料

旧项目积累的真实失败应转化成脱敏 regression corpus。

测试层级必须区分：

- Schema；
-Program Judge；
-deterministic；
-Fake SDK；
-历史真实模型 failure corpus；
-真实 Provider；
-真人产品 UAT。

不得把 deterministic Provider 成功称为真实模型成功。

---

## 3.6 Project Owner 不承担调试循环

正常流程：

```text
Codex / Agent 实现
→ 自动化验证
→ 批量审核
→ 集成节点
→ 项目所有者真人验收
```

不得重新变成：

```text
发现字段问题
→ 让项目所有者点一次
→ 修一个字段
→ 再点一次
```

---

## 3.7 Asset-ready / Asset-agnostic

在 G9 之前：

游戏不实现资产协议。

但所有运行模块必须避免把 Demo 世界写死进 Core。

核心接受：

```text
Runtime Definition
→ Game Bootstrap
→ Game State
```

当前手写测试世界只是 Runtime Definition 的一个来源。

未来资产是另一个来源。

`asset-ready` 只表示 Runtime 不把 Demo 或固定 RPG 机制写死，并保留未来可被资产描述的边界；**不表示需要兼容当前现有 tavern-asset-spec。**

---

## 3.8 Runtime-extensible UI

页面不得假设固定 RPG 状态和固定功能栏。

未来机制资产必须可以通过声明式 UI Contribution：

-增加人物状态显示；
-增加资源条；
-增加状态面板；
-增加侧栏模块；
-增加安全 Action。

UI Host 负责：

-布局；
-权限；
-可见性；
-冲突；
-组件渲染。

资产不拥有前端执行权。

---

## 3.9 从 G2 起持续保持真人可玩路径

G1 可以完全无前端。

从 G2 开始，项目必须始终保留一个随运行能力持续演进的 Playtest Shell。

任何新增的玩家可感知能力，都必须同时具备：

```text
实现
→ 自动化验证
→ 玩家安全 DTO / API
→ Playtest Shell
→ 真实 DeepSeek
→ 真人垂直验收
```

人工验收按完整能力 / 阶段批量进行，不因单个字段或小补丁反复要求项目所有者操作。

Playtest Shell 不是正式产品设计冻结；其职责是尽早暴露真实玩家路径上的集成问题。

---

## 3.10 Codex / Grok Build 工具分工

默认工具策略：

> **Codex = 游戏运行、后端、协议、数据、安全、集成主力。**  
> **Grok Build = 前端页面、交互、视觉、响应式和声明式 UI 渲染主力。**

### Codex 优先负责

- World OS 运行语义；
- Semantic Protocol；
- Model Adapter；
- Program Judge；
- Capability / Authorization；
- RNG / Dice；
- Atomic Commit；
- 数据库 / Migration；
- Save / Restore / Recovery；
- Provider；
- Asset Adapter；
- API / DTO 契约；
- 玩家安全投影；
- 权限 / 安全；
- 自动化 / E2E / Release；
- 前端最终集成审核。

### Grok Build 优先负责

- G2 Playtest Shell；
- G3–G7 新能力对应的最小人工测试 UI；
- G8 正式网页绝大多数页面和交互；
- 正式 Session 视觉；
- 人物 / 物品 / 关系 / 线索等展示层；
- Save / Recovery 的产品级 UX；
- 响应式 / 移动端 / Accessibility；
- Design System / 动画 / polish；
- G9 声明式 Runtime UI Contribution 的渲染组件和 UI Host 表现层。

### 固定协作顺序

前端任务默认采用：

```text
Codex 冻结玩家安全 Contract / DTO / Mock
→ Grok Build 实现前端
→ Codex 接真实 Runtime、做安全 / 类型 / E2E / 集成审核
```

Grok Build 不得自行发明正式 Runtime 字段、数据库字段、Asset Schema 或游戏规则。

若前端发现现有 Contract 无法表达真实产品需求，必须先回到正式 Runtime / API Contract 进行裁定，再继续实现。

“写了多少模块”

作为进度。

任何技术建设如果不能帮助回答这个问题，都不得优先于核心纵向链。
