## 1. 当前真人 UAT 已确认的事实

项目所有者已通过正式 Launcher / Product UI 验证：

- 创建新游戏 → AI 辅助创建 → 三 Step Creation Project → Final Create → 开始游戏主路径成立；
- Creation 快速预设 / 手工输入 / AI Fill 共存；
- `暂不设定` / `AI 补全此项` 交互已改善；
- 更多世界 / 更多角色设定入口可见性已改善；
- API Key server-only `.env.local` 持久化及重启状态表达已收口。

因此：

> `G8-WEB-05` 的 New Game / API / Creation **产品主路径 PASS**，不再重做 Creation UI。

---

## 2. 重新审核后的关键结论

不能直接进入 G9。

原因不是还有普通 UI polish，而是 G8 仍有若干 **阶段级能力未闭环**。

其中最重要的遗漏是：

> `G8-WEB-04｜Runtime-extensible UI Host Foundation` 只有 Foundation / fixture / preview / Product presentation 证据充分，但最终的 **正式 Host Convergence** 仍未完成。

G8 / G9 边界仍保持：

```text
G8
→ 用 typed handwritten Runtime/UI Definition 证明真实 Game Host 能力
→ 冻结 Game Host 的实际能力边界

G9
→ 才根据真实 Host 设计 asset-spec vNext / Creator machine contract
```

不得让 asset-spec 反向补定义 Host。

---

## 3. G8-WEB-04｜必须重新标记为 FINAL CONVERGENCE ACTIVE

当前已经成立：

- Core 五 Surface；
- 9 类 Host Capability typed contract；
- Owner / Contributor；
- duplicate Owner fail closed；
- secondary View；
- safe component vocabulary；
- Product UI 的 Extension Surface / Contextual / Notice 等 fixture/preview 表现；
- reorder 语义与 Restore 分离。

但还存在以下 G9 前必须关闭的 Host gap。

### H01｜正式 Bootstrap 仍是 Core-only Host

正式 `G2本地服务` 当前使用 `createCoreOnlyPlayerProductUiHost()`。

丰富 Host Definition 主要通过 test fixture / preview query 注入。

必须增加一条正式、typed、非 asset-spec 的内部注入路径，使：

```text
handwritten Runtime UI Definition
→ Host Assembly
→ Real Product Server
→ Player-safe Product DTO
→ Formal Product UI
```

真实纵向成立。

默认正式游戏可以仍然没有假 Expansion，但 Bootstrap 必须能够接收真实 game-specific Runtime UI Definitions；G8 test/demo 使用 handwritten definitions 验证，不得依赖浏览器 `?host=` 伪造正式能力。

### H02｜Creation 重构后 Host `game_creation_settings` 合同漂移

当前 Host Creation Field 仍使用旧五段式时代的：

- `sectionId`；
- `required`；
- `playerEditable`；
- old GameCreation sections。

新正式 Creation Project 已冻结：

- `expansion_settings`；
- `character`；
- `opening`；
- Creator-declared field schema；
- AI fill values, never invent schema；
- active/dormant lifecycle。

必须让 Host 的 Game Creation Contribution 与新 Creation Project 对齐。

不得让 G9 同时面对两套 Creation Contribution language。

### H03｜旧 Host Creation Adapter 仍依赖 Five Sections

当前 `玩家界面创建贡献适配器` 仍直接依赖：

- `GAME_CREATION_SECTIONS`；
- `CORE_GAME_CREATION_FIELDS`；
- legacy `GameCreationFieldDefinition`。

必须迁移为新 Creation Project Contribution adapter，并保留 Host / Creation 单一职责：

```text
Runtime UI Definition declares safe creation contribution
→ Host validates safe component/placement
→ Creation adapter converts to current CreationContributionDefinition
→ Creation Project owns values/lifecycle
```

### H04｜Contribution 来源身份必须可追踪

新 Creation Contribution 需要知道其 `ownerGameplayId` / 等价 owner identity，才能在 gameplay enable/disable 时正确 active ↔ dormant。

Host assembly 不能把 contribution 来源 Definition identity 丢掉。

G8 必须形成内部 typed owner/source bridge；最终外部 asset ID / schema 命名仍留给 G9。

### H05｜Surface Order Preference 目前只有进程内存实现

当前默认是 `InMemoryPlayerProductUiPreferenceStore`。

G8 必须裁定并验证正式 Product restart 后的 UI Preference 行为。

最低要求：

- preference 仍独立于 Game State / Save Snapshot；
- Restore 不回滚；
- 产品重启后可恢复玩家排序；
- 新增 Surface 时保持已有相对顺序并确定性插入；
- 不形成 Formal Turn / Event / worldTime。

可以使用独立 SQLite/Product preference storage，不得塞进 canonical world state。

### WEB-04 退出证明

必须至少有一组 handwritten internal definitions，通过真实 server/Product path 验证：

- Player Status；
- Player Character Detail；
- Entity Detail；
- Core Surface Contribution；
- Map Overlay；
- Narrative Contextual；
- Global Notice；
- current Game Creation Contribution；
- Extension Surface；
- secondary View；
- reorder；
- duplicate Owner fail closed；
- unsafe arbitrary frontend code fail closed；
- hidden/private data 不披露。

## 4. G8-WEB-05｜产品主路径 PASS，但仍有技术迁移尾项

### C01｜Legacy One Draft / Five Sections production path 退休

当前正式 Product UI 已经只走 Creation Project，但 production 仍保留：

- `GameCreationDraft`；
- `GAME_CREATION_SECTIONS`；
- `/api/product/new-game/drafts...`；
- Product client legacy draft methods；
- `GameCreationPublicApi` legacy Draft store/generation/create；
- 旧测试与旧 adapter。

Host Creation Contribution 迁移完成后，必须按 Supersession 原则删除旧 production authority。

进入 G9 时正式 New Game authority 必须唯一：

> `Creation Project`。

## 5. G8-WEB-06｜REQUIRED：Save Center + Recovery / Error UX

不能降级为普通 polish。

当前正式 `SaveCenterPage` 仍是“读取存档尚未开放”占位页。

G6 / G7 Runtime 虽已 PASS，但 G8 的目标是 Player Product UI，必须让玩家通过正式产品路径：

- 查看可用 Save；
- Create Save；
- Continue；
- Restore；
- 理解 Branch pending / committed result / Recovery 的玩家安全状态；
- 遇到恢复失败时得到可理解、非工程术语的错误与安全下一步。

最低产品化即可；不建设万能 Timeline Manager / Error Center。

---

## 6. G8-WEB-07｜REQUIRED：Correction / Undo / Re-input

原路线明确把它列入 G8 的“正式体验收口”。

必须建立低摩擦玩家纠错路径，并保持：

- 不静默改历史；
- 不绕过 G6 Restore；
- 不破坏 G7 exactly-once / idempotency；
- 不把失败输入算作成功 Turn；
- 玩家明确知道自己是在撤回 / 恢复 / 重新输入。

不要求建设任意历史编辑器。

---

## 7. G8-WEB-08｜REQUIRED：Controlled Multi-action

原路线同样把它列为 G8 正式体验收口。

而且它与 G9 有直接语义关系：未来 Expansion 可以声明 Action Intent / Resolution capability，因此在冻结 asset-spec 前，Core 必须先确定：

- 一个 Player Input 如何表达少量顺序明确的多个动作；
- 是否形成一个 Formal Turn；
- Program 如何保证 no partial commit；
- 顺序 / 失败 / 时间推进边界；
- 不建设万能 Planner。

因此 WEB-08 不应推迟到 asset-spec 之后再改变基础 Action semantics。

## 8. G8-WEB-09｜REQUIRED，但只要求阶段关闭基线

以下必须在 G8 CLOSED 前完成：

- desktop + narrow 关键路径可用；
- keyboard / focus / basic accessibility 不存在明显 blocker；
- Product E2E 覆盖创建、继续、Turn、Save/Restore、Recovery、Undo/Re-input、Controlled Multi-action 与 Host vertical proof；
- no-key 与 configured-key 关键路径；
- final GitHub-first review；
- 项目所有者真人 Stage UAT。

以下可以留到 G11 / Product Polish：

- 所有设备像素级适配；
- 高级动画；
- 视觉细节极致统一；
- 大规模 performance tuning。
