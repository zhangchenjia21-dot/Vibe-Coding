## 2. 第二版新增的项目级事实

### 2.1 Engineering Correctness 不等于 Playability Completeness

第二版已证明：

- Authority；
- Formal Turn；
- Save / Restore；
- Recovery；
- Creation Project；
- Host；
- Multi-action；

可以全部工程正确，但真实创建出的游戏仍可能是空壳。

因此 G8 Stage Close 必须同时证明：

```text
Engineering Correctness
+
Real Creation Instance
+
Playability Completeness
+
Integration of Meaning
+
Project Owner UAT
```

### 2.2 Rich Fixture 不等于真实创建实例

正式 Gate 必须同时拥有：

```text
Handwritten Rich Fixture Vertical
+
Creation Project
→ Final Create
→ Real Game Instance
→ Multi-turn Product UAT
```

不能再用富测试世界替代正式 Creation 结果。

### 2.3 Contract 不等于能力

所有宣称“已支持”的能力必须标注：

```text
Contract only
Fixture proven
Production vertical proven
Product UAT proven
```

动态推荐、Preview、Router、Host、Materialization 等后续能力都必须追问真实 Owner、数据源、消费者与状态刷新，而不能因为类型和 UI slot 存在就判完成。

### 2.4 Affordance Consistency

```text
Narrative / UI 呈现为具体可交互
→ 必须有 authoritative referent + current capability
```

Narrative 不得创造下一回合无法解析的具体路人、地点、物品；UI 推荐不得引用不存在的对象。

### 2.5 Bounded Context 不能变成 Starved Context

不同模型继续只读取 purpose-built、player-safe、current relevant working set；但当前职责必需的玩家背景、目标、NPC public profile、可达地点与真实对象必须完整提供。

### 2.6 Source Asset → 当局游戏资产 → Runtime State

当前正式三层：

```text
Source Asset Library
↓ snapshot / bind
Game-local Canonical Assets｜当局游戏资产
↓ instantiate / project
Authoritative Runtime State
```

- Source Asset 是跨局模板，不被本局反写；
- 当局游戏资产是本局可持续演化的世界定义；
- Runtime State 管理位置、数值、持有、timer、Turn / Event 等运行状态。

### 2.7 Model 可以书写真实世界，但 Commit 归 Program

正式原则：

> **Models may author and evolve game-local reality, but only through Program-owned typed commit boundaries。**

模型可以提出/生成新的 NPC、地点、物品、连接和当局资产字段；Program 负责 schema、world constraint、stable identity、atomic commit、persistence、recovery 与 information boundary。

### 2.8 World Growth != Prompt Growth

当局游戏资产和 Runtime 世界可以增长到大量实体；普通回合模型 Context 仍由第 15 号 Context Orchestration 裁剪为 current relevant projection。

除既有 A/B/C 分类外，必须检查：

- 现有 asset-spec 是否把 Asset 错当成 Runtime 永久只读定义；
- 是否区分 Source Asset / Game-local Asset / Runtime State；
- 是否假定所有 NPC 都必须来自 Character Card；
- 是否假定所有地点必须在 World Pack 预枚举；
- 哪些现有字段可以作为 canonical anchor / hard constraint；
- 哪些字段应该允许当局实例演化；
- provenance、clone/bind、local patch、materialization boundary 如何表达；
- 现有 Creator 是否只会枚举实例，而不会 author 规则、锚点和生成边界。

```text
→ local instance / snapshot

→ local fields mutate
→ source unchanged
```

### Dynamic Character

```text
Model typed Character proposal
→ Program validation
→ local Character Asset
→ Runtime binding
→ stable identity across Turns
```

### Dynamic Place / Connection

```text
Model typed Place / Scene / Connection proposal
→ atomic local asset commit
→ Runtime graph update
→ later navigation uses same identity
```

### Existing local asset mutation

```text
Model typed patch
→ mutable-field / information-boundary validation
→ local revision commit
→ Save / Restore reproduces value
```

### Context

```text
Growing local asset graph
→ Current Relevant Set
→ bounded JIT projection
```

10. Product Owner UAT 是否使用真实任务，而不是工程 fixture。
