# 2. 总体开发顺序

新版游戏严格按以下阶段推进：

```text
G1 真实模型兼容性
↓
G2 最小世界运行内核
↓
G3 正式世界能力垂直扩展
↓
G4 程序判定与 Dice
↓
G5 长期世界连续性
↓
G6 Save / Continue / Restore
↓
G7 Crash / Resume / Recovery
↓
G8 网页产品化
↓
G9 资产生态接入
↓
G10 Provider 扩展
↓
G11 Alpha / 全系统验收
↓
G12 Windows Release
```

核心原则：

> 先证明纵向真实运行链成立，再增加横向能力。

任何阶段的下游工作不得建立在尚未通过真实验证的上游能力之上。

工具总倾向：

- G1：Codex 主力，Grok Build 不参与正式工作；
- G2–G7：Codex 负责运行核心，Grok Build 负责持续演进的最小 Playtest Shell；
- G8：Grok Build 成为正式前端主力，Codex 负责 Contract、真实集成、安全和最终审核；
- G9：Codex 负责资产 / Runtime 协议与 Adapter，Grok Build 负责动态声明式 UI 的表现层；
- G10–G12：按后端 / 前端职责继续分配。

# G1｜真实模型兼容性

## 目标

在没有正式游戏、数据库和网页的情况下，用真实 DeepSeek 证明：

1. 模型能够稳定使用我们的最小语义协议；
2. 程序能够稳定解析模型输出；
3. 模型语义错误不会突破 Program Judge；
4. 协议适合真实模型，而不是只适合人工 Fixture。

## 内容

建立最小 CLI / Spike：

```text
Scenario
→ Player Input
→ Model-safe Context
→ DeepSeek
→ Semantic Proposal
→ Schema Validation
→ Program Judge
→ Result Report
```

第一版只支持极少语义，例如：

- move；
- item_transfer；
- npc_reaction；
- no_change / clarification。

必须测试：

- 明确行动；
- 否定；
- 条件；
- 愿望；
- 询问；
- “给某人看”；
- “交给某人”；
- 歧义实体；
- 不存在 Ref；
- 隐藏信息；
- 旧项目真实失败形状的脱敏抽象。

## 禁止提前建设

- Next.js；
- SQLite；
- Save；
- Restore；
- Dice；
- Memory；
-复杂 Relationship；
-多 Provider；
-资产协议；
-正式游戏 UI。

## 退出条件

必须取得真实模型实验数据，至少证明：

- 结构化输出高度稳定；
- 明确正常语义达到可接受正确率；
- Program Judge 对未授权世界变化错误接受数 = 0；
- Schema 合法但 Judge 大量拒绝的情况不存在；
- 重复运行具有可接受稳定性。

如果协议不可靠：

停留 G1，修改协议。

不得带着“以后再修”的模型接口进入 G2。

# G2｜最小世界运行内核

## 目标

建立新版第一次真正的游戏 Turn。

最小世界只需要：

- 一个玩家；
- 一个 Scene；
- 一个 NPC；
- 一个 Item；
- 一个简单时间值；
- 少量公开 / 隐藏事实。

最小正式链：

```text
Player Input
→ Capability
→ Model Context
→ Semantic Proposal
→ Program Judge
→ Formal State Change
→ Atomic Commit
→ Narrative
```

## 重要限制

第一版：

- 不需要 Dice；
- 不需要 Save；
- 不需要 Recovery；
- 不需要复杂 Event / Memory；
- 不需要多 Provider；
- 不建设正式产品级网页。

运行核心可以先通过 CLI / API Harness 建立，但 G2 在进入真人验收前必须同步建立一个最小 **Playtest Shell**。

Playtest Shell 的职责不是产品化，而是让项目所有者能够以真实玩家路径完成 Turn。最少包含：

- 对话 / 叙事流；
- 玩家输入框与发送；
- loading / submitting 状态；
- 基础错误提示；
- 当前 Scene / Place；
- 玩家可见人物；
- 玩家可见物品；
- 必要的最小玩家安全状态摘要。

不得为了 G2 Playtest Shell 提前建设：

- 首页；
- 游戏库；
- 正式创建流程；
- 完整人物详情；
- Save Center；
- 设置中心；
- 完整 Design System；
- 复杂动画；
- Runtime UI Contribution；
- 资产安装 UI。

G2 Playtest Shell 应保持代码干净、可演进，但不构成 G8 正式产品 UI 的冻结承诺。

## 最关键退出条件

**真实 DeepSeek 必须连续完成一批真正 committed 的 Turn。**

不是 deterministic Provider。

不是 Fake SDK。

不是人工 Fixture。

必须证明真实模型环境下：

- Turn 能提交；
- 世界状态正确；
- 玩家代理权正确；
- 模型错误只能被拒绝；
- 没有半提交；
- 项目所有者可以通过 Playtest Shell 完成真实玩家 Turn；
- Playtest Shell 只读取玩家安全投影，不接触隐藏状态。

G2 未通过前，不允许开始横向扩展。

# G3｜正式世界能力垂直扩展

## 目标

逐领域增加 World OS 正式能力。

严格一个领域一个领域推进。

推荐顺序从简单能力开始，例如：

1. Position；
2. Item Transfer；
3. Character 状态；
4. Relationship；
5. Item 状态；
6. Event；
7. Time；
8. Memory；
9. Clue / Knowledge。

具体顺序可以根据实际依赖调整。

## 每个领域必须走完整竖切

例如 Position：

```text
真实玩家表达
→ Capability
→ DeepSeek Semantic Proposal
→ Program Judge
→ Position State
→ Atomic Commit
→ Narrative
```

Item Transfer 同理。

## 硬规则

某一领域：

**真实 DeepSeek 竖切没有通过**

则：

**不开发下一个领域。**

从 G2 开始维护同一个可持续演进的 Playtest Shell。G3 每增加一种玩家可感知能力，都必须同步增加最小人工可观察 / 可操作路径，例如：

- Position：玩家能看到当前位置真实变化；
- Item Transfer：玩家能看到持有物真实变化；
- Character 状态：玩家只能看到被正式允许公开的状态；
- Relationship：如果该关系对玩家可见，测试壳必须能展示其玩家安全投影；
- Time：玩家能看到需要公开的时间推进。

前端只消费正式玩家安全 DTO，不得为了展示方便直接读取 Game State 内部结构。

禁止再一次性设计并实现九类巨大状态树。

# G4｜程序判定与 Dice

## 目标

在无骰 Turn 已经稳定以后加入正式判定。

正式链：

```text
Semantic Proposal
→ Program Judge
→ Resolution Plan
→ Program RNG / Dice
→ Program Outcome
→ Final Adjudication
→ Formal State
→ Narrative
```

## 冻结原则

- Dice 由程序控制；
- Outcome 由程序决定；
- Dice 后模型不能重新决定正式世界；
-模型只负责叙事；
-结果 vocabulary 只有真实玩法需要时才扩展。

第一版不要追求：

-万能判定 DSL；
-世界包可编程判定引擎；
-十档结果体系。

从最小可靠机制开始。

## Playtest 要求

G4 必须把正式判定结果接入现有 Playtest Shell，以最小但清晰的方式显示玩家应当知道的信息，例如：

- 是否发生判定；
- 公开 Dice 结果（若规则要求公开）；
- Program Outcome；
- 最终叙事。

具体产品视觉可以留到 G8，但真人 UAT 必须能够确认程序到底裁定了什么。

# G6｜Save / Continue / Restore

> 状态：**PASS / CLOSED（2026-08-15）**  
> 正式收口依据：`12_酒馆游戏_G6_SaveContinueRestore收口裁定_v1.0_2026-08-15.md`

## 目标

在正常运行链稳定后建立完整权威状态的 Save / Continue / Restore / Branch 语义。

## 已完成并冻结的关键能力

- Save 只保存 stable committed state；
- canonical snapshot 是不可变恢复材料，不是第二套实时事实源；
- Snapshot 完整覆盖隐藏状态、Knowledge、Commitment、Pending World Action、Event / Formal history、Dice / Resolution 与 G5 continuity structures；
- Provider raw、reasoning、Prompt、context cache、stale Confirmation、read-only ephemeral response 不进入 Save authority；
- Continue 从当前 committed authoritative state 重新构建 player-safe projection 与 bounded context；
- Restore 原子、fail closed、Provider calls = 0；
- Restore 本身不形成 Formal Turn、不推进 worldTime、不创建普通 Event；
- Restore 可以恢复旧领域世界，但执行 revision 保持单调；
- `revision` 不是 Timeline identity；
- Branch 只在 canonical divergence 后的第一次成功新 Formal Turn 创建；
- 第一次 divergent Restore 冻结 immutable original future；
- 连续 Restore 只是 timeline navigation，不覆盖 origin；
- 回到 original future 会取消 pending，不产生 Branch；
- read-only / failed execution 不消费 pending；
- Timeline metadata 与世界恢复处于同一原子事务；
- raw Snapshot / private state 不发送浏览器。

## 最终 Gate

最终 review-03：`g6:test` 15 tests PASS；`g6:check` 438 tests PASS；68 corpus valid；lint / typecheck / build / disclosure / launcher PASS；DeepSeek `deepseek-v4-pro` Smoke PASS；Restore Provider calls = 0；exact restore / Commitment restore / Branch navigation PASS；项目所有者真人 UAT PASS。

## 阶段止损

G6 关闭后，不因 Archive GC、完整 Timeline Manager/UI、正式 Save Center、Undo/Re-input、Crash/Response-loss Recovery 重开。只有正式状态恢复错误、Branch 误判、Atomic Restore 破坏、隐藏状态泄露、Snapshot 成为第二事实源或恢复绕过权限等硬问题才允许重开。

## G8 正式体验收口：自然输入、撤回与多动作

1. **减少过度 Confirmation**：普通低风险自然输入不应频繁显示“我理解为……”。Program 继续拥有 Capability、Judge、Formal Outcome 与 Atomic Commit 权限。
2. **玩家可见撤回 / 重新输入**：当模型理解与玩家意图不符时，优先提供低摩擦纠错体验。撤回必须建立在 G6 Save / Restore 与 G7 Recovery / idempotency 上，不允许静默改写世界历史。
3. **受控多动作自然输入**：支持“返回酒馆，并睡到第二天”这类顺序明确的高频表达。不得 partial commit，一个玩家输入最终仍最多形成一个 Formal Turn。

## G8 当前正式 Runtime-extensible UI 架构

新版网页采用：

```text
Core Product Surfaces
+
Runtime UI Contributions
+
Game-owned Safe Host
```

### Core 永久一级 World Surfaces

以下五个 Surface 永久具现：

```text
人物
地图
物品
信息
目标
```

它们是玩家认知聚合，不是后台表的一一映射。

- Relationship / Commitment 可以投影到人物或目标；
- Knowledge / Clue / player-visible Event 可以聚合到信息；
- Task / Objective 投影到目标；
- 后台领域对象继续保持独立 authoritative owner。

### 合法 Contribution 落点

Host 至少支持：

1. Player Status Surface；
2. Player Character Detail Surface；
3. Entity Detail Surface；
4. Core Surface Contribution；
5. Map Overlay；
6. Narrative Contextual Surface；
7. Global Notice / Alert；
8. Game Creation / Settings Contribution；
9. Extension Surface。

### Surface Ownership 与 Contribution

必须区分：

```text
owns surface.X
```

与：

```text
contributes to surface.X
```

Surface Owner 创建独立一级 Extension Surface；依赖它的 Runtime Definition 可以向该 Surface 贡献内容。

### Unique Owner Conflict

若两个独立 Runtime Definition 同时声明：

```text
owns surface.X
```

则组合：

> **INCOMPATIBLE**

应在 Game Instance 创建前阻止，不拖到运行时抢占、覆盖或隐式合并。

“唯一 Owner 型能力的冲突优先在组装前判定不兼容”作为后续资产生态的重要设计思路保留。

### 创作者显式一级 Surface

未来创作者明确声明本拓展包需要独立一级 Surface 时，Creator / asset authoring layer 应把该意图编译为结构化 Extension Surface Ownership Request。声明合法后，Host 必须提供一级目的地；正式 Runtime 不应每次启动再通过 NLP 猜说明文字。

### 玩家排序权

玩家拥有 Core + Extension 一级 Surface 的最终排序权。

```text
Asset / Runtime Definition recommends
→ Host initializes
→ Player reorders
→ Player preference wins
```

Surface Order 是 UI Preference，不是 Game State：

- 不形成 Formal Turn；
- 不推进 worldTime；
- 不生成世界 Event；
- 不属于 canonical Snapshot world authority；
- Restore 不回滚玩家当前栏目排序。

### Extension Surface 内部结构

复杂 Extension Surface 可以声明受控：

- secondary View；
- Section；
- List / Card / Meter / Fact / Action；
- Host-owned sub-navigation。

允许资产描述信息架构，不允许资产执行前端。

禁止 arbitrary JS、React injection、DOM access、eval、CSS injection、direct Game State mutation 与 pixel-layout ownership。

# 3. 全阶段共同硬约束

## 3.1 真实模型优先

任何新的模型语义能力：

自动化通过后，

必须尽早通过真实 DeepSeek 垂直验证。

不得拖到最终真人 UAT 才第一次接触真实输出。

---

## 3.2 Model Output 永远不是 Formal World State

模型只负责：

-理解；
-语义建议；
-NPC /世界推演；
-叙事。

程序负责：

-身份；
-授权；
-规则；
-版本；
-时间；
-RNG；
-Dice；
-状态；
-因果；
-最终提交。

---

## 3.3 不兼容早期实现时优先删除，不优先兼容

新版未发布阶段：

错误设计应：

**删除 / 重写**

而不是形成：

v1  
→ v2  
→ v3  
→ legacy adapter  
→ compatibility adapter

只有真正存在发布用户数据以后才建立严格迁移兼容政策。

---

## 3.4 垂直验证优先于横向建设

不得再次发生：

- UI 已完成但 Turn 不工作；
- Save 已完成但模型接口没跑通；
- Recovery 已完成但第一条真实 Turn 没提交；
-多个 Provider 已支持但主要 Provider 没稳定。

---

## 3.5 测试必须包含真实模型失败语料

旧项目积累的真实失败应转化成脱敏 regression corpus。

测试层级必须区分：

- Schema；
-Program Judge；
-deterministic；
-Fake SDK；
-历史真实模型 failure corpus；
-真实 Provider；
-真人产品 UAT。

不得把 deterministic Provider 成功称为真实模型成功。

---

## 3.6 Project Owner 不承担调试循环

正常流程：

```text
Codex / Agent 实现
→ 自动化验证
→ 批量审核
→ 集成节点
→ 项目所有者真人验收
```

不得重新变成：

```text
发现字段问题
→ 让项目所有者点一次
→ 修一个字段

```

## 3.7 Asset-ready / Asset-agnostic

在 G9 之前：

游戏不实现资产协议。

但所有运行模块必须避免把 Demo 世界写死进 Core。

核心接受：

```text
Runtime Definition
→ Game Bootstrap
→ Game State
```

当前手写测试世界只是 Runtime Definition 的一个来源。

未来资产是另一个来源。

`asset-ready` 只表示 Runtime 不把 Demo 或固定 RPG 机制写死，并保留未来可被资产描述的边界；**不表示需要兼容当前现有 tavern-asset-spec。**

页面不得假设固定 RPG 状态和固定功能栏。

资产不拥有前端执行权。
