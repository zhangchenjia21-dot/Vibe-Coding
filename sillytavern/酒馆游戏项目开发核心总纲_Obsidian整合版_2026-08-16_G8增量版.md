> [!abstract] 文档定位

>

> 历史 World OS / H.0A 中权限语境下的旧 `L0–L3` 仅按 `GM0–GM3` 兼容解释。

> G5 已冻结：Character Knowledge、bounded Continuity Context、private/player-safe context 分离、Program Final Outcome、read-only 非 Formal Turn、No Phantom、玩家主动世界变化的程序安全边界。  
> 真实模型的安全 semantic variation 不自动等于 Hard Safety；只有未经授权世界变化、Capability 绕过、Hidden Disclosure、Phantom、partial commit 等才允许重开授权安全边界。  
> 减少过度 Confirmation、“撤回 / 重新输入”和受控多动作自然输入已登记到 G8，不回头阻塞 G6/G7。

> `revision` 不是 Timeline identity；Restore 本身不是 Branch。只有真正从恢复点完成新的成功 Formal Turn 才创建新未来。连续 Restore 不覆盖第一次 origin，返回 original future 会取消 pending。  
> Archive GC、Timeline UI、Save Center、Undo/Re-input 与 Crash Recovery 不回头阻塞 G6。

> [!important] 2026-08-16 G7 阶段收口裁定
> `G7｜Crash / Resume / Recovery` 已 **PASS / CLOSED**，当前正式阶段进入 `G8｜网页产品化`。  
> G7 已冻结：Execution 与 Formal Turn 分离、stage-owned Recovery、Semantic at-most-once、Dice/Resolution no-reroll、Formal Commit exactly-once、committed result replay、immutable logical idempotency identity、recovery key 与 new submission key 分离，以及 G6 Branch 与 Recovery 的原子共存。  
> 项目所有者真人 UAT 命中不可恢复 fail-closed 路径，世界未改变；正向 recoverable 路径由 deterministic Crash Injection + Real DeepSeek Smoke 提供证据。项目所有者明确接受未亲手覆盖该子路径为 UAT coverage debt，不再阻塞 G7。  
> Queue/Worker、分布式 Lease、多设备 Recovery、完整 Error Center、Undo/Re-input 不回头阻塞 G7。

> [!important] 2026-08-16 G8 阶段内 Product UI / Runtime-extensible UI 裁定
> G8 仍 **ACTIVE**；当前任务为 `G8-WEB-04｜Runtime-extensible UI Host Foundation`。  
> G8-WEB-01 已冻结唯一 Player Product UI Contract；G8-WEB-03 已建立 `Main Menu → Product Session → Real DeepSeek Turn`，默认 `启动酒馆游戏.bat` 进入正式 Product UI，Engineering Playtest Shell 降为工程入口。  
> 正式 Core World Surfaces 收口为：`人物 / 地图 / 物品 / 信息 / 目标`，永久具现。Runtime-extensible UI 采用 Surface Ownership / Contribution 分离；duplicate Owner 在创建游戏前判定不兼容；玩家拥有一级 Surface 最终排序权；排序属于 UI Preference 而不是 Game State。  
> 资产可以描述受控信息架构与 Extension Surface，但不得执行任意 JS / React / DOM / eval / CSS 注入。G9 将依据 G8 已验证 Host Capability 重新设计 asset-spec vNext。

## 一、当前权威关系与阅读顺序

本节不是新增项目规则，只整理原文件已经明确表达的覆盖与依赖关系。

1. **World OS Core / FC2**：定义最高运行原则，包括玩家代理权、玩家表达保真、世界一致性、因果、信息边界、存档权威和错误修正。
2. **FC2 补充裁定**：正式确认 Core 在单局中永远不可被开发模式或上帝权限关闭、覆盖或绕过，并明确“开发诊断 / 开发编辑”的边界。
3. **H.0A v0.2**：不重写 Core；负责把时间、空间、物品、知识、计划、回合、叙事纠正和存档进一步软件化。涉及这些具体细节时，应优先采用 H.0A 的目标语义。
4. **2026-08-15 G5 长期连续性与玩家授权收口裁定**：记录新版 Runtime 已通过真实验证的连续性、授权、No Phantom、Context boundedness、测试分类和阶段止损规则；它不得削弱 Core / FC2 / H.0A，但对 G5 后续实现与审核具有当前约束力。
5. **2026-08-15 G6 Save / Continue / Restore 收口裁定**：记录 stable committed Save、canonical snapshot、atomic Restore、Continue、Branch eligibility、immutable original future、timeline navigation 与恢复状态机测试解释；G7 及 G8 的 Recovery/Undo 必须建立在此正常恢复语义之上。

9. **2026-07-28 补充裁定**：对两个曾经重名的 `L0–L3` 建立独立命名空间；代码层级保留 `L3 → L2 → L1 → L0`，上帝权限改用 `GM0–GM3`。
10. **产品 / UI / 网页化协议**：仍作为历史产品与体验基线；其具体右栏栏目、Web 导航或早期静态布局已被 G8 当前 Product UI 裁定更新时，以 G8 最新裁定为准。

## 二、项目定位与产品边界

### 2.1 产品定位

酒馆游戏是一款：

- 本地运行；
- 单人使用；
- 桌面网页优先；
- 以大型聊天框为视觉与交互中心；
- 以 World OS 为世界运行核心；
- 适合长期持续游玩；
- 强调世界一致性、可追溯因果、角色自主性、长期存档和可恢复性；

的轻量 AI 角色扮演网页游戏。

它不是大型商业游戏平台，也不是多人社交产品。

### 2.2 核心体验目标

玩家应能够：

- 创建不同题材世界；
- 创建并长期扮演角色；
- 与拥有独立目标、知识和行动逻辑的 NPC 互动；
- 通过自由输入或建议行动推进游戏；
- 经历成长、关系、冲突、探索与世界事件；
- 查看人物、地图、物品、线索、任务、日志与存档；
- 关闭网页后继续同一世界；
- 在模型出错时不损坏权威世界。

### 2.3 产品优先级

1. World OS 稳定；
2. 长期存档和状态连续；
3. 玩家输入、模型推演和正式世界变化准确衔接；
4. 大聊天框阅读与操作体验；
5. 角色、地图和 UI 可视化；
6. 装饰性功能。

### 2.4 近期明确不做

- 多人联机、匹配、房间、社区；
- 商业付费和创作者市场；
- 3D 场景与实时战斗动画；
- 语音与原生手机 App；
- 复杂云基础设施；
- 一开始实现所有题材和全部模块；
- 在资产协议冻结前建设完整 Creator；
- 近期的多模型切换、多模型分工和复杂模型兼容 UI。

## 三、三项目架构与资产职责

### 3.1 酒馆游戏本体

负责：

- 导入世界包、人物卡、拓展包；
- 调用统一验证器；
- 本地资产库、版本和快照；
- 创建游戏与兼容检查；
- World OS、Turn Engine、判定、动态 UI；
- 游戏实例、存档、多游戏、恢复和迁移；
- 模型与 API 设置；
- 导入导出。

不负责完整世界包编辑器、复杂人物卡编辑器、完整拓展包设计器和大型 AI 创作工坊。

### 3.2 `tavern-asset-spec`

定位：

> 世界包、人物卡、拓展包格式和验证规则的唯一事实源。

负责：

- 版本化 JSON Schema；
- TypeScript 类型；
- 统一验证器；
- 稳定错误码；
- 依赖、推荐、冲突和兼容规则；
- 迁移器；
- 示例资产和测试夹具；
- 发布产物、变更日志和兼容矩阵。

禁止游戏本体和 Creator 各自复制一套 Schema 或验证逻辑。

### 3.3 `tavern-creator`

定位：

> 可选的创作者伴生应用。

负责：

- AI 辅助生成世界包、人物卡和拓展包；
- 可视化和高级结构编辑；
- 预览、兼容配置、统一验证；
- 错误定位、AI 修复建议、人工修改和导出。

不是游戏本体必装组件。

### 3.4 三类资产与游戏实例

**世界包**决定“这是一个什么世界”。  
**人物卡**决定“有哪些可复用角色”。  
**拓展包**决定“这一局启用了哪些额外机制”。  
**游戏实例**保存“这一局真正发生的一切”。

人物卡进入某局后形成实例副本；游戏内变化不得回写原始人物卡。原始资产更新也不得静默覆盖已有游戏实例。

## 四、World OS 六层运行结构

1. **Core**  
   不可覆盖的最高原则。

2. **Default Runtime**  
   默认 d20、判定闸门、行动方向、NPC 分层模拟、谜团预算、节奏与默认叙事规则。

3. **World Generator**  
   开局问询、世界生成、角色创建、初始地点与人物、趋势、规则配置。

4. **World Pack**  
   本局锁定的世界设定与规则，包括玩家可见摘要和后台锁定事实。

5. **Game State**  
   当前世界真正是什么样；包括时间、空间、人物、物品、知识、任务、计划、趋势等权威可变状态。

6. **Turn Context**  
   当前回合真正需要提供给模型的最小相关上下文。

### 4.1 程序与模型的基本分工

> 模型负责理解、推理、叙事和角色扮演；程序负责状态、随机、记录、约束和恢复。

模型不是数据库，也不能直接修改正式世界。模型只能提出候选变化，程序负责验证、随机、事务提交和恢复。

## 五、Core 不可覆盖原则

Core 在单局游戏运行期间永远不可被开发模式或 GM 权限关闭、覆盖或绕过。

至少包括：

- 玩家代理权；
- 玩家表达保真；
- 世界一致性；
- 因果原则；
- NPC 自主性；
- 信息边界；
- 有意义的选择；
- 重大后果来源；
- 存档权威；
- 错误修正规则。

### 5.1 玩家与世界边界

> 玩家决定角色，世界决定结果。

系统不得替玩家决定关键行动、站队、爱恨、价值立场、人生目标、重大情感选择、背叛、原谅或牺牲。

玩家输入表示尝试，不代表自动成功。

### 5.2 玩家表达保真

系统可以自然化表达，但不得加入会改变：

- 行动意义；
- 信息暴露；
- 立场；
- 承诺；
- 策略；
- 风险；
- 因果结果；

的新语义。

### 5.3 重大后果来源

重大、长期或不可逆结果必须来自合法来源，例如玩家明确行动、已确认事实、事前风险、锁定判定、NPC 已建立目标与行动、时间资源或环境变化。

不得因“剧情需要”“更精彩”或骰后临时扩张风险而产生。

## 六、权威世界状态

### 6.1 时间

每局只有一个当前权威世界时钟。

时间分三层：

- **世界真实时间**：内部精确维护；
- **玩家已知时间**：由可靠来源确认并带来源与确认时点；
- **玩家感知时间**：默认用于沉浸叙事和 UI 的大致时段。

普通回合不得无依据倒退时间。

### 6.2 空间

正式空间模型：

> `Region → Place → Scene`

规则：

- Place 属于一个 Region；
- Scene 属于一个 Place；
- 角色保存 Place 与 Scene；
- Region 由 Place 推导；
- 共同在场默认要求同一 Scene；
- 玩家移动必须来自玩家明确授权；
- NPC 可按目标、计划和世界条件自主移动。

### 6.3 物品

所有权与 Placement 分离。

每个有效物品必须拥有一个唯一权威 Placement。

首版 Placement 包括：

- 随角色携带；
- 放在 Scene；
- 放在 Place；
- 放在另一个物品内部。

物品转移必须验证来源、目的地、持有者、位置与可接触性，并原子提交、留下事件记录。

### 6.4 信息

正式采用三层信息模型：

1. 世界真实；
2. 角色知识；
3. 叙事披露。

世界真实变化不会自动更新玩家知识。数据库知道，不等于玩家角色知道。

玩家知识至少记录：

- 当前认知；
- 来源；
- 可信度；
- 最后确认时间；
- 是否可能过时；
- 是否存在矛盾；
- 关联对象。

### 6.5 业务对象职责分离

- **世界事实**：世界真实是什么；
- **线索**：玩家发现了什么证据或异常；
- **知识**：某个角色怎样理解世界；
- **任务**：玩家当前想完成什么；
- **承诺**：谁明确答应了谁什么；
- **事件**：什么事情在什么时候真实发生；
- **长期记忆**：跨对象、压缩后的长期连续性信息。

任务、承诺、位置、计划和世界时钟不得只靠一段“记忆文本”维持。

## 七、正式回合、判定与原子提交

### 7.1 推荐正式回合流程

1. 读取输入与模式；
2. 保留玩家原始输入；
3. 提取玩家明确授权；
4. 编译最小相关上下文；
5. 解析行动与耗时；
6. 通过判定必要性闸门；
7. 必要时由程序生成并锁定正式判定；
8. 模型提出候选世界变化；
9. 程序验证；
10. 在需要时推进相关后台计划和趋势；
11. 原子提交正式世界结果；
12. 生成或确认玩家可见正式叙事；
13. 更新 UI、日志和存档计数。

### 7.2 判定必要性闸门

只有同时满足以下条件才正式判定：

1. 结果真正不确定；
2. 成败产生不同且有意义的世界状态；
3. 角色具备合理尝试可能；
4. 失败存在事前可说明风险。

确定成功的普通行为直接成功；确定不可能的行为直接说明原因。

### 7.3 正式骰点

正式骰点：

- 由程序生成；
- 生成后锁定；
- 模型不能修改；
- 重试模型结算不能重掷；
- 骰后不得修改目标、难度或风险；
- 重掷必须建立新的正式记录并保留关联。

### 7.4 原子提交

正式回合的关键变化必须作为一个事务整体提交。

任何关键部分失败，整个回合不成立，不得留下：

- 半完成世界状态；
- 叙事成功但状态失败；
- 时间前进但物品未转移；
- UI 显示失败但后台偷偷提交。

### 7.5 叙事与状态

> 故事不能创造权威世界；权威世界决定故事能够正式说什么。

状态改变事实必须有对应结构化变化；当前状态陈述必须与权威状态一致；氛围内容可以更自由，但不能偷偷演化成长期事实。


### 7.6 G5 当前玩家授权运行边界

玩家主动 world-changing action 当前采用：

```text
Program deterministic Direct Fast Path
+
Model Candidate → Program-owned controlled fallback
```

Direct Fast Path 只覆盖少量整句、单动作、高置信、无否定 / 愿望 / 问句 / 条件 / 撤回 / 第二个世界变化的常见表达。

Model semantic result 本身不拥有正式世界提交权。无论未来如何改善自然输入体验，正式执行仍必须经过 Program 的 Capability、规则、Formal Outcome 与 Atomic Commit。

### 7.7 Candidate、Authorization 与 Formal Outcome 分离

- Candidate Directory 回答“当前世界允许尝试什么”；
- Authorization 回答“玩家当前输入是否授权现在执行”；
- Formal Outcome 回答“程序最终确认世界发生了什么”。

三者不得合并成模型的一次语义输出。

### 7.8 No Phantom 与安全语义差异

Narrative 中的 Move、Item Transfer、Show Item、Item Interaction、Wait / Time progression 必须有匹配的 Program-owned Formal Outcome。

真实模型对歧义表达产生不同但都安全的解释时，应把 semantic exactness 与 Hard Safety 分开统计。Dialogue / Read-only 等合理差异，只要没有未经授权世界变化、Hidden Disclosure 或 Phantom，不构成单独的 Core 安全失败。

### 7.9 自然输入体验的后续边界

项目所有者已确认：不应为了让模型“绝对不理解错”而无限增加前置 Confirmation、Regex 或规则负担。

因此 G8 将处理：

- 减少普通自然输入的过度 Confirmation；
- 在 G6/G7 的正式恢复语义之上提供玩家可见“撤回 / 重新输入”；
- 支持“返回酒馆，并睡到第二天”这类受控、顺序明确的多动作输入。

这些改进不得把正式提交权交给模型，也不得产生 partial commit。

### 7.10 G6 当前 Save / Restore / Branch 运行边界

G6 已冻结：

```text
Stable committed state
→ Canonical Snapshot
→ Program-owned Atomic Restore
→ Continue from current authoritative state
```

关键不变量：

- Snapshot 是不可变恢复材料，不是第二套实时事实源；
- Restore 不调用模型、不创建 Formal Turn、不推进 worldTime；
- Restore 失败必须 fail closed，世界与 timeline metadata 同事务回滚；
- 领域状态可以回到旧 Save，但 execution revision 保持单调；
- `revision` 不代表 Timeline identity；
- Restore 本身不创建 Branch；
- 第一次 divergent Restore 冻结 original future；
- 连续 Restore 只是 navigation，不覆盖 original future；
- 返回 original future 取消 pending；
- read-only / failed execution 不消费 pending；
- 只有恢复后的第一次成功新 Formal Turn 才创建 exactly one Branch。

这套语义是 G7 Recovery 与 G8 Undo / Re-input 的正式上游基础。


### 7.11 G7 当前 Durable Execution / Recovery 运行边界

G7 已冻结：

```text
Execution Journal
→ resume only missing stage
→ Atomic Commit exactly once
→ committed result replay on response loss
```

关键不变量：

- Execution 可以失败/恢复，但不是正式世界历史；
- Semantic artifact 一旦 durable，不重复调用 Semantic Provider；
- Dice / Resolution 一旦锁定，不重掷、不重判；
- Program Final Outcome 一旦 durable，不重新决定；
- committed Formal Turn 不重复提交，只恢复同一 committed result；
- idempotency key 必须与 expectedRevision + canonical playerInput 共同绑定 logical submission；
- same key / different request 必须在副作用前 conflict；
- accepted 且无 durable Semantic artifact 时 fail closed；
- recovery key 不能自动成为下一条新玩家输入的 key；
- Recovery 与 G6 pending Branch 在同一正式提交边界共存；
- 浏览器只消费 player-safe Recovery Projection。

这套语义是 G8 正式 Recovery/Error UX、Undo/Re-input 与玩家纠错体验的正式上游基础。

```text
旧权限 L1 = GM1
```

### 8.6 代码架构层级

```text
L3 → L2 → L1 → L0
```

永久边界：

## 九、界面信息架构

### 9.1 当前 Product UI 核心原则

> **大聊天区负责经历世界；Player / World Surfaces 负责理解和回顾世界；正式 Product UI 不镜像后台数据库结构。**

中央 Narrative Surface 始终是视觉中心。

正式 UI 只消费 player-safe Product Projection，不直接读取 Game State、SQLite、Snapshot、Durable Execution Journal 或 hidden/private state。

### 9.2 Player Product UI 与 Engineering Playtest Shell 分离

```text
Player Product UI
= 默认玩家入口 / 正式 UAT / 日常游玩

Engineering Playtest Shell
= 工程 regression / 诊断入口
```

根目录默认 Launcher 必须进入 Player Product UI。Playtest Shell 可以继续存在，但不能再次成为默认玩家页面。

### 9.3 Main Menu

首页采用传统单机 Main Menu，而不是 Web App Dashboard 顶部导航。

正式入口至少包含继续游戏、创建新游戏、读取存档、我的资产库、API 设置和右上角 Settings 齿轮。

未完成能力可以显示为明确 unavailable / shell，但不得假成功或用 Mock 冒充真实能力。

### 9.4 Desktop Session

```text
Top Bar
├─ Left Player Surface
├─ Center Narrative Surface
└─ Right World Surface
```

当前不变量：

- 中央 Narrative 是视觉中心；
- Center ↔ Left / Right 的视觉间距一致；
- Top Bar 保持可见；
- Narrative Timeline 是中央主要滚动区域；
- Left / Right 内容过长时各自内部滚动；
- 长聊天不得让整个 document scroll 把左右栏滚出屏幕；
- Composer 属于中央 Narrative Surface；
- 独立资料使用紧凑 Card / Section 表达条目边界，不重新变成 SaaS Dashboard。

### 9.5 Core 永久 World Surfaces

以下五个一级 Surface 永久具现：

```text
人物
地图
物品
信息
目标
```

无数据时也保留入口，只显示轻量 Empty State。

Surface 是玩家心智模型，不是后台表的一一映射。

### 9.6 人物 / 信息 / 目标的聚合语义

**人物**聚合 Character、Relationship、人物相关 Commitment、最近互动、玩家已知人物信息与后续 Person Detail Contribution。

**信息**聚合 Knowledge、Clue、player-known Fact、Rumor、player-visible Event summary、调查信息与来源/可信度/时效等玩家安全内容。“信息”取代工程阶段较窄的“已知 / 记录”。

**目标**聚合 Task / Objective、阶段、状态、最近进展、期限和关联人物/地点/物品/信息。Task 是 World OS Core 的长期目标连续性结构，不是模型根据模糊剧情钩子自动生成的传统 Quest Log。

### 9.7 领域对象独立，Product UI 可以多视图聚合

Relationship、Commitment、Knowledge、Clue、Event、Task 继续拥有独立 authoritative owner。

UI 可以把同一 player-safe 事实引用到多个合适位置，但不得复制第二份业务事实源。

### 9.8 Runtime-extensible UI 合法落点

Host 至少支持：

1. Player Status Surface；
2. Player Character Detail Surface；
3. Entity Detail Surface；
4. Core Surface Contribution；
5. Map Overlay；
6. Narrative Contextual Surface；
7. Global Notice / Alert；
8. Game Creation / Settings Contribution；
9. Extension Surface。

不是所有 Expansion 都应新增一级栏目。优先把机制贡献到最符合玩家认知的位置。

### 9.9 Surface Ownership / Contribution / Compatibility

必须区分：

```text
owns surface.X
```

与：

```text
contributes to surface.X
```

同一个唯一 Extension Surface 只能有一个 Owner。

两个独立 Definition 同时 owns 同一 Surface：

> 创建 Game Instance 前判定 **INCOMPATIBLE**。

不得依赖加载顺序、运行时覆盖或同名自动合并。

### 9.10 创作者显式一级 Surface

未来创作者明确要求本拓展包需要独立一级 Surface 时，Creator / asset authoring layer 应把该意图编译成明确的 Extension Surface Ownership Request，再经过正式 Validator。

Runtime 不应每次启动重新用 LLM 猜 prose。声明合法后，Host 必须提供一级目的地。

### 9.11 玩家一级 Surface 排序

玩家拥有 Core + Extension Surface 最终顺序。资产 / Runtime Definition 只能提供推荐初始顺序。

Surface Order 是 UI Preference：

- 不形成 Formal Turn；
- 不推进 worldTime；
- 不生成 Event；
- 不属于 canonical Snapshot world authority；
- Restore 不回滚玩家 UI 排序。

### 9.12 Extension Surface 内部结构

复杂 Extension Surface 允许受控 secondary View、Section、Host-owned sub-navigation 与 List / Card / Meter / Fact / safe Action。

允许资产描述信息架构，不允许资产执行前端。

禁止 arbitrary JS、React injection、DOM access、eval、CSS injection、direct Game State mutation 和 pixel-layout ownership。

### 9.13 窄屏与交互

窄屏继续 Narrative-first：

- 左右资料通过 Drawer / Sheet / 等价 Host 表现；
- 页面不依赖横向 Web 导航；
- enabled 可交互元素统一 pointer / hover / active / focus-visible；
- disabled 元素不得伪装可点击；
- keyboard focus / Accessibility 属于正式产品能力。

## 十二、Agent 协作与 Git 纪律

### 12.1 角色

**用户**
- 产品负责人和最终裁决者；
- 负责方向、体验取舍、关键架构裁决、试玩与验收；
- 不要求编写代码。

**ChatGPT**
- 总设计、总架构和任务规划；
- 负责产品、World OS、架构、数据边界、UI/UX、任务拆分、验收与审查；
- 面向用户优先使用产品语言。

**Codex**
- 主要开发执行端；
- 负责代码、迁移、测试、重构、本地提交和审查证据。

**Claude Code**
- 仅用于独立工作区的特定任务；
- 必须明确唯一绝对路径、分支和 HEAD。

### 12.2 Git

- 一个项目只有一个正式主仓库；
- 主仓库是合并、审查、验收和发布的唯一事实源；
- 多 Agent 不同时修改同一工作区；
- 非必要不创建 branch / worktree forest；
- 当前不 push；
- 不要求远程仓库；
- 不配置 Git 身份；
- 优先本地提交、本地差异和本地备份；
- 不危险删除、不改写历史、不清理无关脏项。

### 12.3 正式 Codex 任务必须包含

- 任务名称与性质；
- 唯一允许工作区；
- 预期分支与 HEAD；
- 开始前核验；
- 背景、目标、非目标；
- 允许修改范围；
- 禁止事项；
- 实施要求；
- 数据与安全边界；
- 测试与验收；
- `git diff --check`；
- `git status --short`；
- 本地提交主题；
- 禁止 push；
- 最终报告格式；
- 必须上传的审查文件。

### 12.4 任务粒度

采用中等粒度任务包：

- 目标清晰；
- 有内部步骤；
- 有止损条件；
- 可独立验收；
- 可独立回退。

### 12.5 阶段止损与审核分类

当工程 Gate、真实模型测试、独立审核和真人验收已经证明某阶段硬不变量成立，应冻结该阶段的核心架构并继续推进。

后续问题优先分为：

1. **真实安全 / 数据 / 权限失败**：重开上游；
2. **Gate / classification 过严**：修测试与分类；
3. **安全但体验不足**：登记到合适后续阶段；
4. **Provider / Transport**：与世界规则分离处理。

不得再次进入“一个失败句式 → 一个 Regex → 再次 UAT”的长期补丁循环。

对于 Snapshot / Restore / Rollback / Branch 类状态机，还必须避免另一种假绿：只证明“能恢复 / 能分支”，却不证明“同状态不误分支、连续恢复不改写 origin、返回原状态能取消 pending”。这类能力的 Gate 必须包含反向与序列 regression。

对于 Durable Execution / Retry / Response-loss 类状态机，还必须证明：exact duplicate 无副作用重放、same key / different request 冲突失败、已持久化 stage 不重做、committed result 不重复提交、recovery key 不污染下一条新提交。真人 UAT 不要求项目所有者通过精确刷新/断网/kill 时机命中内部竞速窗口；窄窗口由 deterministic fault injection 验证。

## 01｜World OS v1.0 FC2｜现行规则整合版

> [!info]- 原始文件

### World OS v1.0 FC2｜现行规则整合版

**状态：当前规则恢复用整合版**  
**日期：2026-07-12**  
**说明：以原始 FC2 为基础，吸收 2026-07-12 已确认补充裁定；不是原始 FC2 逐字副本。**

---

### 第一部分：World OS Core

#### 一、职责

World OS 的职责不是预写剧情、迎合玩家、帮助玩家必胜或刻意击败玩家。

它要维护一个可信、持续演化、因果可追溯、允许角色自主生活、能自然产生故事并可跨会话恢复的世界。

它负责：

- 维护世界事实、时间和因果；
- 扮演世界角色；
- 公平处理玩家行动；
- 忠实保留玩家表达；
- 推进世界变化；
- 维护人物成长、关系和信息边界；
- 生成并锁定 World Pack；
- 装配玩法模块；
- 生成可靠存档；
- 让玩家长期生活在同一世界中。

#### 二、Core 不可覆盖

Core 是所有世界必须遵守的最高规则。

2026-07-12 已正式确认：

> Core 在单局游戏运行期间永远不可被开发模式或上帝权限关闭、覆盖或绕过。

开发模式和上帝权限可以修改当前世界、人物、关系、历史、资源、World Pack、模块、判定具体实现和当前游戏规则。

但不得关闭：

- 玩家代理权；
- 玩家表达保真；
- 世界一致性；
- 因果原则；
- 信息边界；
- 存档权威；
- 错误修正规则。

若未来采用另一套 Core，应通过 World OS 版本升级、项目级配置或明确的自定义 Core 运行环境实现。

#### 三、世界一致性

已经确认的事实、历史、人物设定、关系、规则和事件结果，不得因剧情方便随意推翻。

新内容与旧事实冲突时：

- 优先保留已确认事实；
- 明确指出冲突；
- 不偷偷改写过去；
- 不用“其实一直如此”强行圆谎。

重大历史、人物身份和世界规则的改变必须经过合法权限和明确确认。

#### 四、因果原则

任何重要结果都必须能够追溯到合理原因，包括：

- 成功和失败；
- 成长和退化；
- 关系变化；
- 态度变化；
- 势力兴衰；
- 战争、灾难和社会变化；
- 获得资源、身份或能力；
- 死亡和长期后果。

不得因为“剧情需要”“玩家喜欢”“应该有高潮”或“这样更精彩”而跳过因果。

不得先决定结果，再临时补造理由。

##### 重大后果来源检查

重大、长期或不可逆后果至少必须来自：

- 玩家明确行动或决定；
- 已确认世界事实；
- 事前说明的风险；
- 按锁定规则完成的合法判定；
- NPC 已建立的目标、知识和自主行动；
- 时间、资源或环境变化的合理结果。

不得来自：

- 模型自行增加的玩家语义；
- 骰后改难度、目标或风险；
- 未建立的规则；
- 为制造高潮突然增加的惩罚；
- 与事前风险无关的天然 1 后果。

来源检查失败时不得执行。已经执行则按因果性运行错误处理。

#### 五、可信模拟

World OS 不追求完整模拟现实，而追求始终可信。

只模拟对以下内容有意义的现实：

- 玩家选择；
- 角色状态；
- 人际关系；
- 世界因果；
- 时间和资源；
- 氛围和沉浸；
- 长期后果。

无意义的日常细节不必逐项描写。

当饥饿、疲劳、距离、天气、疾病或生活条件开始影响行动时，必须进入因果。

#### 六、NPC 自主性

重要 NPC 不是玩家工具。

他们拥有自己的身份、目标、性格、价值观、利益、知识边界、关系、记忆、顾虑和人生轨迹。

他们不会因为玩家是玩家而自动：

- 喜欢；
- 信任；
- 等待；
- 帮助；
- 原谅；
- 降低警惕；
- 放弃利益。

玩家不在场时，重要 NPC 仍会根据目标和处境继续行动。

#### 七、玩家与世界的边界

> 玩家决定角色，世界决定结果。

玩家决定角色主动说什么、做什么、追求什么、相信什么、拒绝什么、坚持什么和放弃什么。

系统不得替玩家决定：

- 关键行动；
- 自愿站队；
- 爱恨和价值立场；
- 人生目标；
- 重大情感选择；
- 是否背叛、原谅或牺牲。

可以描述角色无法完全控制的反应，例如疼痛、手抖、心跳、疲劳、直觉、基于能力的观察和外来精神影响。

玩家提出行动，不代表行动必然成功。

#### 八、玩家表达保真

系统可以自然化玩家台词和动作，但不得加入会改变行动意义、信息暴露、立场、承诺、策略、风险或因果结果的新语义。

未经玩家明确表达，不得擅自补充：

- 身份、姓名、性别、关系或具体位置；
- 角色知道或不知道的关键事实；
- 承认、否认、隐瞒或谎称的具体内容；
- 承诺、威胁、立场或价值判断；
- 行动目标、策略和风险偏好；
- 会暴露秘密或改变他人反应的信息。

玩家表达概括时：

1. 若具体措辞不会影响结果，可采用最中性表达；
2. 若不同措辞会产生不同风险，只保留已明确表达的意图和行为，必要时再确认；
3. 不得为了戏剧性替玩家补出失误、泄密、承诺或挑衅；
4. 重大后果不得建立在系统新增的玩家语义上。

若已经因此产生后果，应暂停并按因果性运行错误处理。

#### 九、信息边界

必须严格区分：

- 世界真实；
- 玩家角色知道或相信的内容；
- 重要 NPC 各自知道或相信的内容；
- 玩家通过 OOC、开发诊断或上帝权限获得的信息；
- 当前叙事允许披露的信息。

默认只向玩家呈现角色能够合理感知、回忆、推断或得知的内容。

不得主动泄露：

- NPC 真实内心；
- 幕后计划；
- 隐藏身份；
- 未发现秘密；
- 玩家不可能知道的远方事件。

OOC、开发诊断和上帝权限信息不会自动成为角色知识。

#### 十、诚实、未知与留白

允许未知、未确认和未定义。

记录不足时：

- 不擅自确定重大事实；
- 可以说明目前无法确认；
- 可以保持留白；
- 可以通过后续调查揭晓。

未定义过去可以合理补全，但：

1. 只能填真正空白；
2. 不能推翻已确认事实；
3. 不能为了眼前便利临时制造过强过去；
4. 重大身世、隐藏血统、秘密婚姻、失散亲人等改变人生意义的内容，必须获得玩家确认或开局随机授权。

> 留白不是修改。

#### 十一、有意义的选择

重要选择必须留下合理影响。

行动、不行动、拖延、沉默、拒绝和回避都可能产生后果。

选项不是全部可能性，也不是唯一正确答案。

世界不保证玩家获胜，但玩家选择不能长期毫无意义。

玩家可以尝试任何世界内合理行动。世界只回应符合现实条件和角色能力的行动。

#### 十二、失败与体验连续性

失败可以带来真实严重后果，例如：

- 资源损失；
- 关系恶化；
- 机会错过；
- 身份受损；
- 被捕、受伤、撤退；
- 重要人物死亡；
- 势力覆灭；
- 历史局势改变。

但普通失误不应无意义终止长期体验。

因果允许时，应保留逃离、求援、谈判、康复、改变目标、承担后果后继续生活和接管其他角色。

失败应尽量成为新的世界状态，而不是简单“游戏结束”。

这不等于放水，也不允许修改真实后果。

#### 十三、开放命运

世界可以有长期趋势、历史惯性、时代矛盾、势力冲突、角色梦想和潜在重大事件。

但不得预设唯一结局。

固定的是正在积累的力量和矛盾，不是最终答案。

#### 十四、六层成长

玩家角色和核心 NPC 使用：

1. 属性；
2. 技能；
3. 经历；
4. 专长；
5. 风格；
6. 信条。

成长必须有来源、有过程、需要时间、有机会成本、能在叙事中被感知，并且不因一次普通行动突然完成。

技能和专长可以退化；经历通常长期保留；风格和信条可以变化，但必须渐进并有重大原因。

普通 NPC 只维护当前剧情需要的部分。

具体属性名、数值、资源、伤势、疲劳和特色规则由 World Pack 或拓展包定义。

#### 十五、死亡与视角继承

玩家角色死亡必须具有：

- 合理危险来源；
- 可察觉风险；
- 符合当前世界规则的致死条件；
- 不存在足以阻止死亡的有效干预。

不得无预兆杀死玩家角色制造戏剧。

确认死亡后，完成直接场景和后果，然后暂停，允许玩家：

1. 接管已建立的重要角色；
2. 在同一世界创建新角色；
3. 结束当前世界并生成终章；
4. 使用合法权限回溯或修改死亡。

接管其他角色时：

- 世界历史不重置；
- 原角色死亡继续成立；
- 新视角只拥有该角色合理知道的信息；
- 物品、资源、关系和目标不自动继承；
- 新角色既有过去、人格、经历和信条不能重写；
- 玩家从接管时起获得角色塑造权。

#### 十六、存档权威

不得假装拥有无限上下文。

正式存档应保存：

- World OS 版本；
- World Pack；
- 启用模块；
- 锁定规则；
- 当前时间和地点；
- 玩家角色六层成长；
- 核心 NPC 重要状态；
- 重要关系；
- 已确认事实；
- 世界趋势；
- 未解决事件；
- 玩家角色掌握的信息；
- 重要资源和长期状态；
- 上帝权限日志；
- 下一场景起点。

最新经过玩家确认的正式存档，是恢复游戏时的权威世界记录。

自动总结、分析文件和开发讨论不是正式存档，除非玩家明确确认。

H.0A 已进一步要求存档恢复完整隐藏状态、世界时钟、精确空间、物品 Placement、任务、承诺、知识、计划、趋势和资产版本。

#### 十七、执行错误修正

##### 轻微叙事错误

例如姓名、方向、物品或时间写错，但尚未影响玩家决策。

处理：

- 明确认错；
- 直接纠正；
- 错误不视为世界历史；
- 不消耗上帝权限。

H.0A 将其实现为每条正式叙事后的“纠正”按钮。

##### 因果性运行错误

例如：

- NPC 知道不该知道的信息；
- 违反锁定规则；
- 替玩家作出关键选择；
- 补充玩家未表达的关键语义并据此推进；
- 错误影响后续多轮；
- 错用模块；
- 正式状态被错误改写。

暂停游戏，允许：

1. 保留现状；
2. 回溯到错误前；
3. 在不破坏 Core 的前提下寻找合法世界内解释。

由系统擅自增加玩家语义产生的后果默认无效。

#### 十八、运行模式

##### 游戏

世界正常运行。

##### OOC／场外交流

用于询问规则、反馈体验、理解判定、讨论角色、回顾玩家已知信息和暂停沉浸。

默认不改变世界，也不进入角色知识。

##### 调试控制

用于调整长度、格式和节奏，补充遗漏选项，提醒遵守既有规则，以及报告疑似执行错误。

默认一次性，不改变世界事实，不进入角色知识，不消耗上帝权限。

##### 开发

保留统一“开发”入口，内部区分：

###### 开发诊断

只读，检查状态链、叙事一致性、系统行为和实现限制。

不创建 Turn，不修改世界，不进入后续游戏上下文。

###### 开发编辑

未来可写，用于当前游戏实例的 World Pack 本地覆盖、模块配置、运行方式、角色创建内容和允许编辑的当前游戏规则。

必须预览、明确确认、验证、记录版本和审计。

不得直接改写资产库原始世界包。

##### 上帝权限

- L0：正常；
- L1：查看风险、隐藏信息、NPC 想法、可能走向和判定依据；
- L2：回溯、重做、重投、修正误执行；
- L3：编辑当前游戏世界。

L1 默认不进入角色知识。

L2、L3 必须明确启用并记录。

---

### 第二部分：Default Runtime

#### 一、默认运行循环

每轮：

1. 判断模式；
2. 读取最新锁定事实、正式状态和存档；
3. 忠实提取玩家明确表达；
4. 判断时间推进；
5. 更新当前行动直接影响的内容；
6. 更新必须演化的相关人物、事件和趋势；
7. 通过判定必要性闸门；
8. 处理结果并检查重大后果来源；
9. 更新角色、关系、知识和世界状态；
10. 只呈现玩家可合理感知、回忆或推断的内容；
11. 在交还控制权时提供合适行动方向；
12. 等待下一步。

不得每回合详细模拟整个世界。

#### 二、分层模拟

##### 前景层

当前 Scene、直接参与者和立即风险，详细运行。

##### 关联层

与当前目标、关系、任务和事件相关的人物、组织和地点，只更新关键变化。

##### 远景层

遥远地区和次要人物，只维持趋势、重大事件和必要状态。

世界在玩家离场期间进行逻辑演化。

#### 三、核心 NPC

活跃核心 NPC 至少维护：

- 当前目标；
- 当前限制或顾虑；
- 下一步最可能行动；
- 与玩家的重要关系；
- 六层成长中当前相关部分。

详细维护的活跃核心 NPC 通常控制在约 4—8 人。

H.0A 进一步细化为：

- 目标；
- 当前意向；
- 正式计划；
- 世界趋势；
- 触发事项；
- 已发生事件。

不是每个意向都创建计划。

#### 四、信息可信和叙述语言

重要信息区分：

1. 已确认事实；
2. 高可信推断；
3. 角色陈述或未证实内容；
4. 幕后未知。

叙述区分：

##### 可观察事实

可以直接陈述。

##### 玩家推断

使用“看起来”“从反应判断”“你无法确认，但可能”“似乎”等表达。

##### NPC 真实内心

只有合法的 OOC、开发诊断或上帝权限可以直接说明。

#### 五、判定必要性闸门

只有同时满足以下条件，才进行正式判定：

1. 结果真正不确定；
2. 成败会产生不同且有意义的世界状态；
3. 角色具备合理尝试可能；
4. 失败存在可以事先说明的风险。

确定成功的普通行为直接成功。

确定不可能的行为直接说明原因。

不得为了增加游戏感而滥掷骰。

#### 六、社交判定闸门

以下内容不自动需要说服判定：

- 提出合理建议；
- 陈述事实；
- 表达私人边界；
- 正常请求；
- 对方依职责本来就应完成的行为。

先依据身份、证据、职责、利益、关系和已建立立场判断。

只有玩家试图改变对方原本不会改变的决定，且角色能力确实会影响结果时，才考虑正式社交判定。

高骰点不能抹掉 NPC 的职责、核心利益、已确认事实和强边界。

#### 七、随机源与默认 d20

Default Runtime 默认可使用 d20。

开局锁定随机源和公开方式。

随机源可以是：

- 程序生成并锁定；
- 玩家自行掷骰；
- 外部工具；
- GPT 生成但不可外部验证；
- 无骰叙事判定；
- World Pack 特色判定。

网页游戏正式实现中，骰点优先由程序生成并锁定。

模型不能事后修改骰点、难度、目标或风险。

世界包或拓展包可以替换具体判定方式，但不能违反 Core。

#### 八、判定公开

##### 紧凑公开

用于普通关键行动，显示判定目标、DC、主要优势和不利、骰点和结果。

##### 完整公开

用于生死、重大政治决定、关键战斗、不可逆选择或玩家主动要求，显示完整风险、依据和结果层级。

#### 九、行动方向

交还玩家控制权时，通常提供 3—6 个不同方向：

- 至少一个保守方向；
- 至少一个主动方向；
- 保留自由行动。

以下情况可省略：

- 玩家要求纯叙述；
- 正在等待明确回答；
- 错误修正暂停；
- OOC、开发、审核流程；
- 当前自然不需要选项。

选项不是全部可能性。

#### 十、谜团预算和节奏

同时活跃的核心未知通常控制在约 2—4 个。

新增未知时，优先：

- 解释旧未知；
- 缩小旧未知；
- 合并旧未知；
- 提供可实际利用的信息；
- 明确新名称属于旧事件。

重大危机后，通常安排低压力阶段，除非已建立威胁仍持续。

避免世界永远依赖新谜团和连续危机推进。

#### 十一、发送前内部检查

正式回复前检查：

- 是否忠实保留玩家表达；
- 是否替玩家补充关键决定；
- 是否泄露隐藏信息；
- 是否违反锁定事实；
- 是否需要判定；
- 判定风险是否事前成立；
- 重大后果是否合法；
- 时间和世界是否合理推进；
- 是否遗漏交还玩家控制权；
- 是否需要存档或错误修正。

---

### 第三部分：World Generator

#### 一、开局方式

只保留：

1. 紧凑问询；
2. 深入设计。

不得擅自增加第三种固定开局模式。

#### 二、紧凑问询

一次收集：

- 世界题材；
- 整体基调；
- 主要玩法；
- 不想体验的内容；
- 角色创建深度；
- 规则复杂度；
- 判定方式；
- 随机源；
- 判定公开格式；
- 希望指定、随机或留白的项目。

玩家可回答“其余随机”。

随后生成：

- 玩家可见 World Pack 摘要；
- 后台锁定记录；
- 推荐模块；
- 角色创建方案；
- 世界趋势；
- 地区矛盾；
- 开局入口。

只展示简短确认摘要。

确认后锁定并开始，避免连续十几轮盘问。

#### 三、深入设计

按阶段：

1. 题材和基调；
2. 时代、地域、社会和世界规则；
3. 力量体系、科技或超自然边界；
4. 势力、趋势和地区矛盾；
5. 玩家角色；
6. 模块、判定、随机源和公开格式；
7. 最终确认和锁定。

每阶段成组提问。

所有项目允许指定、随机或留白并在游戏中发现。

玩家可随时要求“直接完成并开局”。

#### 四、World Pack 双层结构

##### 玩家可见确认摘要

简洁展示：

- 世界概述；
- 基调；
- 核心趋势；
- 地区矛盾；
- 玩家角色；
- 启用模块；
- 判定方式；
- 随机与留白范围。

##### 后台锁定记录

保存运行所需的详细规则和玩家尚不知道的既定事实。

不得预写唯一未来、固定结局或必须发生的剧情。

#### 五、模块

模块可以定义战斗、伤势、魔法或力量、政治、战争、恋爱、生存、经济、身份和其他题材机制。

模块可以替换具体实现，但不得推翻：

- 玩家代理权；
- 玩家表达保真；
- 因果性；
- 一致性；
- 信息边界；
- 判定公平；
- 重大后果来源；
- 存档权威；
- 六层成长；
- 死亡后的继续选择；
- 错误修正。

#### 六、角色创建

可选择轻度、中度、重度或自定义。

每个项目允许玩家指定、系统随机或游戏中发现。

玩家角色默认是重要参与者：

- 不是无敌主角；
- 不是永远接触不到重要事件的路人；
- 有合理身份、能力、关系、责任或潜力接触重要局势；
- 参与资格不等于胜利保证。

不同身份不追求完全数值平衡，而追求合理优势、限制、责任和机会成本。

#### 七、确认与锁定

正式开局前只展示简短确认摘要。

玩家确认后：

- 玩家可见摘要锁定；
- 后台 World Pack 锁定；
- 模块配置锁定；
- 角色设定锁定；
- 未经合法权限和明确确认不得静默改写。

随后进入开场。

## 02｜World OS FC2 补充裁定｜Core 与开发模式

> [!info]- 原始文件

### World OS FC2 补充裁定

**日期：2026-07-12**  
**状态：用户已正式确认**

#### 一、Core 的不可覆盖性

> Core 在单局游戏运行期间永远不可被开发模式或上帝权限关闭、覆盖或绕过。

开发模式和上帝权限可以修改：World Pack、模块、当前世界、历史、人物、关系、资源、判定具体实现和当前游戏规则。

但不得关闭或绕过：

- 玩家代理权；
- 玩家表达保真；
- 世界一致性；
- 因果原则；
- 信息边界；
- 存档权威；
- 错误修正规则。

若未来需要采用不同 Core，应通过 World OS 版本升级、项目级配置或明确的自定义 Core 运行环境实现，而不是在普通单局中临时覆盖。

#### 二、开发模式最终形态

保留一个“开发”入口，内部区分两类能力。

##### 开发诊断

只读，用于检查状态链、叙事一致性、系统行为和实现限制。

- 不创建 Turn；
- 不修改世界；
- 不进入后续游戏上下文；
- 不改变角色知识；
- 可作为临时信息在刷新后消失。

##### 开发编辑

未来可写，用于修改当前游戏实例的 World Pack 本地覆盖、模块配置、运行方式、角色创建内容和允许编辑的当前游戏规则。

必须：

- 先预览；
- 明确确认；
- 完成验证；
- 记录版本；
- 保留审计记录；
- 不静默生效。

开发编辑不得直接改写资产库中的原始世界包，只能创建当前游戏的本地覆盖、派生修订或明确导出的新版本资产。

## 03｜World OS 网页化拆分与运行协议 v0.1

> [!info]- 原始文件
> `03_World_OS网页化拆分与运行协议_v0.1_整理版(2).md`

### World OS 网页化拆分与运行协议 v0.1｜规则整理版

**来源：早期《酒馆游戏体验》中的正式协议草案**  
**状态：当前仍有效；具体时间、空间、物品、知识和存档设计由 H.0A v0.2 进一步细化**

#### 一、目标

把主要供 GPT 阅读的 World OS 指令，转化为网页游戏能够稳定调用、保存、验证、恢复和审计的运行核心。

核心分工：

> 模型负责理解、推理、叙事和角色扮演；程序负责状态、随机、记录、约束和恢复。

#### 二、总原则

##### 模型不是数据库

模型记得某件事，不代表该事实长期可靠。

需要长期有效的信息必须进入正式状态、事件、知识、任务、计划、记忆或存档。

##### 模型不能直接修改正式世界

模型只能提出状态变化。

正式变化必须经过：

1. 格式检查；
2. 来源检查；
3. 锁定规则检查；
4. 玩家代理权检查；
5. 信息边界检查；
6. 确定性验证；
7. 事务写入；
8. 事件记录。

##### 叙事与状态分离

模型结果包含：

- 玩家可见叙事；
- 机器可读状态提案。

叙事可以自然，状态必须结构化、严格、可验证。

##### 世界事实与角色知识分离

程序分别保存：

- 世界真实；
- 玩家角色知识；
- 重要 NPC 各自知识；
- OOC、开发和上帝权限信息。

数据库知道，不等于玩家角色知道。

##### 重大结果可追溯

重要变化应追溯到玩家输入、合法判定、骰子结果、已建立事实、NPC 自主行动、时间推进、正式事件或已确认规则。

#### 三、六层结构

##### 第一层：Core

不可覆盖原则，包括玩家代理权、世界一致性、因果原则、玩家表达保真、NPC 自主性、信息边界、重大后果来源、存档权威和错误修正。

##### 第二层：Default Runtime

默认实现，包括 d20、判定闸门、行动方向、信息可信层级、NPC 分层模拟、谜团预算、节奏规则和默认叙事规范。

##### 第三层：World Generator

负责启动问询、World Pack、角色创建、模块推荐、初始地图和人物，以及最终确认和锁定。

##### 第四层：World Pack

一局游戏的锁定世界规则。

分为：

- 玩家可见摘要；
- 后台锁定记录。

可以包含玩家尚不知道的既定事实，但不得预写唯一未来和固定结局。

##### 第五层：Game State

当前世界真正的可变状态，包括：

- 世界时钟；
- Region、Place、Scene；
- 玩家角色；
- NPC；
- 关系；
- 物品；
- 地图；
- 线索；
- 角色知识；
- 世界趋势；
- 活跃事件；
- 模块状态；
- 承诺；
- 长期状态；
- 计划和触发事项。

##### 第六层：Turn Context

只供当前回合使用的最小上下文，包括：

- 玩家本轮输入；
- 当前 Scene；
- 在场人物；
- 当前地点；
- 相关物品；
- 相关知识和记忆；
- 相关规则；
- 相关模块；
- 最近若干回合；
- 当前判定状态。

Turn Context 动态生成，不是完整存档。

#### 四、核心运行对象

##### Game

一局完整游戏，至少关联 World OS 版本、World Pack、玩家角色、当前世界时钟、当前 Scene、回合编号、状态版本、当前存档和游戏状态。

##### World Pack

保存玩家可见摘要、锁定规则、活跃／休眠／禁用模块、未识别字段、版本和确认时间。

##### Character

保存身份、公开资料、私密事实、六层成长、当前状态、当前 Place/Scene、知识、重要度和生存状态。

##### Relationship

独立保存方向性关系。可以维护后台维度，但玩家只看到有依据的自然语言摘要。

##### Item

保存身份、描述、类别、数量、所有权、唯一 Placement、状态、已知／隐藏属性和来源事件。

##### Region / Place / Scene

H.0A 已取代旧单层 Location。

##### Clue

保存发现的证据和异常，不自动等于世界真相。

##### Knowledge

保存角色当前认知、来源、可信度和时效。

##### Event

保存正式发生的历史。事件不替代当前状态。

##### Memory

保存跨对象、长期、压缩后的连续性信息，不承担位置、物品、任务、计划和时间的权威职责。

##### Save Snapshot

保存完整恢复所需状态、版本和摘要。

#### 五、Turn 输入和输出

##### 输入

至少包含：

- gameId；
- turnId；
- expectedStateVersion；
- inputMode；
- 玩家原始输入；
- 选中的行动；
- 当前相关上下文。

必须保留玩家原始表达。

##### 输出

模型可返回：

- 玩家可见叙事；
- 建议行动；
- 判定请求；
- 状态变化提案；
- 知识变化；
- 关系变化；
- NPC 更新；
- 世界趋势更新；
- 计划或触发事项变化；
- 运行警告。

模型不能直接提交数据库。

#### 六、判定协议

两阶段判定：

1. 模型提出判定请求；
2. 程序验证判定是否必要、目标和风险是否合法；
3. 程序生成并锁定骰点；
4. 将锁定结果交给模型；
5. 模型生成符合结果的叙事和状态提案；
6. 程序再次验证；
7. 原子提交。

骰后不得修改难度、目标、风险和骰点。

手动骰子工具与正式判定必须区分。

#### 七、状态验证

程序至少验证：

- Schema；
- 版本；
- 玩家代理权；
- 玩家表达保真；
- 后果来源；
- World Pack 锁定规则；
- 时间合理性；
- 空间一致性；
- 物品 Placement 唯一；
- 角色知识边界；
- 判定合法；
- 幂等；
- 重复提交；
- 状态版本。

#### 八、事务和原子性

正式回合相关变化必须一起提交：

- 世界状态；
- 时间；
- 事件；
- 知识；
- 任务；
- 承诺；
- 计划；
- 日志；
- 正式叙事；
- 状态版本。

关键部分失败，整个回合不成立。

不能出现状态写一半、叙事成功但正式状态失败、时间前进但物品没转移，或 UI 报失败但后台偷偷提交。

#### 九、上下文编译

每回合只选相关内容。

优先：当前 Scene、在场人物、当前任务、相关物品、相关线索、玩家已知信息、最近回合和当前生效规则。

不反复发送全部数据库、所有远方 NPC、全部隐藏真相和全部历史聊天。

#### 十、存档和恢复

存档必须包含世界状态、隐藏状态、角色知识、世界时钟、空间、物品、NPC 计划、趋势、事件、版本和模型恢复摘要。

恢复从正式状态快照继续，不只是重发全部聊天。

API Key 不进入存档。

#### 十一、浏览器安全

浏览器只接收玩家有权看到的信息。

不得发送：

- NPC 私密事实；
- 隐藏目标；
- 隐藏计划；
- 未发现秘密；
- API Key；
- 原始系统 Prompt；
- 原始模型响应；
- 服务端路径；
- 数据库路径。

#### 十二、与 H.0A 的关系

H.0A 已进一步确定：

- 权威世界时钟；
- 三层时间；
- Region → Place → Scene；
- 物品 Placement；
- 世界真实／角色知识／叙事披露；
- NPC 计划体系；
- 叙事纠正；
- 存档策略和原初时间线；
- 开发诊断／开发编辑。

这些最新细节以 H.0A v0.2 为准。

#### 一、项目定位

一款本地运行、单人使用、以大型聊天框为中心、以 World OS 为世界运行核心、适合长期游玩的轻量 AI 角色扮演网页游戏。

它不是大型商业游戏平台。

网页的价值是让 World OS 比普通聊天框：

- 更稳定；
- 更直观；
- 更容易长期保存；
- 更适合审计和恢复；

- 关闭后继续；
- 查看角色、地图、物品、线索、日志和存档；

```text
↓
系统编译相关上下文
↓
DeepSeek 理解并提出判定或世界变化
↓
程序验证、掷骰、提交
↓
显示正式叙事和可见状态
↓
更新人物、地图、物品、线索、日志和存档

等待下一回合
```

## 05｜酒馆游戏网页端｜界面信息架构 v0.1

### 酒馆游戏网页端：界面信息架构 v0.1｜规则整理版

```text

├──────────────┬───────────────────────────┬─────────────────┤
```

左右栏尽量对称。

显示：

- 世界或游戏名称；
- 当前大致时间；
- 当前 Region › Place › Scene；
- 当前回合；
- 当前主要任务或状态；
- 设置和模式入口。

默认沉浸时间只显示玩家可感知时间。

准确时间需通过世界内钟表等来源获得。

#### 四、左侧玩家栏

显示：

- 玩家立绘；
- 姓名；
- 身份；
- 属性和技能摘要；
- 当前状态；
- 当前资源；
- 判定区；

无正式判定时，判定区显示真实空状态，不伪造“最近判定”。

#### 五、中央聊天区

按正式回合显示：

- 世界叙述；
- NPC 对话；
- 玩家原始行动；
- 判定过程；
- 正式结果；
- 状态变化；
- 建议行动。

每条正式叙事后提供小型：

纠正绑定该条叙事，不占用玩家输入框。

纠正后：

- 轻微文字错误只修正文案；
- 正式状态也错则进入因果性错误修复；
- 不自动推进时间；
- 不计入正式回合。

#### 六、行动区

包含：

- 3—6 个建议方向；
- 自由输入；
- 模式选择；
- 提交；

建议行动只填入草稿或提交明确选项。

地图和物品按钮默认生成行动草稿，不直接修改世界。

#### 七、右侧世界栏

##### 人物与关系

关系合并进入人物详情，不单独占一个永久大栏。

人物卡显示：

- 头像；
- 姓名；
- 身份；
- 玩家已知信息；
- 当前关系摘要；
- 最近互动。

不得显示玩家尚未发现的秘密。

关系默认用自然语言，例如“信任但戒备”“欠你人情”“尊重能力”“明显疏远”“敌对但愿意交易”。

后台可以保存维度，但玩家只看有依据的部分。

##### 地图

采用：

> Region → Place → Scene

世界地图显示 Region，区域地图显示 Place，Place 详情显示 Scene，重要 Place 可有内部 Scene 节点图。

点击“前往”只生成行动意图，不直接移动。

##### 物品

显示名称、类别、当前玩家已知状态、所有权摘要、最后已知位置和可用行动。

隐藏属性不得直接展示。

##### 线索与知识

区分：

- 已确认；
- 高度可信；
- 尚未证实；
- 推测；
- 存在争议；
- 已被否定。

动态信息显示最后确认时间和可能过时。

##### 任务与承诺

任务显示状态、当前目标、最近进展和期限。

承诺显示谁对谁、内容、状态和期限。

##### 日志

显示玩家可见事件。

世界内部隐藏事件不自动进入玩家日志。

##### 存档

显示自动存档、手动存档、游戏内时间、现实保存时间、当前地点和当前任务。

#### 八、统一折叠

大多数信息量较大的资料支持折叠和展开。

折叠后不能只剩标题。

至少显示：

- 名称；
- 当前状态；
- 关键标签；
- 最近变化；
- 当前重点；
- 重要警告。

- 完整描述；
- 历史；
- 来源；
- 关联人物、地点、物品；
- 详细属性；
- 相关任务和事件。

当前 Scene、主要任务和危险状态默认展开。

- 游戏；

#### 十、窄屏

MVP 只保证基本可用：

- 中央聊天全宽；

## 06｜酒馆游戏网页端｜技术方案与项目骨架 v0.1

> [!info]- 原始文件
> `06_酒馆游戏网页端_技术方案与项目骨架_v0.1(2).md`

### 酒馆游戏网页端：技术方案与项目骨架 v0.1

#### 一、文档目的

本文档用于锁定酒馆游戏网页端第一阶段的技术选型、项目结构、数据边界、接口设计、开发顺序和 Codex 工作规范。

项目定位保持不变：

> 一个本地运行、单人使用、以大型聊天框为中心，以 World OS 为世界核心，带有角色立绘、节点地图、玩家状态、物品、人物关系、日志与记忆功能的轻量网页游戏。

技术方案必须服务于以下优先级：

1. World OS 运行稳定；
2. 游戏状态不因模型错误而损坏；
3. 长期存档能够可靠恢复；
4. 玩家输入与世界结果之间保持可追溯因果；
5. 主界面清晰、沉浸且容易长期使用；
6. 开发和维护成本足够低。

### 二、总体技术决策

#### 2.1 应用形态

采用：

> 单仓库、单体全栈、本地运行的网页应用。

前端页面、服务端接口、World OS 引擎、模型调用和 SQLite 数据库都位于同一个项目中。

不采用：

- 前后端分离部署；
- 微服务；
- Docker 编排；
- Redis；
- 消息队列；
- 独立模型服务；
- 多用户认证系统；
- 云端数据库；
- 分布式任务系统。

这些内容对个人自用版本没有足够价值。

#### 2.2 推荐技术栈

##### 基础运行环境

- Node.js 24 LTS；
- npm；
- TypeScript；
- Git。

##### 网页框架

- Next.js；
- App Router；
- React；
- Route Handlers。

##### UI

- Tailwind CSS；
- 少量项目内自定义基础组件；
- 原生 CSS Grid；
- SVG 节点地图；
- 不引入大型游戏 UI 框架。

##### 数据库

- SQLite；
- Drizzle ORM；
- better-sqlite3 驱动；
- Drizzle Kit 管理迁移。

暂不使用仍处于候选稳定阶段的 `node:sqlite`，优先选择成熟驱动。

##### 数据验证

- Zod；
- Zod Schema 作为 TypeScript 数据类型、接口输入验证和模型输出验证的主要来源；
- 必要时由 Zod Schema 转换为 JSON Schema，供模型 Structured Outputs 使用。

##### 模型调用

- OpenAI Responses API；
- OpenAI 官方 Node.js SDK；
- Structured Outputs；
- 服务端调用；
- 模型可替换接口。

##### 测试

- Vitest：单元测试和服务层测试；
- Playwright：浏览器端到端测试；
- 固定模型响应 Fixture：替代自动测试中的真实 API 请求。

---

### 三、为什么采用单体 Next.js

本项目不需要独立后端。

Next.js 同时承担：

- 页面路由；
- React 界面；
- 服务端 Route Handlers；
- SQLite 数据访问；
- 模型调用；
- 文件上传；
- 存档导入导出；
- 本地运行。

这样可以避免：

- 分别启动前端和后端；
- 处理跨域；
- 维护两套类型；
- 建立复杂部署脚本；
- 在多个项目间同步 World OS Schema。

业务逻辑不能全部写在 Route Handler 内。

Route Handler 只负责：

1. 接收请求；
2. 验证输入；
3. 调用服务层；
4. 返回结果。

World OS、游戏状态、骰子和存档逻辑必须放在独立服务模块中，以便测试和重用。

### 十二、模型输出策略

#### 12.1 MVP 采用完整结构化响应

第一版每次模型调用返回完整的结构化 `TurnOutput`。

收到全部响应后：

1. Zod 验证；
2. World OS 验证；
3. 数据库事务提交；
4. 向客户端返回正式结果；
5. 前端逐段或逐字展示叙事。

这样可以防止：

- 玩家先看到一段后来无法提交的叙事；
- 流式 JSON 中途断裂；
- 状态已经展示但验证失败；
- 前端解析半截结构。

#### 12.2 视觉上的流式体验

MVP 使用：

> 已验证文本的渐进呈现。

前端收到完整合法结果后，以较快速度逐段显示。

玩家可以选择：

- 立即显示全文；
- 正常速度；
- 较快速度；
- 关闭逐字效果。

#### 12.3 真正 API 流式输出

真实 token streaming 延后。

只有当以下条件成立时再实现：

- 单次响应等待明显影响体验；
- Structured Outputs 的流式解析已稳定；
- 中断恢复和状态提交逻辑已经设计清楚。

### 十三、回合服务流程

#### 13.1 玩家提交

客户端提交：

```text
gameId
rawText
mode
selectedActionId
expectedStateVersion
idempotencyKey
```

#### 13.2 Turn Service

执行顺序：

1. 检查游戏存在；
2. 检查游戏状态为 active；
3. 检查 `stateVersion`；
4. 检查同一 `idempotencyKey` 是否已经处理；
5. 保存玩家原始输入；
6. 建立 pending Turn；
7. 编译 Turn Context；
8. 调用模型；
9. 验证模型输出。

#### 13.3 不需要判定

若返回 `resolved_turn`：

1. 验证状态变更；
2. 开启数据库事务；
3. 写入状态变化；
4. 写入事件；
5. 写入记忆候选；
6. 更新 Turn；
7. 增加 `stateVersion`；
8. 提交事务；
9. 返回客户端。

#### 13.4 需要判定

若返回 `roll_required`：

1. 验证判定必要性；
2. 保存 Roll Request；
3. Turn 改为 `awaiting_roll`；
4. 返回前端；
5. 左侧骰子区进入等待状态。

玩家点击掷骰后：

1. 服务端生成随机数；
2. 建立并锁定 DiceRecord；
3. 将骰子结果与原上下文交给模型；
4. 模型返回结算结果；
5. 验证状态变更；
6. 原子提交完整回合。

### 十四、程序骰子实现

#### 14.1 随机源

默认使用服务端：

```text
crypto.getRandomValues()
```

或 Node.js `crypto.randomInt()`。

骰点不得由语言模型决定。

#### 14.2 d20

普通：

```text
1 次 d20
```

优势：

```text
2 次 d20，取高
```

劣势：

```text
2 次 d20，取低
```

#### 14.3 结果锁定

生成骰点后立即写入 DiceRecord。

之后：

- 不允许修改；
- 不允许覆盖；
- 页面刷新后仍显示同一结果；
- 重试模型结算不能重新掷骰；
- 孤注一掷建立新记录。

#### 14.4 防止重复点击

掷骰请求带有：

```text
idempotencyKey
```

同一个判定即使点击多次，也只能生成一个正式 DiceRecord。

### 一、文档目的

本稿不重写 World OS，也不重新设计角色成长、判定哲学或玩家与世界的权力边界。

它负责把已经确定的 World OS 原则进一步软件化，回答：

- 世界真实状态由什么组成；
- 时间、空间、人物和物品怎样保持一致；
- NPC 如何在玩家视野外继续行动；
- 玩家知道什么、世界真实是什么、叙事允许说什么；
- DeepSeek 在每回合负责什么，程序负责什么；
- 任务、承诺、线索、知识、事件和记忆怎样避免混乱；
- 叙事错误怎样纠正，因果性错误怎样修复；
- 存档怎样完整恢复世界；
- 哪些内容属于当前版本，哪些延后到正式版。

总原则：

> World OS 规定世界必须怎样可信运行；资产协议规定世界包、人物卡和拓展包怎样表达规则；游戏本体负责保存、验证和执行当前世界。

### 二、不可覆盖的上位基线

以下内容继续以 World OS Core 和 FC2 为准，本稿不得削弱：

1. 世界一致性；
2. 因果原则；
3. 玩家代理权；
4. 玩家表达保真；
5. NPC 自主性；
6. 信息边界；
7. 有意义的选择；
8. 重大后果来源检查；
9. 失败后的体验连续性；
10. 开放命运；
11. 六层成长框架；
12. 死亡后的继续选择；
13. 存档权威；
14. 执行错误修正；
15. OOC、开发、调试和上帝权限的边界。

模型不能成为数据库，叙事不能成为权威状态。

任何长期有效的事实，如果没有进入正式状态、事件、知识、计划、任务或存档，就不能依赖模型“以后还会记得”。

### 三、系统层级与职责

酒馆游戏继续使用六层运行结构：

#### 1. Core

保存不可被世界包和普通运行规则推翻的最高原则。

#### 2. Default Runtime

保存默认运行方法，例如默认 d20、判定必要性闸门、社交判定闸门、行动选项规则、NPC 分层模拟、谜团预算、节奏规则和默认叙事规范。

世界包可以替换具体执行方式，但不能违反 Core。

#### 3. World Generator

负责创建世界、角色、初始地点、初始人物、世界趋势和规则配置。

#### 4. World Pack

保存本局世界的锁定设定与规则，包括题材、时代、社会、法律、经济、力量体系、地理结构、判定方式、状态与资源规则、世界趋势、初始势力与人物、玩家可见摘要和后台锁定事实。

#### 5. Game State

保存当前世界真正是什么样。

本稿新增和细化的时间、空间、物品 Placement、玩家知识、NPC 计划等，都归入 Game State。

#### 6. Turn Context

只向 DeepSeek 提供当前回合真正需要的内容。

不把整个数据库、全部聊天、所有 NPC 和所有远方秘密反复发送给模型。

### 四、权威世界状态

#### 4.1 唯一权威世界时钟

每局游戏必须拥有一个唯一、可计算、可排序的内部世界时钟。

内部时钟负责时间先后、行动耗时、NPC 计划到期、世界事件触发、任务和承诺期限、地点开放状态、天色环境变化和存档恢复。

事件只记录发生时的时间快照，不能反过来决定当前时间。

普通回合不得倒退时间。允许倒退的正式途径只有：

- 读取旧存档；
- 世界内合法时间旅行；
- 已确认的状态修复；
- 上帝权限允许的回溯或编辑。

#### 4.2 世界时间、玩家已知时间、玩家感知时间

时间分为三层：

##### 世界真实时间

系统内部精确维护，例如“第二天 08:17”。

##### 玩家已知时间

玩家最近通过可靠来源确认的时间，例如怀表、墙钟、钟楼报时、手机、时刻牌、日晷、NPC 告知或世界特有计时装置。

准确时间必须记录来源和确认时点。

玩家在 08:10 看过钟，不代表之后永久拥有实时系统时钟。

##### 玩家感知时间

叙事和默认界面显示的大致时段，例如清晨、上午、接近正午、午后、临近黄昏、深夜。

默认采用沉浸时间显示。

未来可提供“始终显示精确时间”的可选设置，但不作为默认。

#### 4.3 行动耗时

DeepSeek 负责提出行动大致耗时，程序负责校验并推进权威时钟。

判断依据包括行动类型、深度、距离、环境、当前状态、世界规则，以及玩家明确指定的等待、休息或旅行时长。

不能先写“过了很久”，再从叙事中猜时间。

一次玩家输入可以包含多个同时发生的动作，耗时不能机械相加。

### 五、空间模型：Region → Place → Scene

正式采用：

> Region → Place → Scene

#### 5.1 Region

较大区域、城区、岛屿、世界分区或行政区，例如雾港、旧城区、北岸。

#### 5.2 Place

稳定目的地、建筑、地标或可在区域地图上显示的节点，例如灰鲸酒馆、港务仓库、旧栈桥。

#### 5.3 Scene

精确互动空间，例如酒馆大厅、吧台前、二楼客房、门外街角、仓库地下通道。

#### 5.4 位置规则

- Place 属于一个 Region；
- Scene 属于一个 Place；
- 角色保存 Place 和 Scene；
- Region 由 Place 推导；
- Scene 与 Place 必须匹配；
- 角色只有在同一 Scene 时，才默认视为共同在场；
- 只有 Place、没有 Scene，表示只知道角色在该地点范围内，不能假定与玩家近距离共处。

玩家移动必须来自玩家明确授权。

NPC 可以依据目标、计划和世界条件自主移动。

#### 5.5 地图显示

采用分层地图：

1. 世界地图显示 Region；
2. Region 地图显示 Place；
3. Place 详情默认显示 Scene 列表；
4. 重要 Place 可以拥有 Scene 节点图；
5. 过于细小或临时的 Scene 只显示为当前位置文字。

Scene 可拥有三种展示级别：

- 隐藏：只供运行时使用；
- 列表：显示在 Place 详情；
- 地图：显示在 Place 内部节点图。

顶部当前位置默认显示：

> Region › Place › Scene

### 六、物品：所有权与 Placement 分离

每个有效物品必须拥有一个唯一权威 Placement。

所有权和当前所在位置不是同一件事。

例如：

> 铜钥匙仍属于玛恩，但暂时由玩家携带。

#### 6.1 Placement 类型

首版支持：

- 随角色携带；
- 放在 Scene；
- 放在 Place；
- 放在另一个物品内部。

角色身上的细节位置使用附加描述，例如右侧口袋、围裙口袋、腰带、背包外侧。

普通口袋不单独建成容器物品。

独立、可移动、具有自身状态的包、箱、盒可以作为容器物品。

固定建筑结构，例如“吧台暗格”，属于 Scene 锚点，不必伪装成普通物品。

#### 6.2 物品生命周期

Placement 与生命周期分开。

生命周期至少区分：

- 有效；
- 已消耗；
- 已损毁；
- 已移除。

“丢失”通常是玩家认知，不等于世界中的物品已经消失。

#### 6.3 转移规则

物品转移必须有明确来源和目的地，验证当前持有者、位置和可接触性，原子提交，并留下事件记录。

同一回合允许多个有顺序的转移。

角色移动时，随角色携带的物品自动移动。

容器移动时，内部物品随容器移动。

首版只处理整件物品或整组堆叠；部分拆分以后再扩展。

### 七、世界真实、角色知识与叙事披露

正式采用三层信息模型：

1. 世界真实；
2. 角色知识；
3. 叙事披露。

同时保留重要 NPC 各自独立的知识边界。

#### 7.1 世界真实

系统内部权威事实。

例如：

> 铜钥匙已经被玛恩转移到后厨暗格。

#### 7.2 玩家知识

玩家角色目前知道、相信、怀疑或误解的内容。

例如：

> 玩家最后一次确认时，铜钥匙在玛恩围裙口袋。

世界真实变化不会自动更新玩家知识。

#### 7.3 NPC 知识

重要 NPC 保存与当前剧情相关的独立知识。

不同 NPC 可以知道不同事实、相信不同解释、撒谎、隐瞒、误解、传播传闻或被误导。

普通 NPC 不需要完整知识库，只保存当前剧情需要的部分。

#### 7.4 叙事披露

叙事只能使用：

- 玩家当前能够直接感知的内容；
- 玩家已经知道或合理记得的内容；
- 当前规则允许披露的内容。

不能因为后台数据库知道真相，就让叙事顺手泄露。

默认视角为玩家有限视角。

### 八、玩家知识模型

重要知识至少记录：

- 当前认知；
- 来源；
- 可信程度；
- 最后确认时间；
- 是否可能过时；
- 是否存在矛盾；
- 关联对象。

#### 8.1 来源

可包括直接观察、亲身经历、NPC 告知、文件或物证、环境线索、玩家推断、传闻、公开信息和特殊能力。

#### 8.2 可信程度

建议采用自然层级：

- 已确认；
- 高度可信；
- 尚未证实；
- 推测；
- 存在争议；
- 已被否定。

“已确认”表示当时有充分依据，不等于永远保持最新。

#### 8.3 时效

稳定知识和时效知识分开。

“灰鲸酒馆位于雾港”通常稳定。

“玛恩现在在吧台后”会迅速过时。

过时不等于错误。

玩家询问某个动态事实时，系统应表达“最后已知”而不是冒充实时真相。

#### 8.4 矛盾信息

矛盾信息不能静默覆盖。

系统应保存各自来源和冲突状态，让矛盾本身成为调查内容。

#### 8.5 错误认知

允许玩家形成错误认知。

系统不能因为知道真相就自动纠正。

只有新的观察、证据、可信陈述、规则能力或正式修正，才能改变认知。

### 九、事实、线索、知识、任务、承诺、事件和记忆

这些对象必须职责分离，避免全部塞进“世界记忆”。

#### 9.1 世界事实

回答：

> 世界真实是什么？

保存稳定或需要长期遵守的真实内容。

#### 9.2 线索

回答：

> 玩家发现了什么证据、迹象或异常？

线索保存发现过程和关联，不负责宣布最终解释。

#### 9.3 知识

回答：

> 某个角色目前怎样理解世界？

知识可以正确、过时、推测或错误。

#### 9.4 任务

回答：

> 玩家当前想完成什么？

任务保存目标、阶段、状态、期限和进展。

任务状态可包括未开始、进行中、受阻、已完成、已失败、已取消。

任务不能因为一句模糊对话而滥建。

通常需要玩家明确接受、NPC 明确委托、世界规则正式触发、现有任务进入新阶段，或玩家明确表示决定去做。

#### 9.5 承诺

回答：

> 谁明确答应了谁什么？

承诺必须来自清晰表达，不能把“也许”“尽量”“可能”自动升级为正式责任。

承诺状态可包括待履行、已履行、已取消、已违背、已过期、无法完成。

#### 9.6 已发生事件

回答：

> 什么事情在什么时候真实发生了？

事件保存历史，不替代当前状态。

后来发现新真相，可以改变解释，但不能改写当时真实发生的行为和陈述。

例如事件应记录：

> 玛恩声称老柯林已经离开雾港。

而不是未经验证地记录：

> 老柯林已经离开雾港。

#### 9.7 长期记忆

长期记忆不再承担所有业务对象的职责。

它主要保存：

- 不适合放入单一实体、但未来必须继续遵守的重要摘要；
- 跨对象关系；
- 长期约束；
- 经过压缩的恢复信息；
- 已确认的叙事连续性要求。

任务、承诺、物品位置、人物位置、计划和世界时钟必须有自己的权威结构，不能只靠记忆文本。

#### 9.8 单一权威与关联

同一事实只保留一份权威内容。

其他模块通过关联使用，不复制自己的事实副本。

界面可以把相关内容聚合成“调查主题”，但后台仍保持职责分离。

### 十、NPC 自主性与后台世界推进

World OS 已确定 NPC 在玩家不在场时仍可行动。

本稿将其软件化。

#### 10.1 六类运行对象

##### 目标

人物长期想实现什么。

##### 当前意向

人物下一步最可能做什么。

柔性、短期、容易因新情况改变。

##### 正式计划

需要跨回合记住的未来行动。

只有在当前回合不能立即完成、未来需要再次检查、会影响世界状态、忘记会造成明显因果错误时，才创建。

##### 世界趋势

较大范围、持续积累的变化。

##### 触发事项

到达某个时间或满足某个条件后，系统必须检查的事项。

触发不等于必然成功。

##### 已发生事件

计划、趋势或触发事项真正产生结果后，进入世界历史。

#### 10.2 连接关系

通常为：

> 目标 → 当前意向 → 正式计划 → 触发检查 → 成功、失败或改变 → 已发生事件 → 更新状态与趋势

不是每个意向都需要计划。

不要求 DeepSeek 每回合给所有 NPC 生成计划。

#### 10.3 后台模拟层级

继续采用 World OS 的三层模拟：

##### 前景层

当前 Scene、直接参与者、立即风险，详细运行。

##### 关联层

与当前目标、关系、任务和事件有关的人物、组织和地点，只更新关键变化。

##### 远景层

遥远地区和次要人物，只维持趋势、重大事件和必要状态。

不模拟整个世界的日常生活。

#### 10.4 后台推进时机

优先在明显时间推进、长距离旅行、长时间调查、等待或睡眠、任务条件变化、重要事件完成、玩家离开区域、阶段转换或触发条件成立时检查。

普通一句短对话不应让整个世界大幅推进。

#### 10.5 隐藏世界变化

玩家不在场时，NPC 可以转移物品、移动、完成行动或失败。

隐藏变化必须有世界内原因，例如 NPC 目标、已建立计划、世界规则、时间触发、任务脚本、势力行动、环境变化或玩家行为的间接后果。

“为了剧情更精彩”不是合法原因。

隐藏变化更新世界真实，但不会自动更新玩家知识或玩家日志。

### 十一、AI 临时创建内容

允许 DeepSeek 丰富世界，但不允许无限扩张世界。

#### 11.1 可自由生成但不必长期保存

- 无名路人；
- 即时环境细节；
- 一次性氛围物件；
- 不改变长期状态的普通描述。

#### 11.2 可临时创建并按需升级

- 临时 Scene；
- 临时 NPC；
- 小型可互动对象。

当临时内容开始拥有名字、反复出现、参与任务、持有重要物品、形成关系或影响长期状态时，系统应将其升级为正式实体。

#### 11.3 严格限制

新 Place、核心人物、重要组织、重要物品和世界规则不能因为叙事方便随意生成。

DeepSeek 可以提出新增，系统根据 World Pack、世界一致性和必要性决定是否接受。

### 十二、游戏输入与回合

#### 12.1 模式先于意图

系统先判断模式：

- 游戏；
- OOC；
- 调试；
- 开发；
- 上帝权限。

然后再识别该模式下的意图。

#### 12.2 游戏模式核心输入

游戏输入框主要处理：

- 行动；
- 对话；
- 观察；
- 内心表达；
- 只读状态查询。

“输入含糊”不是一种意图，而是系统处理规则。

系统默认采用最少改变世界的合理解释。

只有不同解释会产生明显不同后果时，才需要进一步确认。

#### 12.3 叙事纠正不占用输入框

每条正式叙事后提供小型“纠正”按钮。

纠正不是角色行动、玩家台词、OOC、开发诊断或上帝权限操作。

纠正默认不推进剧情、不推进时间、不创建世界事件、不创建世界记忆、不计入正式回合，也不进入后续游戏叙事上下文。

#### 12.4 什么算正式回合

行动、对话、观察和内心表达可以形成正式游戏回合。

只读查询、纠正、OOC、调试、开发诊断、设置操作和失败请求不计入正式游戏回合。

一次玩家输入只形成一个回合。

NPC 的正常回应属于同一回合。

#### 12.5 回合与时间

正式回合不等于必须出现明显时间变化。

- 内心表达通常不推进可见时间；
- 短对话和快速观察消耗少量时间；
- 连续短互动会累积时间；
- 深入调查、旅行、等待和休息按实际情况推进。

### 十三、正式回合运行流程

推荐目标流程：

#### 1. 读取输入与模式

保留玩家原始输入。

不得用改写后的“自然化台词”覆盖原文。

#### 2. 提取玩家明确授权

识别玩家做什么、说什么、观察什么、表达什么内心，哪些只是愿望或条件句，以及哪些关键决定没有获得授权。

#### 3. 编译最小相关上下文

包含精简 Core、当前 Runtime、当前世界时间、当前 Region/Place/Scene、在场人物、当前可见和可互动内容、相关人物/物品/任务/承诺/线索/知识、最近若干回合、相关世界规则和当前判定状态。

默认不加载无关远方秘密和全部历史。

#### 4. 解析行动与时间

DeepSeek 提出本回合发生什么、行动大致耗时、是否需要正式判定，以及哪些相关后台事项需要检查。

#### 5. 判定必要性闸门

只有同时满足以下条件，才正式判定：

1. 结果真正不确定；
2. 成败会产生不同且有意义的世界状态；
3. 角色具备合理尝试可能；
4. 失败存在可说明的风险。

确定成功的普通行为直接成功。

确定不可能的行为直接说明原因。

#### 6. 正式判定

Default Runtime 保留默认 d20。

世界包或拓展包可以替换具体判定方式，但不能违反 Core。

骰点和正式判定结果由程序生成和锁定，模型不能事后修改。

现有 DND 骰子能力保留，但应区分手动骰子工具与正式规则判定。

玩家随手掷骰不能直接修改世界。

#### 7. 生成候选世界结果

模型提出时间、位置、物品、人物状态、关系、任务、承诺、线索、知识、目标、意向、计划、世界趋势和事件等结构化变化。

模型只能提出，不能直接写入正式世界。

#### 8. 验证

程序检查：

- 玩家代理权；
- 玩家表达保真；
- 重大后果来源；
- 世界事实；
- 时间合理性；
- Scene 与 Place 一致；
- 人物不能无依据同时出现在两个地方；
- 物品 Placement 唯一；
- 物品转移合法；
- 判定合法；
- 隐藏信息边界；
- World Pack 锁定规则；
- 幂等与重复提交；
- 数据格式。

#### 9. 后台推进

只有时间或条件真正需要时，才处理相关计划、趋势和触发事项。

不重新详细模拟整个世界。

#### 10. 原子提交

以下内容必须作为同一个正式结果提交：

- 世界状态；
- 世界时钟；
- 世界事件；
- 角色知识；
- 玩家日志；
- 任务与承诺；
- 计划与趋势；
- 叙事记录；
- 状态版本。

任何关键部分失败，整个回合不成立。

失败回合不得留下半完成世界。

#### 11. 生成正式叙事

长期目标采用两阶段流程：

> 先确定合法世界结果，再根据已确认结果生成玩家可见叙事。

叙事可以自由生成氛围，但不能创造权威状态。

过渡阶段如果仍使用一次模型调用返回“叙事 + 状态提案”，叙事也必须被视为未确认结果；状态验证失败时，不能把它作为正式历史。

#### 12. 更新界面与存档计数

成功正式回合才增加回合编号、更新世界状态、更新玩家可见资料，并计入自动存档频率。

### 十四、叙事与状态一致性

叙事内容分三类：

#### 14.1 状态改变事实

例如人物移动、物品转移、时间推进、任务完成、人物受伤、地点封锁。

必须有对应正式状态变化。

#### 14.2 当前状态陈述

例如“玛恩仍在吧台后”。

必须与当前正式状态一致。

#### 14.3 氛围性内容

例如雾、灯光、气味、普通声音和不影响长期因果的环境细节。

可以较自由生成，但不能偷偷演化成长期事实。

原则：

> 故事不能创造权威世界；权威世界决定故事能够正式说什么。

### 十五、叙事纠正与因果性错误修复

#### 15.1 纠正入口

每条正式叙事后提供“纠正”。

可选分类：

- 玩家没有执行这个行动；
- 地点或 Scene 错误；
- 人物不在场；
- 物品状态错误；
- 时间错误；
- 玩家没有说过或想过这些内容；
- 其他。

允许玩家补充简短说明。

#### 15.2 轻微叙事错误

正式状态正确，只是文字写错。

处理：

- 原叙事保留；
- 标记“已纠正”；
- 生成修正版；
- 正式世界不变；
- 不推进时间；
- 不形成新回合；
- 后续上下文使用修正版。

#### 15.3 因果性运行错误

正式状态也已经被错误修改，或错误已经影响后续因果。

普通纠正不能静默改数据库。

系统应暂停相关推进，显示影响范围，并提供 FC2 已规定的处理方向：

1. 保留当前结果；
2. 回溯到错误前的安全节点；
3. 在不违反已确认事实的前提下寻找合法世界内解释。

如果需要直接编辑历史、人物、资源、死亡或世界规则，则进入相应的上帝权限或开发编辑流程。

#### 15.4 已影响多个后续回合

系统应识别错误边界：

- 最早错误回合；
- 受影响状态；
- 受影响事件；
- 受影响知识；
- 后续依赖回合。

默认不逐条手工修补整条历史。

优先从错误前安全快照恢复，再保留旧进度作为内部可追溯历史。

普通玩家不需要管理后台时间线。

### 十六、模式体系

现阶段保留现有模式数量，不急于合并。

#### 16.1 游戏

世界正常运行。

#### 16.2 OOC

玩家层面的场外交流。

未来玩家可见名称建议改为“场外交流”，并保留 OOC 说明。

用于询问规则、回顾已知内容、讨论角色、反馈体验、暂停沉浸和调整体验偏好。

默认不改变世界。

#### 16.3 调试

运行层面的短期控制。

用于报告格式问题、调整长度和节奏、补充遗漏的行动选项、提醒遵守既有规则，以及报告疑似执行错误。

默认一次性执行，不作为持续世界状态。

#### 16.4 开发

当前 Demo 已实现“只读开发诊断”。

未来完整开发能力需要同时区分：

##### 开发诊断

只读。

用于解释状态链、叙事一致性、系统行为和当前实现限制。

不创建 Turn，不修改世界，不进入后续游戏上下文。

##### 开发编辑

未来能力。

用于提出 World Pack 当前游戏实例、模块配置、运行方式和角色创建内容的修订。

修改必须预览、明确确认、验证并记录版本，不得静默生效。

开发编辑不应直接修改安装在资产库中的原始世界包文件。

它应创建当前游戏的本地覆盖或派生修订。

#### 16.5 上帝权限

继续使用 Level 0—3：

- L0：正常；
- L1：查看后台与判定依据；
- L2：回溯、重做、重投、修正误执行；
- L3：编辑当前游戏世界。

L1 信息默认不进入角色知识。

L2、L3 必须明确启用并记录日志。

#### 16.6 模式帮助

每种模式提供小型说明按钮。

说明用途、是否推进剧情、是否改变世界、是否进入角色知识、是否需要确认。

### 十七、存档、读档与原初时间线

#### 17.1 存档内容

存档不是聊天文本备份。

必须包含：

- 完整当前状态；
- 隐藏世界状态；
- 世界时钟；
- Region、Place、Scene；
- 人物和物品；
- 关系；
- 任务与承诺；
- 线索与知识；
- NPC 目标、意向和计划；
- 世界趋势与触发事项；
- 正式事件历史；
- 正式叙事历史；
- 模型恢复摘要；
- World OS 版本；
- World Pack 版本；
- Schema 版本；
- 提示词版本；
- 资产版本。

不保存 API Key 或其他凭据。

#### 17.2 保存时机

只在稳定边界保存：

- 回合已完整提交；
- 状态与叙事已确认；
- 没有未完成判定；
- 没有半完成后台推进。

失败回合不能覆盖正常存档。

#### 17.3 自动存档

玩家可设置：

- 开启或关闭；
- 每 N 个成功正式游戏回合保存一次；
- 最多保留最近 N 个自动存档；
- 是否启用关键节点额外保存。

自动存档只统计成功正式游戏回合。

不统计 OOC、调试、开发诊断、叙事纠正、设置操作、失败回合和未完成回合。

达到上限后，只轮换最旧的自动存档。

自动存档以整局游戏为范围，不按后台时间线分别保留。

玩家可把自动存档转为手动存档。

#### 17.4 手动存档

手动存档默认永久保留，不参与自动轮换，可命名、重命名、导出，并可由玩家主动删除。

删除前必须确认，并显示存档名称、游戏内时间、当前地点、当前任务或最近事件，以及删除影响。

#### 17.5 读档

读档完整恢复整个世界，而不是只改变顶部时间。

恢复内容包括隐藏计划、隐藏物品位置和玩家当时的知识边界。

游戏关闭期间默认暂停，不按现实时间继续运行。

#### 17.6 原初时间线

每局游戏最初创建的后台时间线称为：

> 原初时间线

普通玩家不管理时间线。

界面不提供时间线列表、时间线切换或删除时间线。

玩家只看到继续游戏、自动存档和手动存档。

读取旧存档本身不创建新时间线。

只有玩家从较早存档继续并完成新的正式回合，后台才产生新的时间线。

自动存档继续进入同一全局滚动列表。

玩家若希望长期保留过去节点，应创建手动存档或把自动存档转为手动存档。

未来可加入“沿原初时间线完成游戏”的成就。

正常继续、崩溃恢复和读取最新进度不得误判为离开原初时间线。

### 十八、界面信息架构

#### 18.1 大聊天区保持核心

界面不应演变成复杂管理仪表盘。

大聊天区负责经历世界。

其他面板负责理解和回顾世界。

#### 18.2 大资料统一折叠

大多数信息量较大的资料支持“折叠 / 展开”。

折叠后不能只剩标题。

至少显示名称、当前状态、重要标签、最近变化、当前重点和必须注意的警告。

展开后显示完整描述、历史、来源、关联人物/地点/物品、详细属性和相关任务事件。

优先适用于人物、物品、线索、知识、任务、承诺、世界事实、事件日志、Region/Place/Scene、长篇诊断和复杂规则说明。

当前 Scene、当前主要任务和危险状态默认展开。

历史资料、已完成任务和长篇设定默认折叠。

重要警告不能被折叠隐藏。

界面记住用户最近的展开状态，但这只是 UI 偏好，不属于世界状态。

#### 18.3 判定区

保留左侧判定区域。

无判定时显示真实空状态。

正式判定时显示目标、难度、有利与不利因素、风险、骰面和最终结果。

当世界包采用非骰子规则时，判定区应适配对应规则，或在不需要时收纳。

不要求所有世界永久展示完整 DND 面板。

### 十九、DeepSeek 与模型范围

近期正式游戏只以 DeepSeek 为目标模型。

当前不建设：

- 游戏中途模型切换；
- 多模型历史展示；
- 跨模型风格衔接；
- 多模型分工；
- 复杂提供商兼容界面。

但底层必须保持世界状态、人物资料、任务、物品、计划、知识和存档独立于模型；模型配置与游戏世界分离；同一回合锁定提交时的模型配置。

正式版扩展更多模型 API 时，再单独设计兼容和迁移。

### 二十、迁移与兼容边界

H.0A 只冻结目标语义，不在此直接决定所有数据库迁移细节。

#### 20.1 旧 Location

现有 Location 混合了区域、地点和 Scene 粒度。

迁移目标：

> Region → Place → Scene

H.0B 或专门迁移任务再确定哪些旧记录升级为 Place、哪些拆分为 Scene、旧 ID 怎样兼容、现有地图怎样保持可用。

#### 20.2 旧物品位置

旧 owner、ownerId、locationId 不足以表达完整 Placement。

迁移目标：

- 所有权独立；
- 当前 Placement 唯一；
- 支持随角色、Scene、Place 和容器；
- 保留旧数据兼容读取。

#### 20.3 旧时间

旧事件时间标签不能继续充当当前时间。

迁移目标：

- 建立唯一权威世界时钟；
- 旧事件保留时间快照；
- 无法可靠还原的旧 Demo 数据使用明确迁移策略，不伪造精确历史。

#### 20.4 旧记忆

旧 memories 不直接删除。

逐步分类为世界事实、人物事实、关系、任务、承诺、线索、知识、趋势、恢复摘要，以及仍需人工判断的旧记忆。

### 二十一、系统不变量

以后实现和测试必须保护以下不变量。

#### 时间

- 每局只有一个当前权威世界时钟；
- 时间只能通过正式操作推进；
- 事件不能反向决定当前时间；
- 普通回合不能无依据倒退。

#### 空间

- Scene 必须属于当前 Place；
- Place 必须属于 Region；
- 角色不能无合法原因同时存在于两个 Scene；
- 共同在场默认要求同一 Scene。

#### 物品

- 每个有效物品只有一个权威 Placement；
- 物品不能被两个计划同时成功转移；
- 容器移动会带动内容物；
- 叙事中的转移必须有正式状态变化。

#### 玩家代理权

- 不能替玩家追加关键行动、承诺、立场、爱恨、背叛、原谅或牺牲；
- 玩家输入表示尝试，不自动表示成功；
- 失败后不能替玩家选择新的应对。

#### 信息边界

- 世界真相不能自动进入玩家知识；
- NPC 陈述不能自动成为世界事实；
- 过时不等于错误；
- 矛盾信息不能静默覆盖；
- 叙事不能泄露未获准隐藏信息。

#### 判定

- 不需要判定的行为不得滥掷骰；
- 难度、风险和目标不能骰后修改；
- 骰点锁定后模型不能改变；
- 重大后果必须在事前风险与合法来源范围内。

#### 回合

- 同一玩家提交最多形成一个正式回合；
- 失败、取消和未验证结果不改变世界；
- 同一回合不能重复提交；
- 所有正式变化原子提交。

#### 叙事

- 状态改变必须有结构化变化；
- 当前状态陈述必须与权威状态一致；
- 叙事不能直接成为数据库；
- 被纠正的错误文本不继续污染后续上下文。

#### 存档

- 存档完整恢复隐藏状态；
- 手动存档不被自动轮换；
- 自动存档只按玩家设置清理；
- API 密钥不进入存档；
- 旧存档加载不能污染原来较新的状态。

### 二十三、核心验收场景

#### 场景一：门外街角

玩家正式位于：

> 雾港 › 灰鲸酒馆 › 门外街角

玛恩位于：

> 雾港 › 灰鲸酒馆 › 酒馆大厅 › 吧台前

系统不得默认双方近距离共同在场。

叙事不能写“玛恩就在几步外的柜台后”，除非存在合理视线、声音或玩家重新进入酒馆。

#### 场景二：铜钥匙

玩家把铜钥匙交给玛恩。

正式状态必须记录转移。

后来玛恩在玩家不在场时把钥匙放入后厨暗格。

世界真实更新。

玩家知识仍保持：

> 最后确认由玛恩保管，曾放入围裙口袋。

玩家询问时不能泄露暗格。

#### 场景三：休息到清晨

玩家明确休息到第二天清晨。

系统推进唯一世界时钟。

检查到期计划、任务期限和相关后台事件。

顶部按沉浸模式显示“第二天 · 清晨”。

事件复制当前时间快照。

#### 场景四：查询准确时间

玩家在酒馆看墙钟。

系统给出较准确时间并记录来源。

之后离开酒馆一段时间，界面逐渐回到估计时间，而不是永久显示实时分钟。

#### 场景五：叙事写错

正式状态仍在门外，叙事却写玩家走进酒馆。

点击“纠正”。

系统识别为轻微叙事错误：

- 原文标记已纠正；
- 显示修正版；
- 不改世界；
- 不计回合。

#### 场景六：状态也错了

系统已经错误把玩家位置提交为酒馆大厅，并影响后续人物在场。

点击“纠正”。

系统识别为因果性运行错误，显示影响范围，不静默改数据库。

#### 场景七：正式判定

玩家尝试撬开锁门。

系统通过判定必要性闸门。

程序确定难度、风险和骰子规则。

骰点锁定。

模型只能根据结果叙述，不能事后修改难度或把普通失败扩张成未公开的灾难。

#### 场景八：旧存档继续

玩家读取较早手动存档。

只是查看，不产生新时间线。

玩家提交新的正式行动后，后台创建新的时间线。

界面仍只显示自动存档和手动存档。

### 二十四、重大审阅结论

本轮发现的两项重大问题均已由用户确认，现正式写入 H.0A 基线。

#### 24.1 Core 的不可覆盖性

正式决定：

> Core 在单局游戏运行期间永远不可被开发模式或上帝权限关闭、覆盖或绕过。

开发模式和上帝权限可以修改：

- World Pack；
- 模块；
- 当前世界；
- 历史；
- 人物；
- 关系；
- 资源；
- 判定具体实现；
- 当前游戏规则。

但不得关闭或绕过：

- 玩家代理权；
- 玩家表达保真；
- 世界一致性；
- 因果原则；
- 信息边界；
- 存档权威；
- 错误修正规则。

若未来需要采用不同 Core，应通过：

- World OS 版本升级；
- 项目级配置；
- 明确的自定义 Core 运行环境；

而不是在普通单局游戏中临时覆盖。

#### 24.2 开发模式的最终形态

正式决定：

保留一个“开发”入口，内部区分：

##### 开发诊断

只读。

用于检查：

- 状态链；
- 叙事一致性；
- 系统行为；
- 实现限制。

开发诊断：

- 不创建 Turn；
- 不修改世界；
- 不进入后续游戏上下文；
- 不改变角色知识；
- 刷新后可作为临时信息消失。

##### 开发编辑

未来可写。

用于修改当前游戏实例的：

- World Pack 本地覆盖；
- 模块配置；
- 运行方式；
- 角色创建内容；
- 允许编辑的当前游戏规则。

开发编辑必须：

- 先预览；
- 明确确认；
- 完成验证；
- 记录版本；
- 保留审计记录；
- 不静默生效。

开发编辑不得直接改写资产库中的原始世界包。

它只能创建：

- 当前游戏的本地覆盖；
- 当前游戏的派生修订；
- 明确导出的新版本资产。

#### 24.3 审阅状态

至此：

> H.0A 无未决重大冲突项。

当前方案未推翻 World OS Core、FC2、六层成长、默认 d20、信息边界、存档权威或三项目架构。

可以进入 H.0B 的现有实现审计、数据模型验证和迁移方案设计。

### 二十五、候选结论

H.0A 的核心成果不是新增大量面板，而是建立一套可长期运行的权威世界：

> 系统保存世界真实，角色拥有各自知识，DeepSeek 理解和推演，程序验证和提交，叙事只表达已经合法发生且允许玩家知道的内容。

当前候选架构已经形成完整闭环：

> 世界规则  
> → 权威时间与空间

> → 玩家行动  
> → 判定与后台推进  
> → 候选状态  
> → 验证  
> → 原子提交  
> → 玩家可见叙事  
> → 知识、任务、日志与存档  
> → 下一回合

H.0A 的两项重大审阅问题已经裁定，可以进入 H.0B 的现有实现审计、数据模型验证与迁移方案设计。

默认由 ChatGPT 在当前聊天提供完整可复制任务，用户自行粘贴给 Codex。

- 数据和安全边界；
- 测试和验收；
- `git diff --check`；
- `git status --short`；
- 本地提交主题；
- 禁止 push；
- 最终报告格式；

#### 六、模型推荐

## 10｜补充裁定｜代码层级与上帝权限命名空间 v1.0

> [!info]- 原始文件

### 酒馆游戏补充裁定：代码层级与上帝权限命名空间 v1.0

**状态：正式生效**  
**日期：2026-07-28**  
**裁定者：项目所有者**  
**适用范围：酒馆游戏本体、`tavern-asset-spec`、`tavern-creator`、项目级规则文件、后续代码、文档、UI、持久化协议与迁移任务**

---

#### 一、裁定目的

项目原有两套概念同时使用 `L0–L3`：

1. 项目所有者指定的通用代码架构层级；
2. World OS／H.0A 中的上帝权限等级。

同一标识承担两种无关语义，容易在代码、文档、测试、存档、UI、资产协议和跨仓库交接中产生歧义。

本裁定通过建立独立命名空间解决冲突。

本次调整只改变上帝权限的规范标识，不改变其能力、顺序、安全边界、启用要求、日志要求或 Core 不可覆盖原则。

---

#### 二、项目通用代码架构

项目通用代码架构继续使用：

```text
L3 → L2 → L1 → L0
```

永久规则如下：

1. 业务代码依赖方向遵守 `L3 → L2 → L1 → L0`；
2. 跨模块只能通过对方的 `L3` 公开边界；
3. 不得绕过公开边界直接依赖对方内部层；
4. 业务目录和业务源文件默认使用简体中文清晰命名；
5. 生态、语言和工具链要求的标准文件名继续使用标准名称，例如 `package.json`、`tsconfig.json`、`README.md`、`index.ts`；
6. 公开契约和复杂规则使用简体中文语义注释，重点说明边界、不变量、失败方式和副作用，不逐行翻译代码。

本裁定不额外定义各层的具体技术职责。各仓库如需进一步解释 L0–L3 的职责，必须通过该仓库的正式架构任务或 ADR 决定，但不得改变上述依赖方向和跨模块边界。

自本裁定生效后，项目文档中的裸 `L0–L3` 默认表示代码架构层级；引用历史上帝权限时必须明确标注为“旧权限 L0–L3”。

---

#### 三、上帝权限规范标识

World OS 原上帝权限 `L0–L3` 的规范标识调整为：

| 旧权限标识 | 新规范标识 | 权限语义 |
|---|---|---|
| `L0` | `GM0` | 正常运行 |
| `L1` | `GM1` | 查看后台、风险和判定依据 |
| `L2` | `GM2` | 回溯、重做、重投、修正误执行 |
| `L3` | `GM3` | 编辑当前游戏世界 |

规范顺序为：

```text
GM0 → GM1 → GM2 → GM3
```

`GM0`、`GM1`、`GM2`、`GM3` 是新代码、新文档、新 UI、新测试和新持久化写入所使用的规范权限标识。

内部枚举、类名或常量名不在本裁定中冻结；实现可以使用语义清晰的名称，但对外与持久化标识必须能够无歧义映射到 `GM0–GM3`。

---

#### 四、权限语义保持不变

本裁定不重新设计上帝权限。

以下既有语义继续有效：

1. `GM0` 为正常运行；
2. `GM1` 只读查看后台信息、风险和判定依据；
3. `GM1` 获得的信息默认不进入玩家角色知识；
4. `GM2` 用于回溯、重做、重投和修正误执行；
5. `GM3` 用于编辑当前游戏世界；
6. `GM2`、`GM3` 必须由用户明确启用；
7. `GM2`、`GM3` 的使用必须记录日志和审计信息；
8. `GM3` 不能关闭、覆盖或绕过 Core；
9. 玩家代理权、玩家表达保真、世界一致性、因果原则、信息边界、存档权威和错误修正规则仍不可被任何 GM 等级绕过。

---

#### 五、历史文档与兼容映射

历史 World OS、FC2、H.0A 或其他既有材料中的上帝权限 `L0–L3` 不直接改写。

在权限语境下，历史标识按以下规则解释：

```text
旧权限 L0 = GM0
旧权限 L1 = GM1
旧权限 L2 = GM2
旧权限 L3 = GM3
```

历史文档继续作为可追溯证据；本补充裁定提供当前规范名称和兼容映射。

引用历史内容时，应写成例如：

```text
H.0A 旧权限 L2（现 GM2）
```

不得在新文档中继续裸用 `L0–L3` 表示上帝权限。

---

#### 六、游戏本体迁移原则

线程 A 必须在适当任务边界对游戏本体进行只读事实审计，至少检查：

- 枚举和常量；
- UI 文案；
- Save 和 Snapshot；
- 数据库字段和值；
- 上帝权限日志；
- 测试和 Fixtures；
- Prompt 与模式分发；
- 导入、导出和迁移逻辑。

在审计完成前，不得猜测游戏本体是否已经持久化旧权限值。

如果尚未落地旧值，后续实现直接使用 `GM0–GM3`。

如果已经存在旧值，兼容迁移必须遵守：

```text
读取：兼容旧权限 L0–L3 与新标识 GM0–GM3
内部规范化：统一转换为 GM0–GM3
新写入：只写 GM0–GM3
旧值：保留明确兼容读取或显式迁移，不静默误判或丢失
```

任何数据库或 Save 迁移必须单独规划、测试、审核，并保证失败关闭。

---

#### 七、资产协议与拓展包边界

`tavern-asset-spec` 中：

1. `L0–L3` 只表示代码架构层级；
2. 上帝权限统一写作 `GM0–GM3`；
3. 术语表和权威来源索引必须记录历史映射；

5. 拓展包只能通过受控的 Capability、Action Intent 和 UI Contribution 表达需求；

GM 权限属于玩家或开发者对当前游戏实例的受控运行模式，不是资产包权限系统。

---

#### 八、Creator 边界

`tavern-creator`：

- 不生成要求 `GM1–GM3` 的资产；
- 不把 GM 权限作为拓展包兼容条件；

- 如需展示历史资料，可显示旧权限映射，但不得继续产生旧标识。

---

#### 九、权威优先级

本文件是项目所有者正式补充裁定。

它：

- 保留并正式确认项目通用代码架构 `L3 → L2 → L1 → L0`；

G5 关闭以后，不因普通安全语义差异、偶发多一次确认或生僻表达 clarification 重新打开 G5。

## 二、G5 已冻结的长期连续性成果

以下能力已经通过实现、自动化、真实 DeepSeek 与真人路径验证，作为后续阶段的正式上游基础：

1. **Character Knowledge 是正式权威状态。**
2. **World Truth ≠ NPC Knowledge ≠ Player Knowledge。**
3. Pending Commitment 具有独立正式语义。
4. Pending World Action 具有独立正式语义。
5. Background Progression 只能依据正式状态、目标、计划、规则或触发推进。
6. Continuity Context 保持 bounded：
   - recent Turns `<= 4`；
   - relevant Events `<= 6`；
   - 不发送完整 transcript。
7. 当前 authoritative state 优先于 old history。
8. Semantic private context 与 Narrative player-safe context 分离。
9. Program whitelist 只允许已批准 Disclosure 进入 Narrative。
10. Program Final Outcome 在 Narrative 前确定。
11. Program owns facts；Model writes prose。
12. Natural Narrative 不能退回程序模板回显。
13. No Phantom World Change 是正式不变量。
14. G4 Resolution 链继续保持单一正式结果事实源。
15. `read_only_query`：
    - 不形成 Formal Turn；
    - 不增加 revision；
    - 不推进 worldTime；
    - 不产生 Event；
    - 使用 ephemeral player-safe response。
16. Dialogue / Observation / Inner Expression 可以形成 Formal Turn。
17. Playtest Shell 继续只消费玩家安全投影。
18. Atomic Commit、rollback 与 hidden disclosure boundary 继续保持。

## 三、玩家主动世界变化的当前安全边界

### 3.1 两级授权架构

当前 Runtime 采用两级授权：

#### Tier 1｜Program Deterministic Direct Fast Path

Program 只对少量：

- 整句；
- 单动作；
- 高置信；
- 无否定；
- 无愿望；
- 无问句；
- 无条件；
- 无撤回；
- 无第二个世界变化；

的常见明确表达提供 Direct Fast Path。

Fast Path 是体验优化，不是完整 NLP 引擎。

#### Tier 2｜Model Candidate → Program Confirmation

Program 无法确定证明、但 Model 能理解的合法 world-changing Candidate，当前进入 Program-owned Confirmation。

Confirmation 保持：

- exact candidate-bound；
- revision-bound；
- capability-bound；
- single-use；
- cancel 无副作用。

模型返回 `execute_now` 本身不构成直接执行授权。

### 3.2 Candidate Directory 与 Authorization 分离

Program 从正式世界生成玩家安全、当前可行的 Candidate Directory。

Candidate Directory 回答：

> 当前世界允许尝试什么？

Authorization 回答：

> 玩家当前输入是否授权现在执行？

Program 不能因为自己没有先用 Regex 识别动作，就从模型可选能力中删除该 action family。

### 3.3 正式提交权仍归 Program

即使后续产品体验选择更信任模型的自然语言理解，以下边界仍不可改变：

```text
Model interprets / proposes
→ Program validates Capability / rules / authority
→ Program determines Formal Outcome
→ Atomic Commit
→ Narrative realizes committed result
```

“更信任模型理解玩家语言”不等于“把正式世界提交权交给模型”。

---

## 四、No Phantom 与多动作安全

### 4.1 No Phantom World Change

任何 Narrative 中已经发生的主动世界变化，都必须拥有匹配的 Program-owned Formal Outcome。

至少包括：

- Move；
- Item Transfer；
- Show Item；
- Item Interaction；
- Wait / Time progression。

Program Outcome 与 Narrative 不一致时，必须 fail closed；Narrative 不能替 Program 补造世界变化。

### 4.2 当前多动作输入边界

G5 当前实现优先保护“不偷偷 partial commit”。

例如：

> 返回酒馆，并睡到第二天。

如果 Runtime 当前只可靠识别其中一个 world-changing Candidate，不得静默只执行其中一项并假装整句完成。

现阶段出现单动作 Confirmation 属于**安全但体验不足**，不再视为 G5 blocker。

完整的自然多动作顺序执行作为 G8 产品化体验能力处理，前提是继续保持：

- 一个玩家输入最多形成一个正式 Turn；
- 动作顺序明确；
- Capability 分别成立；
- Formal Outcome 可验证；
- 最终提交原子；
- 失败时不得半提交。

---

## 五、真实模型测试解释规则

### 5.1 Hard Safety 与安全语义差异必须分开

真实模型的 semantic variation 不等于安全失败。

例如玩家输入：

> 我能往酒馆门口走吗？

在当前有可见 NPC 的 Scene 中，至少存在两类合理、安全解释：

1. 系统能力询问 → `read_only_query`；
2. 对当前 NPC 的询问 → Dialogue Formal Turn。

只要没有：

- 执行 Move；
- 执行 Wait；
- 修改 Item；
- 产生未经授权 world-changing outcome；
- 泄露 private Knowledge；
- 产生 Phantom World Change；

就不能仅因 Dialogue / Read-only 分类不同而记为 Hard Safety failure。

### 5.2 G5 继续作为硬 Gate 的内容

- Player Agency violations = 0；
- Phantom World Changes = 0；
- Hard Safety failures = 0；
- Confirmation Candidate 与执行一致；
- stale Confirmation 不可执行；
- Capability-invalid Candidate 不可执行；
- Hidden Knowledge 不泄露；
- Atomic Commit；
- 常见明确动作具有可用 Direct Fast Path；
- Model-only paraphrase 至少可以安全进入受控路径；
- Confirmation cancel 无世界副作用。

### 5.3 不再单独作为 G5 blocker

除非频繁到真实游戏不可玩：

- 某个歧义问句被理解为 Dialogue 而非 Read-only；
- 某个自由表达多一次 Confirmation；
- 某个生僻表达 clarification；
- 偶发安全语义差异；
- 某个不常见 paraphrase 未走 Direct Fast Path。

## 六、授权架构止损规则

G5 关闭后，授权架构默认冻结。

不得因为以下体验差异重新进入“一个失败句式 → 一个 Regex → 再次 UAT”的循环：

- 多一次确认；
- Dialogue / Read-only 安全差异；
- 生僻说法 clarification；
- 某个 paraphrase 没有 Direct Fast Path；
- 模型偶发但可安全纠正的理解偏差。

只有以下情况允许重开玩家授权安全边界：

1. 未经授权 world-changing commit；
2. Confirmation 显示 A 却执行 B；
3. stale Confirmation 被执行；
4. Capability 被绕过；
5. Phantom World Change；
6. Hidden Disclosure；
7. partial commit；
8. 常见明确表达高频无法使用，已达到真实游戏不可玩程度。

## 七、G8 已登记体验债：自然输入、撤回与多动作

项目所有者在 G5 真人体验后明确指出：

> 不应为了让模型“绝对不理解错”而无限增加前置确认、规则和维护成本。对普通自然语言交互，可以更信任模型的理解能力；更好的产品纠错手段应包括玩家可见的撤回和重新输入。

因此以下内容正式登记到 G8，而不回头阻塞 G5、G6、G7：

### 7.1 减少过度 Confirmation

目标体验：

- 正常、低风险、自然表达不频繁弹出“我理解为……”；
- Model interpretation 可以承担更多自然语言理解；
- Program 继续拥有 Capability、Judge、Formal Outcome 和 Commit 权限。

### 7.2 玩家可见“撤回 / 重新输入”

目标体验：

- 玩家发现系统理解错后，可以快速撤回最近一次可安全撤销的操作；
- 回到明确稳定状态；
- 重新输入。

实现顺序必须建立在 G6 的 Save / Restore 正式语义以及 G7 的 Recovery / idempotency 基础之上。

“撤回”不是允许静默改历史，也不能绕过世界一致性和正式恢复语义。

### 7.3 单条输入中的多个连续动作

支持类似：

> 返回酒馆，并睡到第二天。

这类自然、顺序明确的多动作表达。

目标不是建设万能 Multi-action Planner，而是为真实高频玩家表达提供受控的顺序执行语义。

必须继续满足：

- 不偷偷挑一部分执行；
- 不把多个世界变化拆成无法回滚的半状态；
- 一个玩家输入最多形成一个 Formal Turn；
- Program 最终拥有完整 Formal Outcome；
- Atomic Commit。

## 二、G6 已冻结的权威状态语义

### 2.1 Save 只发生在稳定 committed boundary

Save 只能捕获已经完成 Atomic Commit 的正式世界。

不得把以下执行中间态保存为可恢复世界：

- failed / cancelled Execution；
- awaiting Confirmation；
- incomplete Resolution；
- 未提交 Narrative；
- read-only ephemeral response；
- Provider transient state；
- UI draft / loading state。

Save 的语义是：

> **保存一个已经成立的权威世界，而不是保存一次正在运行的请求。**

### 2.2 Canonical Snapshot 是恢复材料，不是第二实时事实源

G6 使用 canonical snapshot 保存恢复所需完整状态，但当前运行世界继续由正式 normalized Runtime State / 持久化结构拥有。

Snapshot：

- immutable；
- versioned；
- integrity checked；
- 用于 Save / Restore / Branch comparison；
- 不参与普通 Turn 的实时写入权威。

因此不得形成：

```text
Live Runtime State
+
Live Snapshot State
```

两个并行事实源。

### 2.3 Snapshot 必须覆盖完整恢复语义

G6 已验证恢复至少覆盖：

- worldTime；
- Region / Place / Scene / Position；
- Item Placement / state；
- Character State；
- Character Knowledge；
- Relationship；
- Commitment；
- Pending World Action；
- Background Progression state；
- Event / Formal history；
- G4 Dice / Resolution history；
- G5 continuity structures；
- 当前正式叙事与恢复所需历史边界；
- state/schema/world/runtime version metadata。

不得通过“把聊天重新发给模型”重建这些事实。

### 2.4 Snapshot 明确不保存临时或危险内容

不进入 canonical Save authority：

- API Key / Authorization；
- raw Provider response；
- reasoning；
- 完整系统 Prompt；
- bounded context cache；
- stale Confirmation execution authority；
- read-only ephemeral response；
- 浏览器临时 UI 状态。

旧 Confirmation 在 Restore 后不得重新获得执行权。

---

## 三、Continue 正式语义

Continue 从当前最新稳定 committed world 继续。

Continue 不等于：

- 重新发送整段 transcript；
- 恢复 Provider 内存；
- 恢复浏览器缓存；
- 从某个旧 Save 猜测当前状态。

正式流程是：

```text
读取当前 committed authoritative state
→ 重建玩家安全投影
→ 重新编译 bounded continuity context
→ 等待下一次玩家输入
```

G5 的 bounded Context 仍保持：

- recent Turns `<= 4`；
- relevant Events `<= 6`；
- current authoritative state 优先于 old history。

---

## 四、Restore 正式语义

### 4.1 Restore 是 Program-owned、无模型的权威状态恢复

Restore 本身：

- 不调用模型；
- 不形成 Formal Turn；
- 不推进 worldTime；
- 不创建普通世界 Event；
- 不创建新的游戏事实；
- 不让 Narrative 决定恢复结果。

真实 DeepSeek Smoke 已验证：

> `Restore Provider calls = 0`。

### 4.2 Restore 必须原子

Restore 的 canonical validation、world state replacement、formal history replacement、timeline metadata 与 pending branch metadata 必须处于同一原子事务边界。

任何 Snapshot 损坏、版本错误、引用错误、integrity failure 或注入故障都必须：

> **fail closed，当前世界保持原样。**

不得出现：

- 世界回去了但 pending metadata 没回去；
- Branch metadata 改了但世界没改；
- 只恢复公开状态，没有恢复隐藏知识；
- 部分表成功、部分表失败。

### 4.3 Domain state 与 operation revision 分离

G6 采用单调 revision / state version 继续保护 stale request、old Confirmation、并发覆盖与 execution identity。

因此 Restore 后：

- **领域世界可以回到旧 Save；**
- **执行 revision 不必倒退。**

关键裁定：

> `revision` 是执行与并发控制元数据，不是 Timeline identity，也不是“世界是否发生分歧”的事实源。

---

## 五、Branch 正式语义

### 5.1 Restore 本身不创建 Branch

正式 Branch 不是“调用过 Restore”，而是：

> **玩家离开原本的正式未来，并从旧状态完成第一次新的成功 Formal Turn。**

```text
Restore older state
→ pending divergence only
→ Branch count = 0

successful new Formal Turn
→ exactly one Branch
```

### 5.2 Canonical divergence 才能建立 pending branch

当不存在 pending origin 时：

```text
current canonical state/history == target save
→ Restore allowed
→ pendingBranch = false

current canonical state/history != target save
→ archive current original future
→ pendingBranch = true
```

Canonical equality 可以忽略纯执行层顶层 `sourceRevision`，但不能忽略会改变真实世界或正式历史的内容。

### 5.3 第一次离开正式未来时冻结 immutable Branch Origin

第一次 divergent Restore：

```text
Original Future
→ immutable pending Branch Origin
```

在第一次新的成功 Formal Turn 之前，后续 Restore 只是 timeline navigation。

不得每 Restore 一次就创建新 origin，也不得用当前回退节点覆盖 original future。

### 5.4 返回 original future 会取消 pending

```text
T1
→ Restore T0
→ pending = true
→ Restore T1
→ pending = false
→ next successful Turn = normal continuation
→ NO Branch
```

这保证“读旧档看看，再回到原进度”不会污染时间线。

### 5.5 连续回溯保持第一次 Origin

```text
T3
→ Restore T1
→ Restore T0
```

只保留第一次离开时的 T3 original future 作为 pending origin；后续成功新 Turn 的 Branch 继续引用 T3，而不是 T1。

### 5.6 只有成功 Formal Turn 消费 pending

read-only query、failed/cancelled execution、model/narrative/validation failure 与 Restore navigation 本身都不能消费 pending。

只有：

```text
pending exists
+
successful Atomic Commit of new Formal Turn
```

才创建 exactly one Branch 并消费 pending。

## 八、G6 阶段复盘

### 8.1 原目标

```text
Save
→ mutate through normal committed Turns
→ Restore complete authoritative state
→ Continue
→ new successful Turn after true rewind creates Branch
```

### 8.2 做对了什么

1. 没有复制旧版 Turn/Timeline 实现，只复用了已经想清楚的产品语义。
2. Snapshot 保持为恢复材料，没有变成第二实时事实源。
3. Restore 从一开始就保持 Program-owned、无模型、原子事务。
4. G4 Dice / G5 Knowledge / Commitment / Continuity 没有在恢复中降级。
5. 玩家只在工程 Gate 和独立审核完成后做一次有价值 UAT，没有承担 branch 语义调试循环。

### 8.3 最大返工

最大返工不在“如何保存数据库”，而在 **Branch eligibility / Timeline identity**。

review-01 发现“恢复同一当前状态仍会 Branch”；review-02 进一步发现“连续 Restore 会覆盖 Branch Origin，回到原未来仍 pending”。最终才收口为：

```text
Canonical divergence
→ immutable original future
→ navigation
→ first new committed result creates Branch
```

### 8.4 被推翻的假设

**被推翻：** 比较 current snapshot 与 target snapshot 就足以决定所有 Branch 行为。

**新结论：** 一旦进入 pending rewind，比较基准必须变为第一次离开时冻结的 original future；当前回退节点不再是 Branch identity 的基准。

### 8.5 测试经验

只测试“旧档 → 新 Turn → Branch”不足以证明 Branch 正确。恢复/回滚状态机必须同时覆盖：

- positive case；
- negative case；
- repeated navigation；
- return-to-origin；
- read-only / failed operation；
- transaction fault injection。

> **状态机的不变量必须通过序列测试证明，而不是只靠单步 happy path。**

### 8.6 用户负担

Branch 的两轮语义问题由独立 Review + deterministic regression 发现；真人 UAT 只在 review-03 无 blocker 后进行。用户不需要查看数据库、日志或重复跑技术 case。

### 8.7 阶段止损

review-03 以后不再继续扩张 Archive GC、Timeline Manager、Save Center、Undo 或 Crash Recovery；它们要么不是 blocker，要么属于 G7/G8。

---

## 九、对 G7 的正式边界

G7 可以建立在 G6 以下稳定能力之上：stable committed state、canonical snapshot、atomic restore、monotonic execution revision、immutable branch origin、player-safe restore projection。

G7 负责 idempotency、durable execution、semantic at-most-once、Dice locking in recovery、crash/resume、response-loss recovery 与 narrative recovery。

**G7 不重新设计 Save / Restore / Branch 的正常语义。**

---

## 十、对 G8“撤回 / 重新输入”的影响

G6 现在为 G8 Undo / Re-input 提供完整 authoritative restore、Branch/original future 语义与原子恢复基础；但仍需 G7 的 idempotency、recovery ownership 与 crash/response-loss 边界后才能产品化。

---

## 十一、Lifecycle / Harness 可泛化经验

1. **Snapshot 是不可变恢复材料，不应成为第二套 live truth。**
2. **执行 revision / version 与业务状态等价性必须分离。** 版本号变化不自动代表业务世界产生分歧。
3. **Restore / rollback 是导航；Branch / fork 需要真实的新提交。**
4. **第一次离开原状态时的 origin 必须稳定。** 新提交前的重复导航不应不断重写 origin。
5. **恢复状态机必须测试反向路径和操作序列。** 同状态恢复、连续恢复、返回 origin、失败/只读、故障注入与 happy path 同等重要。
6. **Timeline / recovery metadata 与业务状态应在同一原子边界。**

这些经验进入跨项目 Lifecycle Harness；酒馆游戏专属的 Formal Turn、World Time、Character Knowledge 名称不写入通用 Skill。

---

## 十二、生效结论

自 2026-08-15 起：

```text
G6 = PASS / CLOSED
G7 = ACTIVE
```

> **Save 保存已经成立的世界；Restore 原子恢复完整权威世界；Continue 从当前 committed truth 继续；Branch 只在真正从恢复点提交新未来时成立。**
>
> **恢复操作、执行 revision 与业务分歧是三个不同概念，不得混为一个状态。**

## 二、Execution 与 Formal Turn 的正式边界

### 2.1 Durable Execution 只是运行过程

G7 允许建立最小 Durable Execution Journal，用来保存 execution identity、idempotency identity、已稳定完成的阶段、恢复继续所需的最小结构化 artifact、committed / terminal failure 状态，以及 player-safe recovery status。

Durable Execution **不是世界历史**，也不是第二套 Game State。

### 2.2 Formal Turn 仍只在 Atomic Commit 后成立

以下状态不构成 Formal Turn：

- accepted；
- semantic_ready；
- resolution_ready；
- formal_outcome_ready；
- narrative_ready；
- terminal_failed。

只有正式世界、Event、Dice/Resolution ownership、G6 pending Branch 与 committed execution checkpoint 在同一原子提交成功以后，才存在新的 Formal Turn。

新版继续禁止把 `pending / processing / failed Formal Turn` 作为长期核心模型。

## 三、阶段所有权与“只补缺失阶段”

Recovery 只能继续**尚未完成的执行阶段**。

如果已有 durable evidence 证明某阶段完成：

- Semantic Proposal 已持久化 → 不重新调用 Semantic Provider；
- Dice / Resolution 已锁定 → 不重掷、不重新 Judge；
- Program Final Outcome 已持久化 → 不重新决定 Outcome；
- Narrative 已持久化 → 不重新生成；
- Formal Turn 已 committed → 不再次提交，只恢复同一个 committed result。

> **Recovery 不是“从头再跑一次”，而是由 Program 根据 durable stage ownership 补齐缺失阶段。**

## 四、Semantic at-most-once 与 Dice no-reroll

同一 Durable Execution 如果已经拥有合法 Semantic artifact，Crash / refresh / retry 后直接复用，不重新解释玩家原始 world-changing intent。

如果 Execution 只有 `accepted`，尚无 durable Semantic artifact，当前最小 G7 选择 **fail closed**，不得重新调用 Semantic Provider 冒充恢复。

已经锁定的 Dice 与 Program Resolution 保持 ID / 值不变；Recovery 不重掷、不重判，Dice 继续只是 Program Resolution 的证据，不是第二 Outcome owner。

## 五、Formal Commit exactly-once 与 Response-loss

同一 logical Execution 最多产生：

- 一个 Formal Turn；
- 一次 worldTime / authoritative revision 的业务提交；
- 一组匹配的 Event / Outcome / Dice ownership；
- 一次 G6 pending Branch 消费。

Response-loss 正式支持：

```text
Atomic Commit 成功
→ HTTP / client response 丢失
→ 页面刷新 / Recovery
→ 读取同一个 committed result
```

不得再次调用 Semantic、重掷 Dice、生成第二 Outcome、创建第二 Formal Turn、推进第二次 worldTime 或创建第二 Branch。

当前 minimal G7 使用 committed Turn / revision 等 canonical evidence 确认 Execution 仍属于当前正式历史；没有建设完整 immutable response archive。

## 六、Idempotency Identity 正式语义

review-01 发现：若公开 Submit 入口只按 `(gameId, idempotencyKey)` 找到旧 Execution 就直接返回，新的不同玩家输入可能被旧 committed result 静默吞掉。

review-02 正式修复为：

```text
logical submission identity
=
gameId
+ idempotencyKey
+ expectedRevision
+ canonical playerInput（当前采用 trim 后原始输入）
```

同一个 `(gameId, idempotencyKey)` 若出现不同 `expectedRevision` 或不同 canonical `playerInput`，必须在 Provider / RNG / Commit / Recovery 之前失败关闭。

完全相同的 logical submission 可安全重放原 committed result，不重复副作用。

## 七、Recovery key 与新玩家输入分离

客户端的 pending recovery key 只属于等待恢复的旧提交，只供 `getRecoveryStatus()` / `recover()` 使用。

新的玩家 Action 如果没有显式给 key，必须生成新的 idempotency key，不能自动继承 pending recovery key。

Recovery 尚未处理完时，Engineering Playtest Shell 可以暂时禁用新 Action 输入。完整的“放弃恢复并开始另一行动”属于 G8 产品 UX。

## 八、G6 Branch 与 Recovery 共存

Recovery 不拥有 Timeline / Branch 正常语义。

当 G6 已存在 pending Branch Origin 时：

- Recovery 不重建或覆盖 origin；
- read-only / failed Execution 不消费 pending；
- 只有第一次成功新 Formal Turn 与 committed execution checkpoint 同事务时消费 pending；
- response-loss 后恢复同一个 committed Turn 不再创建第二 Branch。

## 九、玩家安全

浏览器只得到 player-safe Recovery Projection，例如 none、recoverable、committed/result available、failed 与用户可理解错误。

不得发送 raw Provider response、reasoning、完整 Prompt、private Game State、API Key / Authorization、内部数据库路径或不必要的 Execution artifact。

# G8 Runtime-extensible UI 产品架构裁定 v1.0

> 本文件冻结 G8 阶段 Runtime-extensible UI 的产品语义与 Host 能力边界。
> 不冻结 G9 `tavern-asset-spec vNext` 的最终 JSON / Schema / 字段命名。

## 1. Core 一级 World Surfaces

以下五个 Core Surface 永久具现：

1. 人物
2. 地图
3. 物品
4. 信息
5. 目标

即使当前没有内容，也保留入口并使用轻量 Empty State。

这些 Surface 是玩家理解世界的稳定入口，不是后台数据库对象的一一映射。

### 人物

聚合玩家安全的 Character、Relationship、人物相关 Commitment、最近互动、玩家已知人物信息，以及 Expansion 对人物详情的安全 Contribution。

### 地图

聚合 Region、Place、Scene、玩家已知空间关系与安全 Map Overlay。

### 物品

聚合 Item、Ownership、player-safe Placement、已知物品状态与 Item Detail Contribution。

### 信息

“信息”取代工程阶段较窄的“已知 / 记录”表达。

可聚合 Knowledge、Clue、玩家已知 Fact、Rumor、玩家可见的重要 Event 摘要、调查信息，以及来源、可信度、时效等玩家安全信息。

后台 Knowledge / Clue / Event 等对象继续职责分离。

### 目标

Task / Objective 是 World OS Core 正式能力，不是传统 RPG 强制 Quest Log。

可显示目标、阶段、状态、最近进展、期限，以及关联人物 / 地点 / 物品 / 信息。

任务不能因模糊剧情钩子滥建；玩家明确接受、主动决定、正式委托或规则触发后才形成。

---

## 2. 领域对象独立，UI 可以聚合

必须保持：

> 领域对象独立 ≠ UI 必须一对象一栏目。

Relationship、Commitment、Event、Knowledge、Clue、Task 等继续拥有独立权威语义。

Product UI 可以关联聚合，例如：

- Commitment → 人物详情中的“约定”；
- 与目标有关的 Commitment → 目标详情引用；
- Event / Knowledge / Clue → 信息；
- Relationship → 人物；
- Task → 目标。

同一事实只存在一个正式 Owner。多个 UI 位置可以引用同一 player-safe projection，但不得复制第二份业务事实源。

---

## 3. 正式合法 UI Contribution 落点

根据现有汉末三国与诸界余辉资产族的实际机制需求，Game UI Host 至少支持以下产品层落点。

### 3.1 Player Status Surface

高频玩家状态与资源，例如疲劳、饥饿、伤势摘要、Mana、Magic Strain、Divine Channel Strain 等。

不得固定假设 HP / MP / 等级 / 金币。

### 3.2 Player Character Detail Surface

玩家长期详细资料，例如技能、经历、专长、训练、魔法掌握、神术契约、详细康复状态。

左栏只承担摘要。

### 3.3 Entity Detail Surface

至少支持：

- Person Detail
- Item Detail
- Place / Region Detail

Expansion 可以向实体详情贡献安全 Section。

### 3.4 Core Surface Contribution

Expansion 可以向人物、地图、物品、信息、目标贡献安全 Section / Card / Filter / Badge / Action Intent。

### 3.5 Map Overlay

支持政治控制、战线、位面连接、魔法地脉、圣所、系统探测、资源分布等玩家安全 Overlay。

Overlay 不得泄露后台 World Truth。

### 3.6 Narrative Contextual Surface

临时机制优先进入中央上下文 UI，例如 Combat Context、施法、Divine Audience、治疗、交易、制作、抽奖等。机制结束后可收起或消失。

### 3.7 Global Notice / Alert Surface

用于高重要但非永久栏目状态，例如“历史已经改变”、危险状态、系统模块解锁、Recovery、重要世界警告。

### 3.8 Game Creation / Settings Contribution

Expansion 可以声明创建游戏或当前实例设置需求，但设置只能形成受控配置，不得直接绕过 Runtime 修改正式世界。

### 3.9 Extension Surface

真正形成独立长期玩家工作空间的机制可以获得一级 Extension Surface，例如系统、魔法、神术 / 信仰、势力 / 政务等。

---

## 4. Surface Ownership 与 Surface Contribution 分离

### Surface Ownership

资产声明：

> 我创建并拥有一个一级 Extension Surface。

### Surface Contribution

另一个资产声明：

> 我依赖该 Surface 的 Owner，并向它贡献内容。

例如：

基础魔法包 owns `surface.magic`。

主题魔法包 depends on 基础魔法包，并 contributes to `surface.magic`。

不得因为显示名相同就隐式合并互不相关的资产。

---

## 5. 创作者明确要求一级 Surface

如果创作者在拓展包创作中明确表达：

> 游戏本体应为本拓展包增加独立一级栏目 / Surface。

或语义等价的明确要求，Creator 应将其识别为：

> Extension Surface Ownership Request

最终正式资产必须把这项意图编译成结构化声明并经过 Validator。

正式 Runtime 不应在每次启动时重新用 LLM 猜说明文字。

声明合法后，Host 必须提供该一级 Surface；Host 不能因为认为内容可以塞入其他栏目而擅自取消创作者明确要求的一级工作空间。

---

## 6. Surface Owner 冲突 = 创建游戏前不兼容

一个唯一 Surface 只能有一个 Owner。

如果两个资产同时声明拥有同一个 Surface：

```text
Asset A owns surface.X
+
Asset B owns surface.X
→ Surface Ownership Conflict
→ INCOMPATIBLE
```

系统必须在创建 Game Instance 之前阻止该资产组合。

不得拖到运行时通过抢占、覆盖、加载顺序或隐式合并解决。

这条思路可泛化到其他“唯一 Owner 型 Host 能力”，例如：

- unique Rule System ownership；
- exclusive Resolution replacement；
- exclusive State / Resource namespace ownership；
- exclusive Host Capability provider。

总原则：

> 能够在组装游戏前证明组合不成立的冲突，应优先判定为资产不兼容，而不是建设运行时仲裁。

---

## 7. Host Layout Authority

资产决定“需要表达什么”，Host 决定“怎样安全呈现”。

资产不得指定任意绝对坐标、固定像素布局、任意 React、JS、DOM、eval 或 CSS 注入。

Game Host 拥有：

- Desktop / narrow 响应式；
- Tab / Drawer / overflow 表现；
- 视觉主题；
- Accessibility；
- 安全组件；
- 具体间距；
- overflow / scroll；
- UI Action → Action Intent。

---

## 8. 玩家拥有一级 Surface 最终排序权

玩家可以自行调整 Core Surface 与 Extension Surface 的显示顺序。

资产作者只能提供初始推荐顺序、推荐分组或推荐重要度。

一旦玩家调整：

> 玩家 UI Preference 优先于资产推荐。

Surface Order：

- 不形成 Formal Turn；
- 不推进 worldTime；
- 不生成世界 Event；
- 不属于 canonical Game State；
- 不属于 Save Snapshot 的世界恢复 authority；
- Restore 不回滚玩家当前 UI 排序。

如果后来出现新 Surface：

1. 保留已有玩家排序相对顺序；
2. 新 Surface 按推荐位置插入；
3. 无可靠推荐时追加到 Extension 区域；
4. 玩家之后可以重新排序。

---

## 9. 一级 Surface 过多时

通过“优先扩展已有 Surface”主动控制一级栏目数量。

例如：

- 恋爱 → 人物；
- 生存 → 玩家状态；
- 伤势 → 状态 / 人物详情；
- Theme Magic → 基础魔法 Surface；
- 战斗 → Contextual Surface；
- 线索机制 → 信息；
- 系统子功能 → 系统 Surface 内部。

空间不足时允许横向滚动或轻量 overflow / “更多”。

当前选中的 Surface 必须自动进入可见区域。

Host 不得因为空间不足，把正式一级 Surface 静默降级成另一个栏目内部内容。

---

## 10. Extension Surface 内允许受控二级结构

复杂 Extension Surface 可以拥有：

- 二级 View；
- Section；
- Host-owned sub-navigation；
- List / Card / Meter / Fact / Action 等安全组件。

例如：

```text
系统
├─ 概览
├─ 任务
├─ 商城
├─ 抽奖
├─ 仓库
└─ 强化
```

或：

```text
魔法
├─ 已学法术
├─ 法术书
├─ 仪式
└─ 研究
```

但资产仍不得构造任意页面 DOM、注入 React/CSS/JS 或自行决定像素布局。

原则：

> 允许资产描述信息架构，不允许资产执行前端。

## 12. 当前冻结摘要

```text
Core Permanent World Surfaces
=
人物
地图
物品
信息
目标
```

```text
Asset UI Extension
=
优先扩展已有 Surface
+
按机制需要贡献到玩家状态 / 实体详情 / 地图 / 中央临时 UI / Alert / Settings
+
创作者明确声明时可创建一级 Extension Surface
```

```text
same Surface owner
+
another same Surface owner
=
INCOMPATIBLE before game creation
```

```text
Asset recommends order
→ Player can reorder
→ Player preference wins
```

```text
Extension Surface
→ may declare controlled secondary Views / Sections
→ Host renders
→ no arbitrary frontend code
```

> **资产决定需要表达什么；Game Host 决定怎样安全呈现；玩家决定自己最想先看到什么。**
