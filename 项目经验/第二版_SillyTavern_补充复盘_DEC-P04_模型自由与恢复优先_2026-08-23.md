# 第二版 SillyTavern 补充复盘｜模型自由与恢复优先

## 1. 新增的一阶教训

第二版此前已经得出：

```text
Engineering Correctness != Playability Completeness
```

G9 Owner 真人试玩与核心游玩重构进一步揭示另一条同等级、甚至更深的教训：

> **风险控制成本可能远高于风险本身。**

第二版一度采用的默认思路是：

```text
模型可能犯错
↓
提前设计约束
↓
Schema
↓
Validator
↓
Typed mutation
↓
权限边界
↓
状态机
↓
更多前置防错
```

每个局部机制都能解释自己要防什么错误，但整体累积后产生了新的系统成本：

- Prompt 被大量禁止项占据；
- 模型主持能力和世界主动性下降；
- 简单世界变化被拆成机械 Tool Call；
- Context 需要携带更多协议和状态；
- 状态传播路径越来越复杂；
- 测试证明 typed path 可以工作，却更难证明真实模型能自然使用；
- 新抽象携带旧产品假设，形成新的 bug surface；
- 为了避免偶发低成本错误，核心玩法本身被压掉。

最终出现悖论：

> **为了让 AI GM 几乎不犯错，我们把它设计得越来越不像 GM。**

---

## 2. 单人 AI RPG 的很多模型错误其实很便宜

对 The World 这类单人 RPG，很多错误具有以下特点：

```text
玩家立即看得见
+
没有外部第三方副作用
+
可以重生成
+
可以撤回
+
可以回档
+
恢复只需要几十秒
```

例如：

- 一句台词不合适；
- 一个剧情方向不好；
- 一个 NPC 生成得无聊；
- 一次世界发展不够合理；
- 一处普通细节前后轻微冲突。

如果这种错误一次的真实代价只有几十秒，那么为了理论上消灭它而建设数周甚至数月的复杂 Runtime，就是典型的：

```text
Prevention Cost >> Error Cost + Recovery Cost
```

这不是稳健，而是风险治理失衡。

---

## 3. 新风险哲学：Freedom Before Prevention

以后默认不再问：

> “模型有没有可能犯错？”

因为答案几乎永远是“有可能”。

应该改问：

> “这个错误发生一次到底有多贵？”
>
> “玩家是否能发现？”
>
> “能否轻松撤回、重生成、修正或回档？”
>
> “为了避免它，我们准备付出的产品体验和工程复杂度是多少？”

因此正式原则是：

> **低成本、可感知、可恢复错误 → Recovery-first。**
>
> **高成本、不可逆、隐蔽错误 → Prevention-first。**

---

## 4. 哪些旧成果仍然正确

Recovery-first 不是否定第二版全部工程基础。

相反，以下能力价值更清楚了：

- Save / Restore；
- Crash Recovery；
- stable identity；
- atomic commit；
- branch / checkpoint；
- Source != Game-local != Runtime。

它们不只是为了“把系统做严谨”，更重要的是：

> **它们降低了模型犯错后的恢复成本。**

这意味着第二版真正应该保留的工程投入，是能让错误便宜、可逆、可恢复的基础设施；而不是无限增加让错误“绝对不发生”的预防层。

---

## 5. 哪些边界仍然值得前置保护

并非所有错误都便宜。

以下仍然需要强边界：

- 模型替玩家做不可逆决定；
- hidden / private 信息泄露；
- 修改 Source Asset 或局外持久资源；
- 外部发送、发布、支付、删除等真实副作用；
- 存档损坏且无法恢复；
- 正式高影响规则结果被随意改写。

这些错误的成本高、可能不易发现或难以恢复，所以 Prevention-first 合理。

因此真正教训不是“不要安全设计”，而是：

> **安全边界必须和风险等级匹配。**

---

## 6. 第二版为什么会走到过度预防

主要有四个原因：

1. 早期没有正式 Product Purpose / Core Value Gate，架构容易把“更严谨”误当“更正确”；
2. 自动化测试擅长验证约束是否执行，却不会告诉我们约束本身是否值得存在；
3. 理论错误比真实错误更容易在设计会议中获得注意力，因此每个“万一”都倾向于变成一个机制；
4. 真人试玩太晚，直到 Owner 真正玩起来，才看见预防机制的累积体验成本。

---

## 7. 对以后 AI 产品开发的通用教训

任何准备限制模型能力的机制，在实现前至少回答：

```text
Error frequency?
Error impact?
Detectability?
Recoverability?
Prevention cost?
Core-value damage?
New complexity / bug surface?
```

如果错误低影响、容易发现、容易恢复，而限制明显伤害核心价值，则默认不做强预防。

特别是 AI 原生产品，不应把传统确定性软件的目标：

```text
尽量消灭所有运行时错误
```

机械复制成：

```text
尽量消灭模型所有可能的语义错误
```

AI 的核心价值往往正来自开放式判断、生成和适应。把这些能力全部前置程序化，可能等于消灭产品价值本身。

---

## 8. 最终永久经验

第二版新增一条永久经验：

> **优先让模型做好它擅长的开放式工作，并让错误容易恢复；不要为了低成本的理论错误，提前建设比错误本身更昂贵的限制体系。**

与前一条教训合并后：

```text
产品目的
→ 核心体验
→ 核心循环
→ 风险真实成本
→ 最小必要护栏
→ Recovery 能力
→ 架构
→ 实现
→ 早期真人验证
```

而不是：

```text
列出模型所有可能犯的错
→ 为每一个错误建立机制
→ 最后再看产品还能不能玩
```
