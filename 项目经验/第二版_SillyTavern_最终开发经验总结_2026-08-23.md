# 第二版 SillyTavern｜最终开发经验总结

> [!summary] 最终结论
> 第二版真正的失败不是“代码质量差”或“Runtime 没做出来”，恰恰相反：它做出了大量可靠、复杂、可测试的工程基础。真正的问题是：**我们在没有持续把“做一个好玩的 AI RPG”作为最高约束的情况下，过早把大量理论风险固化成架构、状态机、Schema、Validator、权限链与 Provider 契约，最终形成了一个越来越可靠、却越来越不像优秀 AI GM 的系统。**
>
> 第二版最重要的教训不是“以后把 Runtime 做得更好”，而是：**不要把已经成熟的通用 Agent 能力重新发明成游戏 Runtime；把工程预算集中在真正独特的游戏机制上。**

---

# 1. 第二版完成了什么

第二版不是一个“什么都没做成”的项目。

它实际建立并验证了大量高质量基础：

- Program Authority 与玩家自主权边界；
- 原子 Formal Turn；
- SQLite 持久化；
- revision / CAS；
- Save / Restore / Branch；
- Crash / Resume / exactly-once Recovery；
- Creation Project；
- Source Asset 与本局实例隔离思想；
- 动态 UI Host；
- Provider 接口与真实 DeepSeek 接入；
- 多层自动化测试；
- GitHub 原生多 Agent 协作；
- Current Source / Decision Propagation；
- exact-SHA 独立审核与任务治理。

这些工作证明团队有能力构建一个相当严谨的长期 AI Runtime。

但最终真人试玩也证明：

```text
Runtime 很可靠
!=
游戏很好玩
```

甚至更进一步：

```text
Runtime 越复杂
+
错误的产品假设越深入
→
后续纠偏成本越高
```

---

# 2. 第一根本教训：Primary Purpose 必须始终压过架构局部最优

酒馆游戏的首要用途其实很简单：

> **让玩家进入一个活着的世界，由 AI 像优秀 GM 一样主动主持，让玩家不断遇到人物、局势、选择和后果，并愿意继续玩。**

第二版开发过程中，许多局部问题都有合理的工程答案：

- 如何防模型越权；
- 如何保证状态唯一；
- 如何防幻觉；
- 如何保证 Save / Restore；
- 如何做 typed mutation；
- 如何限制 Context；
- 如何保证 deterministic recovery。

但这些局部最优逐渐取代了最高问题：

> **玩家现在到底好不好玩？**

于是形成了典型反转：

```text
支撑能力
→ 逐渐成为设计中心

核心玩法
→ 逐渐变成必须适应架构的下游消费者
```

以后任何重大能力都必须回答：

1. 它直接服务什么核心体验；
2. 不做它，玩家真实损失是什么；
3. 做它会不会降低模型作为 GM 的表现；
4. 如果会，是否值得。

如果不能回答，不应因为“架构更完整”而实现。

---

# 3. 第二根本教训：不要把模型的可能错误自动升级成架构需求

第二版长期采用的隐含风险哲学接近：

```text
模型可能犯错
↓
提前限制
↓
Schema
↓
Validator
↓
权限边界
↓
Typed mutation
↓
状态机
↓
更多测试
```

每一层单独看都有理由。

但累积后产生：

- Prompt 禁止项越来越多；
- Context 工作集越来越机械；
- 模型不能自然延续剧情；
- 新 NPC / 地点需要穿过多层契约；
- 一个自然动作被拆成多个工具与阶段；
- 测试容易证明“合法 typed input 能运行”，却证明不了真实模型自然会产生这种 input；
- 新 bug 更多来自协议间矛盾，而不是模型本身。

最终得到一个核心悖论：

> **为了让 AI GM 几乎不犯错，我们把它做得越来越不像 GM。**

因此正式采用：

> **Freedom Before Prevention；Prefer Recovery over Prevention。**

低成本、可见、可恢复的错误，不值得用重型架构消灭。

---

# 4. 第三根本教训：风险治理必须看真实错误成本

单人 AI RPG 中很多错误实际很便宜：

- 一句 NPC 台词不好；
- 一个剧情发展不喜欢；
- 一次世界细节轻微冲突；
- 新 NPC 质量一般；
- GM 对某个非关键意图理解偏差。

通常可以：

```text
撤回
重新生成
人工改一句
回档
重新走一个分支
```

成本可能只是几十秒。

如果为了避免几十秒错误，建设数周或数月的 Runtime 防错系统，则是：

```text
Prevention Cost
>>
Error Cost + Recovery Cost
```

真正值得 Prevention-first 的只应是高成本边界，例如：

- Player Agency；
- 隐私 / hidden 信息泄露；
- 外部真实副作用；
- 无法恢复的数据损坏；
- 高影响正式规则结果；
- Source / 外部持久资源污染。

防错强度必须和风险等级匹配。

---

# 5. 第四根本教训：Recovery 基础设施比“绝不出错”更有长期价值

第二版中的 Save / Restore / Crash Recovery 原本主要从一致性角度建设。

经过 DEC-P04 后，它们获得了更重要的产品意义：

> **Recovery 是模型自由的保险，而不是模型自由的敌人。**

未来更值得投入的是：

- 一键 regenerate；
- 撤回最近响应；
- 回滚最近世界变化；
- checkpoint；
- branch；
- revision history；
- 玩家可理解的世界事实修正；
- 低摩擦回档。

这些能力允许模型大胆工作，又不会让一次普通错误毁掉长期游戏。

---

# 6. 第五根本教训：不要重新发明成熟 Agent 已经解决的问题

第二版自己建设了大量 Runtime 职责：

- 世界状态维护；
- 本地资产管理；
- Provider 编排；
- Context 切片；
- 工具调用；
- Mutation；
- Recovery；
- 存档；
- 文件与状态一致性。

但现代 Agent Harness 本身已经越来越擅长：

- 长上下文工作；
- 本地文件读写；
- 结构化工具调用；
- 目录与资产维护；
- checkpoint / session；
- Agentic planning；
- 多文件修改；
- 插件与工具扩展。

如果成熟 Harness 已经能可靠完成这些通用职责，游戏项目再自研一套平行 Runtime，会同时付出：

```text
开发成本
+
维护成本
+
模型能力损失
+
重复基础设施成本
+
新的集成 bug surface
```

后继方向因此应优先考虑：

> **让成熟 Agent Harness 当基础设施；游戏只开发真正独特的游戏插件。**

---

# 7. 第六根本教训：游戏层应该围绕“差异化能力”建设

如果以成熟 DeepSeek Harness 为基座，真正值得我们自己开发的部分主要是：

### GM 流程插件

负责：

- 开场点火；
- 场景主持节奏；
- 世界主动性；
- NPC 驱动；
- 情节推进；
- 局势 / 钩子；
- 回合或非回合主持节奏；
- 何时调用其它 RPG 插件。

### RPG 元素插件

负责真正需要明确规则的部分：

- 属性；
- 技能；
- 判定；
- 战斗；
- 资源；
- 状态；
- 装备；
- 成长；
- 时间 / 旅行等需要规则化的机制。

### 拓展包机制插件

负责：

- 世界观特殊规则；
- 角色专属机制；
- 阵营机制；
- 魔法 / 科技 / 政治 / 经营等特殊系统；
- 通用核心机制与专用扩展之间的依赖。

### 产品体验层

只在真实玩法需要时增加：

- 游戏 UI；
- 状态展示；
- 角色 / 地图 / 任务视图；
- 存档管理；
- 插件配置。

原则是：

```text
能由成熟 Harness 做好的通用能力
→ 不重复开发

真正决定“这是一个什么游戏”的能力
→ 我们自己做
```

---

# 8. 第七根本教训：插件化应该解决产品组合，不应再次演化成万能协议工程

第二版已经证明，“高度扩展”本身很容易诱导过早平台化。

后继项目即使采用高度插件化 Harness，也必须避免再次犯：

```text
为了未来可能需要的插件
→ 先设计万能 Schema / DSL / Protocol
→ 再让玩法适应协议
```

正确顺序仍然是：

```text
核心玩法
↓
真实插件需求
↓
最小插件接口
↓
第二个真实消费者
↓
抽取共享能力
↓
再稳定协议
```

特别是拓展包开发已经得到明确教训：

```text
通用核心引擎
↓
通用机制插件
↓
世界 / 品类级扩展
↓
角色 / 特定内容专用扩展
```

不能再先写一批专用包，最后才发现底层核心需要重构。

---

# 9. 第八根本教训：真实 Provider 是架构测试的一部分

第二版后期 correction-01 有一个非常有价值的例子：

所有离线测试都通过以后，真实 DeepSeek 探针仍然把：

```text
traversalDurationMinutes
```

输出成带单位的自然语言，导致 parser 失败。

这证明：

```text
Schema test PASS
Fixture PASS
Parser test PASS
```

仍然不能替代：

```text
真实模型
→ 真实 Prompt
→ 真实 Tool Call
→ 真实 Program consumer
```

以后任何模型主导能力，在基础安全 Gate 通过后，应尽早做少量、受控、可清洗的真实 Provider 探针。

真实模型不是部署末端，它本身就是架构依赖。

---

# 10. 第九根本教训：Context 的问题不是越少越好，而是职责所需信息要完整

第二版经历了两种错误：

```text
给太多
→ Context 膨胀 / 泄露风险
```

和：

```text
给太少
→ 模型看不到局势 / 背景 / 当前变化
```

后者同样致命。

例如：

- Active Situation 已存在但模型看不到；
- 玩家刚移动，World Initiative 却仍读取旧世界 frame；
- Narrative 看不到完成当前职责所需的人物背景。

因此：

> **Bounded Context != Starved Context。**

Context 设计的正确问题不是“还能裁掉多少”，而是：

> **这个 Agent 当前职责需要哪些最小充分信息？**

成熟 Harness 如果已经拥有更好的文件搜索、working memory、tool retrieval 与上下文路由能力，也应优先复用，而不是在游戏内再造一套复杂 Context compiler。

---

# 11. 第十根本教训：Player Agency 需要保护，但世界不属于玩家授权

第二版最严重的语义扩张之一是：

```text
Player Authorization
```

逐渐变成：

```text
World Authorization
```

最后表现为：

- 玩家没先说出某人 → 世界难以生成这个人；
- 玩家没说出某地点 → 世界难以创建这个地点；
- 世界变化需要从玩家输入找 evidence；
- NPC / 世界主动发展被系统性压制。

正确边界是：

```text
玩家做什么
→ 玩家授权

NPC / 世界做什么
→ GM / 世界拥有行动权

高影响规则结果
→ 规则插件裁定
```

这三者不能再混成一套总授权链。

---

# 12. 第十一根本教训：不要让 Typed Reality 变成 Typed Story

结构化状态对长期 RPG 很有价值。

但第二版逐渐出现一个危险趋势：

> 因为 durable reality 需要结构化，所以故事本身也越来越被迫结构化。

两者应严格区分：

### 适合结构化

- HP；
- inventory；
- identity；
- location；
- relationship 的机械值；
- rule state；
- checkpoint；
- 真正需要长期查询的关键世界事实。

### 不应过早结构化

- 一次普通对话的意义；
- NPC 当下语气；
- 大量剧情节拍；
- 所有世界细节；
- 所有剧情因果；
- 所有潜在未来内容。

如果 Agent + 文件本身已经能维护大部分开放世界记忆，则只有真正需要程序化消费的部分才值得进入 typed state。

---

# 13. 第十二根本教训：测试数量不能抵消测试对象选错

第二版最终拥有超过千项测试。

问题不是测试没用，而是很多测试验证的是：

> **在当前架构假设成立时，代码是否正确。**

它们无法回答：

> **当前架构假设本身是不是错的。**

甚至约束越多，测试越容易证明“系统严格执行了错误限制”。

以后测试至少分四层：

```text
工程正确性
真实 Provider 契约
真实产品纵向
真人核心价值
```

最后一层不能被前面三层替代。

---

# 14. 第十三根本教训：真人试玩应该是架构发现工具，而不是最终验收仪式

如果第二版在最早能运行核心 GM 循环时，就进行短时间真人连续试玩，很多问题会很早暴露：

- 世界不主动；
- 玩家不知道做什么；
- 第二 NPC / 第二地点出不来；
- AI GM 比普通网页版 AI 更僵硬；
- 规则和安全机制开始压制体验。

以后正确节奏应是：

```text
最小核心循环能运行
↓
立刻试玩
↓
修产品方向
↓
再增加基础设施
```

而不是：

```text
把基础设施做完整
↓
最后让玩家试试看
```

真人试玩是最便宜的架构反证之一。

---

# 15. 第十四根本教训：简单基线必须长期存在

第二版真正刺眼的对照不是另一个复杂游戏框架，而是：

> **直接打开一个强模型，对它说“我要玩 RPG，你来主持”。**

如果复杂产品在：

- 主动性；
- 创意；
- NPC 自然表现；
- 场景推进；
- 承接意图；
- 继续玩的欲望；

这些核心维度上明显更差，那么：

```text
更可靠
更持久
更多测试
更复杂
```

都不能证明产品成功。

后继项目应把“裸 DeepSeek GM”作为长期对照组。

每增加一个插件或规则，都应问：

> **它让游戏更好了吗，还是只是让系统更复杂了？**

---

# 16. 第十五根本教训：旧代码不是资产，经过证明仍适合新目标的代码才是资产

沉没成本最危险的表现是：

```text
已经写了这么多
→ 所以新方案应该继续建立在旧代码上
```

这是错误的。

后继项目应采用反向继承：

```text
新产品核心成立
↓
旧能力逐项申请进入
↓
证明仍符合新产品哲学
↓
才迁移
```

而不是：

```text
旧 Runtime 先全部保留
↓
再把新玩法塞进去
```

真正值得继承的是已经验证的知识、资产、Recovery 经验和必要基础，不是历史代码量本身。

---

# 17. 第十六根本教训：停止项目也是一种正确的工程决策

持续修补并不天然比重启更负责。

当出现以下组合时，应正式比较 rebuild：

- 根本产品哲学已改变；
- 旧假设进入多个基础抽象；
- 每修一层又暴露同根下一层；
- 测试体系大量绑定旧语义；
- 新方案可以依赖更成熟的通用基础；
- 继续修复的预期成本超过重建核心纵向。

此时继续投入可能只是沉没成本偏差。

第二版最终停止 correction-02，就是一次有价值的终止决策：

> **项目已经完成了其学习价值，不需要为了证明“能修好”而继续支付无限纠偏成本。**

---

# 18. 后继项目建议的最小启动方式

第三版 / 后继项目不应先建设完整框架。

第一阶段只做一个极小的真实纵向：

```text
成熟 DeepSeek Harness
+
汉末世界资产
+
刘备角色
+
GM 流程插件
+
一个最小 RPG 判定插件
+
Harness 原生文件 / 存档能力
↓
连续真人玩 10–20 回合
```

成功只看：

1. 世界会不会自己发生事情；
2. NPC 会不会自然主动；
3. 新人物 / 地点 / 局势会不会自然生长；
4. 玩家能不能自由尝试；
5. 重要选择有没有后果；
6. AI 是否能维护足够一致的本地资产与存档；
7. 出错后是否能快速恢复；
8. 加插件以后是否仍然不明显输给裸 DeepSeek GM；
9. 玩家是否愿意继续玩。

在这九项成立前：

- 不做大型协议；
- 不做万能 Schema；
- 不做复杂插件市场；
- 不做长期平台化；
- 不为低概率理论错误建立重 Runtime。

---

# 19. 第二版最终应该留下什么

第二版最有价值的遗产不是代码仓库本身，而是以下认知：

```text
1. 先定义产品核心，再设计架构。
2. Guardrail 不能成为 Product Owner。
3. 模型可能犯错，不等于必须提前限制。
4. 低成本错误优先 Recovery。
5. 不要重新发明成熟 Agent 已有能力。
6. 自研部分集中在真正差异化的游戏机制。
7. Player Agency 与 World Agency 必须分离。
8. Typed Reality 不应演化成 Typed Story。
9. Bounded Context 不能变成 Starved Context。
10. Fixture / 测试通过不等于真实产品成立。
11. 真实 Provider 必须尽早进入纵向验证。
12. 真人试玩是架构发现工具。
13. 简单基线必须长期存在。
14. 旧代码只有在符合新目标时才值得继承。
15. 停止错误路线也是项目成功的一部分。
```
