## 0. 当前产品基线

当前正式产品方向：

> **Personal State / Information & Action Desktop**

CORE：

```text
Today
Plan
Tracks
```

V0：

> **Thin Tracks + Usable Plan + Derived Today**

核心关系：

```text
Tracks
= 长期事项与当前真实状态
        ↓ 可选关联
Plan
= 未来安排 / 日程 / Reminder / Memo / Current Vector / Unscheduled
        ↓ 按当前日期派生
Today
= 默认首页 / 当日信息切片
```

# A. Canonical State / Ownership

## AQ-A01｜Tracks / Plan / Today 各自拥有什么事实？

- **Question**：三者的 authoritative state / derived projection 边界如何定义？
- **Why it matters**：如果 Today、Plan、Tracks 各自复制同一事实，会形成多份 live truth。
- **Cost of being wrong**：高；后续编辑、恢复、同步都会出现状态冲突。
- **Category**：Canonical ownership
- **Current hypothesis**：Tracks 拥有 Track 长期状态；Plan 拥有未来安排、循环定义、Reminder、Memo、Unscheduled、Current Vector；Today 主要是派生视图。
- **Evidence needed**：Reference Audit 检查类似产品的状态边界；实现前 state matrix。
- **Decision status**：**OWNER-APPROVED CONSTRAINT**：Today 不复制 Plan / Tracks 的业务事实。

## AQ-A02｜Today 的“已完成”是否改变 Plan / Track？

- **Question**：Today 勾选完成是否属于业务状态变更？
- **Why it matters**：产品明确不希望 Today 变成 Habit / 评分系统，也不希望一次确认自动推进长期状态。
- **Cost of being wrong**：高；会把 Today 变成第二套任务状态源。
- **Category**：Canonical ownership
- **Current hypothesis**：Today 只保存极窄的“当天确认”辅助状态。
- **Evidence needed**：实现前明确 acknowledgement key 与 retention。
- **Decision status**：**OWNER-APPROVED CONSTRAINT**：Today 的“已完成”只是当天视觉确认；不修改 Plan、Track、循环定义，不产生完成率、连续打卡或长期行为评价。

## AQ-A03｜Today 当天确认需要持久化多久？

- **Question**：关闭 / 重启后勾选是否保留，历史是否永久保存？
- **Why it matters**：当天体验不能因重启丢失，同时又不应无意形成长期行为历史库。
- **Cost of being wrong**：中。
- **Category**：Persistence
- **Current hypothesis**：当天确认应跨当日 restart 保留，但 V0 不承诺长期历史统计。
- **Evidence needed**：Reference Audit / 实现设计确定最小保留策略。
- **Decision status**：**OWNER-APPROVED CONSTRAINT**：需要支持当日视觉状态可靠恢复；长期完成历史 / 统计明确不是 V0 目标。

# B. Track Model

## AQ-B01｜Track 的最小稳定身份是什么？

- **Question**：Track 是否需要与名称分离的 immutable internal identity？
- **Why it matters**：Track 可重命名，Plan Item 又可以关联 Track。
- **Cost of being wrong**：高；名称变化可能破坏引用。
- **Category**：Identity
- **Current hypothesis**：HYPOTHESIS：使用稳定内部 ID，名称只是 display field。
- **Evidence needed**：Reference Audit + implementation state model。
- **Decision status**：**HYPOTHESIS**。

## AQ-B02｜Thin Track 的字段边界是否足够？

- **Question**：Name / Long-term Goal / Current Phase / Current Real State / Near-term Direction / Last Updated / Status 是否足够支撑 V0？
- **Why it matters**：字段过少无法表达长期状态；字段过多会把 Tracks 做成项目管理系统。
- **Cost of being wrong**：中高。
- **Category**：Product-dependent architecture
- **Current hypothesis**：产品定义中的 Thin Track 足以作为 V0 first consumer。
- **Evidence needed**：Owner 真实数据 UAT。
- **Decision status**：**PROPOSED**。

## AQ-B03｜Track Lifecycle

- **Question**：Active / Completed / Archived 的 transition 与可恢复性如何实现？
- **Why it matters**：默认列表只应显示真正活跃事项，但历史不应因状态切换丢失。
- **Cost of being wrong**：中。
- **Category**：Lifecycle
- **Current hypothesis**：Completed / Archived 都保留对象；默认首页只展示 Active。
- **Evidence needed**：UAT。
- **Decision status**：**OWNER-APPROVED PRODUCT CONSTRAINT**。

## AQ-B04｜Sources / Update Mode 在 V0 做到什么程度？

- **Question**：产品定义预留 Sources / Update Mode，但 GitHub / AI update 不属于 V0，是否应提前做 UI 或平台？
- **Why it matters**：过早实现会形成没有真实 consumer 的同步 / AI 平台。
- **Cost of being wrong**：高。
- **Category**：Future extension boundary
- **Current hypothesis**：可保留最小 nullable 语义空间，但 V0 UI 不展示，不实现同步 / 自动更新能力。
- **Evidence needed**：未来第一个真实 Source consumer。
- **Decision status**：**OWNER-APPROVED CONSTRAINT / DEFERRED IMPLEMENTATION**。

# C. Plan Model

## AQ-C01｜Plan 中不同对象是否应强行统一成一种万能 Item？

- **Question**：Scheduled Item、Unscheduled、Reminder、Memo、Current Vector 是否共享单一用户模型？
- **Why it matters**：它们语义明显不同；过度统一会产生大量无意义字段和复杂表单。
- **Cost of being wrong**：高。
- **Category**：Domain model
- **Current hypothesis**：UI 明确认可它们是不同类型；底层是否共享部分字段由实现证据决定。
- **Evidence needed**：02 研究类似 planner 的 domain model；实现前 minimal schema review。
- **Decision status**：**OWNER-APPROVED CONSTRAINT**：用户界面不采用一个“万能事项”表单。

## AQ-C02｜Track Link 如何表达？

- **Question**：Plan Item 可选关联 Track 时，如何保持引用稳定？
- **Why it matters**：不得依赖标题关键字猜测，也不能因 Track 改名丢失关系。
- **Cost of being wrong**：高。
- **Category**：Identity / reference
- **Current hypothesis**：HYPOTHESIS：引用 Track stable identity；不复制 Track 状态到 Plan。
- **Evidence needed**：Track identity decision。
- **Decision status**：**HYPOTHESIS**。

# D. Calendar / Recurrence

## AQ-D01｜循环定义与某一次发生如何区分？

- **Question**：循环事项是否提前持久化所有 occurrence？
- **Why it matters**：提前展开会产生大量重复数据，并使编辑整个系列非常困难。
- **Cost of being wrong**：很高。
- **Category**：Recurrence / identity
- **Current hypothesis**：循环规则是 authoritative definition；occurrence 按日期动态派生；仅 exception 持久化。
- **Evidence needed**：02 研究成熟 calendar 的 recurrence semantics；必要时 technical spike。
- **Decision status**：**OWNER-APPROVED CONSTRAINT**。

## AQ-D02｜编辑循环事项时有哪些作用范围？

- **Question**：编辑某次 occurrence 时是否提供“仅这一次 / 整个循环 / 这次及以后”？
- **Why it matters**：第三种会引入 series split，显著增加 V0 复杂度。
- **Cost of being wrong**：高。
- **Category**：Recurrence UX / domain semantics
- **Current hypothesis**：V0 只提供“仅这一次 / 整个循环”。
- **Evidence needed**：Owner UAT。
- **Decision status**：**OWNER-APPROVED CONSTRAINT**。

## AQ-D03｜删除循环事项时有哪些作用范围？

- **Question**：删除某次 occurrence 如何影响系列？
- **Why it matters**：删除一次不能终止整个系列。
- **Cost of being wrong**：高。
- **Category**：Recurrence UX / domain semantics
- **Current hypothesis**：V0 只提供“仅这一次 / 整个循环”。
- **Evidence needed**：Owner UAT。
- **Decision status**：**OWNER-APPROVED CONSTRAINT**。

## AQ-D04｜Occurrence 的稳定身份如何生成？

- **Question**：动态 occurrence 如何被单次修改 / 删除 / Today acknowledgement 精确引用？
- **Why it matters**：这是 recurrence exception 与 Today 当日确认的底层关键。
- **Cost of being wrong**：很高。
- **Category**：Identity / Spike-required
- **Current hypothesis**：HYPOTHESIS：由 series stable ID + occurrence logical date/time 形成稳定逻辑键；具体算法不冻结。
- **Evidence needed**：Reference Audit + technical spike / deterministic tests。
- **Decision status**：**OPEN / SPIKE-REQUIRED**。

## AQ-D05｜时区与本地日期语义

- **Question**：V0 单用户 Windows 桌面应用如何处理本地时区、系统时区变化和 date-only 数据？
- **Why it matters**：Today、循环日程、Reminder 都依赖“今天”与本地时间。
- **Cost of being wrong**：高。
- **Category**：Reference-dependent / Spike-required
- **Current hypothesis**：HYPOTHESIS：V0 以 Owner 本地时区为主，但必须避免 date-only 因序列化跨日。
- **Evidence needed**：02 技术研究 + 日期边界测试。
- **Decision status**：**OPEN**。

# K. 当前高沉没成本问题

Route Freeze 前必须由 G0.4 Reference Audit / 必要 Spike 重点攻击：

1. **Desktop host**：托盘、窗口隐藏/恢复、Windows 长期运行、本地数据库与打包是否稳定；

7. **Track reference identity**：Track 改名不能破坏 Plan linkage；
8. **Migration contract**：V0 数据一旦进入真实使用，后续版本不能用重建数据库替代迁移。

# L. 当前架构位置

已经经 Owner 明确认可、可作为 G0.3 submission 输入的约束主要包括：

- Workbench 自己拥有 Core Personal State；
- Today 主要是 derived view，不复制 Plan / Tracks live truth；
- Today “已完成”只是当日确认视觉状态，不推进 Plan / Track；
- Current Vector 日期区间禁止重叠，系统不自动修改其它 Vector；

- Sources / Update Mode 不在 V0 UI 建平台；
- Plan 不以一个万能表单强行统一所有语义；
- Milestones / AI / GitHub sync / Google Calendar / Custom / Plugin / SDK / Page Builder 均不阻塞 V0。

仍然没有冻结：

- Electron / Tauri / Native / Web host；
- SQLite / file / embedded DB；
- 具体 schema；
- occurrence key 算法；
- UI component framework；
- backup file format；
