## 1. 项目定位基线

Personal Workbench 从零启动，目标是**逐步构建一个真正改善 Owner 现有 AI Coding 工作流的个人开发工作台**。

当前阶段不以“建设庞大的多 Agent 平台”为默认目标，也不以功能数量、Agent 数量或统一所有工具为成功标准。

现实中的简单基线是：

```text
ChatGPT Web
+ GitHub
+ 外部 Coding / Review Agent
+ Owner 人工协调与 UAT
```

`01｜产品定义` 已形成 `current/产品定义.md` v0.1。经 `00｜项目总控` Stage Gate 审核，**G0.1 Product Baseline 与 G0.2 Scope 已达到 PASS，可进入 Draft Task Axis；这不等于 Route Freeze 或 implementation authorization。**

当前第一版产品命题是：

> 把 Owner 已经在使用的 `ChatGPT → Coding Agent → GitHub → ChatGPT Review` 工作流收敛成一个明显更顺畅、仍由 Owner 控制的闭环，优先消除复制、切换、启动、观察和 Review 提醒等机械协调劳动。

首条验证纵向采用 **Codex-first**：

```text
Discuss
→ Select GPT text
→ Send to Codex
→ Real execution
→ GitHub push
→ One-click GPT Review
→ Fix / Accept
```

完整 Primary Purpose / JTBD / Core Value / V0 Scope / Deferred / Non-scope / Success Criteria 以 `current/产品定义.md` 为准。

## 2. 当前现实协作模型

在 Workbench 自身尚未具备调度能力之前：

- **ChatGPT Web** = 临时 Control Plane，负责讨论、产品/架构推演、任务规划、审核与跨聊天协调；
- **GitHub** = 正式项目事实、代码、Task 与 Review evidence 的共享状态层；
- **Codex / Grok / Kimi 等外部 Agent** = Coding / Review / Investigation 执行者；V0 首条纵向只要求 Codex；
- **用户** = Product Owner + 最终 UAT 裁定者。

禁止把未来 Workbench 可能拥有的能力当作当前已存在能力。例如自动 Agent 调度、自动完成检测、自动触发 Review、统一日志、额度管理等，在被正式实现与验证前都只是候选能力。

## 4. Authority

默认权威顺序：

1. 用户当前明确指令；
2. 当前项目 GitHub 中已批准的 Product / Architecture / Roadmap / Decision；
3. implementation repository 当前代码、测试、运行事实和 Git HEAD；
4. Vibe-Coding 当前治理规则与适用 Skill；
5. 当前项目其他聊天中的已确认结论；
6. 历史资料、Reference 与模型记忆。

历史聊天不能自动覆盖 current source。

若两个 current source 冲突，不得自行拼接第三套方案；应进入冲突识别与 Owner 裁定流程。

## 5. 项目推进顺序

```text
Primary Purpose / Core Value
```

专业聊天可产出证据和建议，但重大跨域裁定与 Stage 切换回到 `00`。

## 8. Decision Propagation

任何已批准决定都必须继续判断是否影响：

- Current Stage / Gate；
- Current Goal / Blocker；
- Product Scope；
- Task Axis / Roadmap；
- Architecture Questions；
- 已发 executable Task；
- implementation repository；
- Review / UAT 要求。

重大决定不能只停留在聊天记录中；应写回对应 canonical GitHub source。
