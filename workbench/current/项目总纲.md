状态：current

Owner：用户（最终 Product Owner）

> 本文件记录项目已经明确的基础规则与协作边界。它不是最终 Product Definition，也不冻结具体技术架构。

## 1. 项目定位基线

Personal Workbench 从零启动，目标是**逐步构建一个真正改善 Owner 现有 AI Coding 工作流的个人开发工作台**。

当前阶段不以“建设庞大的多 Agent 平台”为默认目标，也不以功能数量、Agent 数量或统一所有工具为成功标准。

最终产品价值需要相对于现实中的简单基线得到证明：

```text
ChatGPT Web
+ GitHub
+ 外部 Coding / Review Agent
+ Owner 人工协调与 UAT
```

第一版究竟优先消除哪一种摩擦、形成怎样的 Core Value，仍由 `01｜产品定义` 在 Stage 0 内进一步明确并提交 Owner 审核。

## 2. 当前现实协作模型

在 Workbench 自身尚未具备调度能力之前：

- **ChatGPT Web** = 临时 Control Plane，负责讨论、产品/架构推演、任务规划、审核与跨聊天协调；
- **GitHub** = 正式项目事实、代码、Task 与 Review evidence 的共享状态层；
- **Codex / Grok / Kimi 等外部 Agent** = Coding / Review / Investigation 执行者，具体角色不在 Stage 0 预先冻结；
- **用户** = Product Owner + 最终 UAT 裁定者。

禁止把未来 Workbench 可能拥有的能力当作当前已存在能力。例如自动 Agent 调度、自动完成检测、自动触发 Review、统一日志、额度管理等，在被正式实现与验证前都只是候选能力。

## 4. Authority

默认权威顺序：

1. 用户当前明确指令；
2. 当前项目 GitHub 中已批准的 Product / Architecture / Roadmap / Decision；
3. implementation repository 当前代码、测试、运行事实和 Git HEAD；
4. Vibe-Coding 当前治理规则与适用 Skill；
5. 当前项目其他聊天中的已确认结论；
6. 历史资料、Reference 与模型记忆。

历史聊天不能自动覆盖 current source。

若两个 current source 冲突，不得自行拼接第三套方案；应进入冲突识别与 Owner 裁定流程。

## 5. 项目推进顺序

当前项目遵循：

```text
Primary Purpose / Core Value
→ Product Definition
→ Draft Task Axis
→ Reference Audit
→ Risk / Omission / Ordering Review
→ Owner Discussion
→ Revised Task Axis / Architecture
→ Owner Approval
→ Route Freeze
→ Implementation
→ Validation
→ Independent Review
→ Owner UAT
→ Decision Propagation
→ 下一阶段
```

除明确标记为 Spike / Prototype 的低成本探索外，在 Route Freeze 前不得推动正式大规模实现。

## 6. Stage 0 当前要求

Stage 0 必须至少关闭以下问题：

1. Primary Purpose / JTBD / Core Value；
2. Core User Journey / Non-negotiable Core；
3. Simple Baseline 与成功标准；
4. REQUIRED / Deferred / Non-scope / Future；
5. Draft Task Axis；
6. 至少两种独立视角的 Reference / Path Audit；
7. 高沉没成本决策与关键 Architecture Questions；
8. 最早 First Usable / Reality Gate / Owner UAT 节点；
9. Revised Task Axis 与必要 Architecture；
10. Owner Route Freeze。

在这些问题关闭前，DeepSeek Harness、Electron/Tauri、具体 Agent Router、MCP、数据库、统一额度面板等均不得因为历史讨论而自动成为 current architecture。

## 7. 专业聊天职责

- `00｜项目总控`：Stage / Gate / Status / 跨域冲突 / Decision Propagation；
- `01｜产品定义`：Primary Purpose / Core Value / Scope / Product Definition；
- `02｜参考审计与技术研究`：参考项目、历史经验、可行性、Spike、Build/Fork/Extend/Rewrite 证据；
- `03｜架构与开发路线`：Architecture Questions、Draft / Revised Task Axis、Roadmap、Architecture；
- `04｜Agent 任务调度`：Gate 通过后的 executable Work Item / Task Packet / Agent routing；
- `05｜代码审核与 UAT`：Independent Review、Debug、Reality Gate、Owner UAT 设计与 Stage Exit Audit。

专业聊天可产出证据和建议，但重大跨域裁定与 Stage 切换回到 `00`。

## 8. Decision Propagation

任何已批准决定都必须继续判断是否影响：

- Current Stage / Gate；
- Current Goal / Blocker；
- Product Scope；
- Task Axis / Roadmap；
- Architecture Questions；
- 已发 executable Task；
- implementation repository；
- Review / UAT 要求。

重大决定不能只停留在聊天记录中；应写回对应 canonical GitHub source。
