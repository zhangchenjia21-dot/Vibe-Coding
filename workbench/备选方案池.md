# Personal Workbench｜备选方案池

状态：**IDEA POOL / NON-CURRENT / NON-AUTHORITY**  
Owner：用户（最终 Product Owner）  
适用范围：Personal Workbench 的未来产品机会、候选能力与尚未进入正式 Roadmap 的构想

> 本文件用于保存“值得保留，但当前不应进入 V0 / Current Product / Route Freeze”的想法。
>
> 收录到本文件 **不等于批准开发、不等于进入 Roadmap、不等于 Architecture Decision**。任何条目未来若要进入正式开发，仍需经过 Product Discovery、必要的技术 / Reference Audit、Owner 审核与对应 Stage Gate。

---

## 1. 使用规则

### 1.1 什么内容进入这里

适合进入备选方案池的内容包括：

- Owner 在开发过程中产生、值得保留的未来功能设想；
- 已有真实痛点，但当前优先级不足以进入 V0 的能力；
- 可能改变长期产品形态，但尚未经过充分验证的产品机会；
- 值得未来做 Spike / Research 的自动化、工作流或集成方向。

### 1.2 什么内容不进入这里

- 已确认并正在生效的 Product Definition → `current/`；
- 已批准的正式 Architecture → `architecture/`；
- Owner 正式裁定 → `decisions/`；
- Reference / Spike 证据 → `research/`；
- executable implementation Task → `zhangchenjia21-dot/Workbench`。

### 1.3 Promotion 路径

```text
Idea Pool
→ 真实需求再次出现 / 价值信号增强
→ Product Discovery
→ 必要 Research / Spike
→ Owner 审核
→ Current Product / Roadmap / Decision
→ Stage Gate
→ Implementation
```

不要因为某个想法“以后可能有用”就直接从 Idea Pool 跳进实现。

## 2. 当前备选方案

### IDEA-001｜Workflow Playbooks / 固定工作流模板与自动化

状态：**候选 / Future / Not in V0**  
首次记录：2026-09-06  
建议长期归属：`CORE → Workflows / Automation` 候选

#### A. 真实问题

Owner 当前启动一类成熟开发流程时，仍需要重复执行大量已经相对固定的初始化工作。

以“启动一个新的 AI 驱动软件项目”为例，当前可能需要：

```text
产生新项目想法
→ 先新建一个 GPT 聊天询问如何启动项目
→ 在 ChatGPT Web 新建 Project
→ 配置 Project Instructions
→ 新建 00｜项目总控
→ 新建 01｜产品定义
→ 新建 02｜参考审计与技术研究
→ 新建 03｜架构与开发路线
→ 新建 04｜Agent 任务调度
→ 新建 05｜代码审核与 UAT
→ 分别注入对应初始 Prompt / 规则
→ 建立或关联 GitHub repository
→ 建立 Vibe-Coding 项目治理工作区
→ 才真正开始项目开发流程
```

这些步骤中有相当一部分并不需要 Owner 每次重新判断，而属于重复、机械、可模板化的工作。

#### B. 产品机会

Workbench 未来可以保存 Owner 已经验证过的固定开发方法，并允许通过快捷方式、引导式流程或自动化重新启动。

核心目标不是保存几段 Prompt，而是：

> **把 Owner 已经稳定形成的工作方法，从“存在脑中 / 旧聊天 / 文档里”升级为可重复启动、可执行、可演化的 Workflow Playbook。**

#### C. 理想使用体验

未来可以存在：

```text
New Workflow

选择 Playbook：
● AI 驱动新项目开发
○ Existing Project Feature Development
○ Bug / Debug
○ Architecture Refactor
○ Release
○ 其它 Owner 后续沉淀的流程
```

选择“AI 驱动新项目开发”后，仅要求填写真正需要变化的参数，例如：

```text
项目名称：Personal Workbench
Implementation Repo：zhangchenjia21-dot/Workbench
Governance Workspace：Vibe-Coding/workbench
```

然后由 Workbench 执行或引导可自动化步骤，例如：

```text
✓ 建立 Project Workspace
✓ 建立 / 关联 GitHub repository
✓ 建立治理目录
✓ 加载适用 Lifecycle
✓ 创建 / 引导建立 ChatGPT Project
✓ 创建 / 引导建立 00～05 专业聊天
✓ 注入对应初始化 Prompt / 规则
✓ 初始化项目状态与 Stage Gate
→ 打开 00｜项目总控，开始正式流程
```

自动化程度可以逐步提高，而不要求第一次实现就全部自动完成。

#### D. 正确抽象：Playbook，而不是 Prompt Library

此能力不应只做成：

```text
[复制 00 Prompt]
[复制 01 Prompt]
[复制 02 Prompt]
```

更完整的 Playbook 应逐步能够表达：

```text
Step
→ Actor / Tool
→ Input
→ Template / Instruction
→ Expected Output / Artifact
→ Owner Gate
→ Completion Condition
→ Next Step
```

例如：

```text
Step：Product Definition
Actor：ChatGPT
Input：项目初始目标
Template：01｜产品定义
Output：产品定义 Owner
Gate：G0.1 / G0.2
Next：Draft Task Axis / Architecture Questions
```

因此该能力长期更接近“可执行工作方法”，而不是静态 Prompt 收藏夹。

#### E. 可能的成熟层级

可以考虑按复杂度渐进实现：

**L1｜Shortcut / Template**  
保存流程说明、初始化 Prompt 与快捷入口，主要由 Owner 手动确认执行。

**L2｜Guided Workflow**  
Workbench 根据当前 Step 告诉 Owner 下一步做什么，并自动准备相关模板与上下文。

**L3｜Semi-Automation**  
能自动建立部分 Project / Repository / Governance 文件 / ChatGPT 输入，并在关键 Gate 请求 Owner 确认。

**L4｜Executable Playbook**  
在外部能力允许的前提下，自动执行大部分机械步骤，仅把产品、架构、风险与 UAT 等真正需要判断的 Gate 留给 Owner。

目标原则始终是：

> **Owner 做判断，Workbench 做机械操作。**

#### F. 与当前 V0 的关系

**不进入当前 V0。**

当前 V0 继续聚焦高频、高摩擦的 AI Collaboration Core：

```text
ChatGPT
→ Selected Text
→ Codex
→ GitHub
→ ChatGPT Review
```

Workflow Playbooks 解决的是更高层的“如何重复启动和推进一整套工作方法”，属于低频但高摩擦的流程自动化问题。

当前只要求：

- UI / 信息架构不要把未来扩展空间彻底封死；
- 不为该能力提前建立大规模 Workflow Engine；
- 不改变现有 Product Definition / V0 Scope / Route Gate。

#### G. 与 AI Collaboration Core 的长期关系

二者未来可能形成两个互补层级：

```text
CORE
├── AI Collaboration
│   └── GPT ↔ Agent ↔ GitHub 的单次任务执行闭环
│
└── Workflows / Playbooks
    └── 保存并组织多个步骤、多个 Gate 与多个任务循环
```

AI Collaboration 负责“这一条任务怎么执行”；Workflow Playbooks 负责“这一类事情通常按什么流程推进”。

#### H. 需要未来验证的问题

1. ChatGPT 是否提供稳定、合规的能力来创建 Project / Chat、注入 Prompt 或执行类似初始化操作；
2. 如果无法直接自动化 ChatGPT Web，什么级别的引导 / 半自动体验仍然足够有价值；
3. Playbook 是纯数据模板、状态机、DSL 还是其它形式；
4. 如何表达 Step、Gate、Dependency、Artifact 与 Owner Confirmation；
5. Playbook 如何版本化，避免固定流程本身发生变化后旧模板悄悄过期；
6. 哪些步骤可以安全自动化，哪些必须保留 Human Gate；
7. GitHub repository、Vibe-Coding governance workspace 与本地项目初始化如何统一参数化；
8. 是否应支持“从一次成功完成的真实流程反向沉淀为 Playbook”。

#### I. Promotion Trigger

只有在满足至少一类信号后，再考虑把本条目升级为正式 Product Discovery / Roadmap 候选：

- AI Collaboration V0 已通过真实 Owner UAT；
- Owner 在多个项目中重复执行相同启动 / 开发流程，重复劳动持续出现；
- 现有流程已经稳定到足以模板化，而不是仍在频繁变化；
- 技术 Spike 证明关键自动化步骤具有合理稳定性；
- 实现该能力不会反向拖累当前更高频的 AI Collaboration Core。

```text

C. 理想体验
```
