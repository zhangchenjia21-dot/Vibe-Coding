# 3. S1｜Packaged Windows Desktop Lifecycle

## 3.1 Question

验证候选 desktop host 是否能在真实 Windows runner 中完成：

```text
packaged / release executable
→ tray object exists
→ close window does not terminate app
→ window becomes hidden
→ tray restore handler restores/focuses window
→ explicit real exit terminates process
→ packaging output exists
```

候选：

- Electron
- Tauri v2

## 3.2 Important limitation

GitHub hosted runner 能执行 GUI app 和检查 lifecycle 状态，但不能像 Owner 本人一样肉眼确认 notification-area icon，也不能真实用鼠标点击 shell tray icon。

因此 S1 的 PASS 精确定义为：

> **packaged lifecycle seam PASS**，包括真实 Tray object 创建、close-hide、与 tray click 共用的 restore handler、real exit、package artifact。

仍保留一个很小的 Owner-machine residual check：

> notification-area icon 实际可见性 + 真实鼠标点击/唤起体验。

该 residual 不等于当前技术阻塞。

## 4.3 Crash / Restart Result｜PASS

Probe 创建 v1 DB，写入 Track + Plan link，然后启动 child process：

```text
PRAGMA journal_mode=WAL
PRAGMA synchronous=FULL
BEGIN IMMEDIATE
UPDATE track ...
process os._exit(73)
```

child process 在 **未 COMMIT、未正常 close** 的情况下直接退出。

重启连接后：

- 未提交修改不存在；
- 原始 Track 数据仍正确；
- `PRAGMA integrity_check = ok`。

随后正常 COMMIT 的修改在关闭连接并重新打开后仍存在。

### Finding

SQLite 的 transaction / restart seam 满足当前 V0 所需的最低 durability 模型。

---

## 4.4 Backup Result｜PASS

对 live DB 使用 SQLite online backup API 生成 standalone backup：

- backup `integrity_check = ok`；
- backup 保留 Track / Plan relationship；
- backup 可作为独立数据库打开。

### Finding

当前 Reference Audit 提出的：

```text
Manual Backup
→ consistent SQLite snapshot
→ one standalone backup file
```

具有现实可行性。

---

## 4.5 Restore + Safety Snapshot Result｜PASS

Probe 流程：

```text
valid live DB
→ online backup
→ destructive mutation of canonical DB
→ create pre-restore safety snapshot
→ validate selected backup
→ copy to staging DB
→ validate staging DB
→ close canonical DB connection
→ os.replace(staging, canonical DB)
→ reopen canonical DB
→ verify original Track / Plan data restored
→ integrity_check = ok
```

Windows runner 上 `os.replace` 对关闭连接后的 canonical DB replacement 成功。

### Finding

Reference Audit 提出的：

> restore 前 safety snapshot + staged/validated replacement

可作为轻量 V0 recovery contract，不需要重型 recovery subsystem。

---

## 4.6 Invalid Backup Rejection｜PASS

故意创建非 SQLite bytes，restore validation 阶段触发 `DatabaseError` 并拒绝继续。

### Finding

V0 restore 不应把用户选择的任意文件直接覆盖 canonical DB；restore 前 validation 是必要且低成本的 guardrail。

---

## 4.7 Migration Success + Failure Result｜PASS

v1 fixture：

```text
schema_version = 1
track(id, name)
```

v1 → v2 migration：

```text
BEGIN IMMEDIATE
ALTER TABLE track ADD COLUMN status ...
UPDATE schema_version = 2
COMMIT
```

结果：

- schema version = 2；
- new column 存在；
- existing data 自动获得 default；
- integrity check PASS。

随后另建一个 v1 fixture，在同一 transaction 中：

```text
ALTER TABLE
UPDATE schema_version
→ deliberate SQL failure
→ ROLLBACK
```

结果：

- schema version 仍为 1；
- `status` column 不存在；
- integrity check PASS。

### Finding

“schema version + ordered transactional migration + fixture test”足以作为 V0 最小 migration baseline。

---

## 4.8 S2 Conclusion

S2 强化了原 Reference Audit 推荐：

> **SQLite = high-confidence preferred persistence candidate。**

这仍不是 Architecture Decision，但已经没有必要在 G0.5 把普通 JSON / pile-of-files 与 SQLite 当成完全同等置信候选。

仍需 G0.5 定义的不是“SQLite 能不能用”，而是：

- runtime library / binding；
- canonical DB location；
- exact backup file naming / UX；
- schema-version representation；
- app startup migration failure UX。

# 5. S3｜Recurrence Identity / Exception / Today Projection

## 5.1 Probe scope

S3 是纯 domain seam probe，不是 production recurrence engine。

测试：

```text
weekly series
→ dynamic occurrences
→ edit only one occurrence
→ delete only one occurrence
→ Today projection
→ acknowledgement persistence / reprojection
→ date-only boundary
→ DST local-time boundary
```

## 5.2 Dynamic occurrence｜PASS

Series：

```text
id = series-cpa-weekly
weekday = Monday
local time = 09:00
```

从 2026-09-07 动态得到：

```text
2026-09-07 09:00
2026-09-14 09:00
2026-09-21 09:00
2026-09-28 09:00
```

没有预持久化所有 occurrence。

---

## 5.3 Single-occurrence edit identity｜PASS

原 occurrence：

`2026-09-14 09:00`

被单次移动为：

`2026-09-15 15:00`

identity 始终保持：

`series-cpa-weekly|2026-09-14T09:00`

即：

```text
OccurrenceIdentity
=
SeriesStableID
+
OriginalScheduledOccurrenceKey
```

而不是当前 start time。

### Finding

Reference Audit 对 occurrence stable identity 的候选得到了可执行 domain proof。

---

## 5.4 Single-occurrence delete｜PASS

删除 2026-09-21 occurrence 只产生该 occurrence 的 deleted exception；series 本身仍存在，其它 occurrence 不受影响。

### Finding

当前 V0 的“仅这一次 / 整个循环”边界可在不预展开 occurrence 的前提下实现。

---

## 5.5 Today projection｜PASS

移动后的 9/14 occurrence：

- 9/14 不再投影；
- 9/15 正确投影；
- identity 仍为原始 9/14 logical occurrence。

被删除的 9/21 occurrence：

- 9/21 Today projection 不出现。

### Finding

`series + exceptions → Today projection` 可以保持 derived-view ownership，不需要 Today 复制 schedule truth。

---

## 5.6 Today acknowledgement｜PASS

示例 acknowledgement key：

`2026-09-15|series-cpa-weekly|2026-09-14T09:00`

模拟 restart 后重新生成 series / occurrence projection，再次用同一 stable occurrence identity 找到 acknowledgement。

Series definition 未因 acknowledgement 被修改。

### Finding

当前：

```text
TodayAcknowledgement
=
local display date
+
stable source/occurrence identity
+
acknowledged state
```

是可行的窄辅助状态，不需要把 `completed` 写回 series / Track。

---

## 5.7 Date-only boundary｜PASS

Probe 明确演示：

```text
2026-09-07T00:00:00Z
```

转换到 `America/Los_Angeles` 后日期为：

`2026-09-06`

因此日期型 Memo / Reminder 若表示 `2026-09-07`，不能用 `UTC midnight instant` 偷偷代表。

### Finding

```text
date-only != timestamp
```

应成为 G0.5 architecture contract。

---

## 5.8 DST / local wall time｜PASS

测试 `America/Los_Angeles` DST fall-back 前后两周的本地 09:00 recurrence：

- local wall time 仍保持 09:00；
- UTC offset 发生变化；
- 对应 UTC hour 发生变化。

### Finding

对“每天/每周当地 09:00”一类 recurrence，应基于 local-time recurrence semantics，而不是固定 UTC instant recurrence。

---

## 5.9 S3 unresolved contract

S3 **有意没有决定**：

> Whole-series edit when prior exceptions already exist。

例如：

```text
每周一 09:00
+ 某次已移动
+ 某次已删除
↓
整个 series 改成每周二 10:00
```

原 exceptions：

- 保留？
- 重置？
- 按 original identity remap？

这是 G0.5 必须明确的 deterministic product/domain policy，不能由 implementation agent 临时决定。
