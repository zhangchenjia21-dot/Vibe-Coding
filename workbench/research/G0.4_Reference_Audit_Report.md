当前产品 Scope 本身没有明显失控，但工程风险密度已经不低。真正的复杂度不是 Today / Plan / Tracks 三个页面，而是它们下面同时存在：

```text

+ exception
+ Today acknowledgement
+ date / timezone
+ stable references
+ local canonical state
+ migration
+ backup / restore
+ crash recovery
+ desktop tray lifecycle
```

## 核心判断 A｜Complete V0 后才第一次 Owner UAT 不建议保持

当前 `TA-1 Complete V0 Integrated Build` 同时承担：

- Tracks 是否真的够表达长期状态；
- Plan 是否自然；
- Today 是否清楚；
- Reminder / Memo / Unscheduled 是否有价值；
- 月 / 周 Calendar 是否值得；
- recurrence；
- tray；
- persistence；
- backup / migration；
- 第一次真实产品 UAT。

这把工程语义风险与产品价值风险压在同一个第一次可用点。

**ROUTE-CHANGING FINDING RC-01**：建议把 TA-1 拆为 `TA-1A First Usable Core Vertical → Owner UAT → TA-1B Complete V0`。这不是为了流程而拆阶段，而是把只有 Owner 真实使用才能回答的问题提前。

## 核心判断 B｜recurrence + persistence + migration + tray 会形成高返工 seam

这些能力本身没有发现技术死路，但它们一旦做错会被整个产品依赖。因此不应到完整 V0 集成末期才第一次现实验证。

**ROUTE-CHANGING FINDING RC-02**：Route Freeze 前应完成极小、可丢弃的高风险 Spike，至少覆盖 desktop lifecycle、SQLite durability / backup / migration、recurrence identity / exception。

# 2. Pass 1｜Calendar / Recurrence

## 2.1 Series / Occurrence / Exception 模型

成熟 Calendar 系统具有高度一致的语义：

- Google Calendar：Recurring Event / Parent → Instance → Modified Instance / Exception；单个 instance 保留 `recurringEventId` 与 `originalStartTime`。
- Microsoft Graph / Outlook：`seriesMaster` / `occurrence` / `exception` / `singleInstance`，并保留 `seriesMasterId` 与 `originalStart`。
- Apple EventKit：修改过的 instance 具有 detached 语义，并保留 occurrence 的原始发生位置。
- iCalendar RFC 5545：使用 `UID + RECURRENCE-ID` 精确识别 series 中某一 occurrence；即使 occurrence 被移动，identity 仍指向原始 occurrence。

### Finding

当前批准方向：

```text
series definition
→ dynamic occurrence
→ exception
```

与成熟领域模型一致。

### Recommendation

**Adopt / 保持。** 不预生成无限 occurrence。

---

## 2.2 Occurrence Stable Identity

当前 Architecture Register 的 HYPOTHESIS 是 `series stable ID + occurrence logical date/time`。

Reference Audit 后建议收敛为更明确的候选：

```text
OccurrenceIdentity
=
SeriesStableID
+
OriginalScheduledOccurrenceKey
```

而不是 `SeriesID + CurrentStartTime`。

原因：单次 occurrence 被从周一 09:00 移到周二 15:00 后，它仍必须是原来那个 occurrence；exception 与 Today acknowledgement 都需要引用原 identity。

### Recommendation

**Adopt as G0.5 architecture candidate。Confidence：高。**

---

## 2.3 “这次及以后”为什么显著增加复杂度

Google Calendar 对“this and following”的建议实现是：

```text
截断旧 series
+
创建新 recurring series
```

而不是普通 occurrence exception。RFC 5545 的 `THISANDFUTURE` 也体现了 series-range mutation / split 的额外复杂度。

### Finding

当前 V0 只支持：

```text
仅这一次
整个循环
```

是有充分领域证据支持的 Scope Reduction。

### Recommendation

**Adopt / 保持。** 不引入“这次及以后”。

---

## 2.4 Whole-series edit + existing exceptions 尚未定义

例：

```text
Series: 每周一 09:00
9/7 exception → 15:00
9/14 exception → deleted
```

如果 Owner 把整个 series 改成每周二 10:00：已有 exceptions 如何处理？

这是当前 Draft Route 没有明确回答的 architecture gap。

### Recommendation

G0.5 必须给出 deterministic policy，不能留给实现 Agent 自行解释。

**Modify。**

# 3. Date / Time Semantics

成熟标准明确区分：

```text
DATE
DATE-TIME UTC
DATE-TIME Local
DATE-TIME + timezone
```

## Finding

V0 不需要复杂 timezone UI，但 schema 必须从第一版区分：

```text
date-only != timestamp
```

日期型 Reminder / Memo 不能先偷偷转换为 `00:00 UTC` 再还原，否则存在跨日本地日期错误。

Timed recurrence 则需要明确本地时间 / 时区语义，而不是把“当地每天 09:00”简单等同于固定 UTC instant。

### Recommendation

**Adopt。** G0.5 定义最小 Date / Local Time / Instant contract，并加日期边界测试。

# 4. Today / Personal Dashboard

## 4.1 Today 不应成为第二份 Truth

Things 等成熟产品将 Today 明确作为跨基础数据的时间过滤 / 当前行动视图；Akiflow 等产品也把 Today 建立在已安排到当天的原始任务之上。

### Finding

当前：

```text
Plan / Tracks truth
→ Today projection
```

得到强支持。

### Recommendation

**Adopt current constraint。**

---

## 4.2 Today Acknowledgement

当天“已完成”可以保持为极窄辅助状态：

```text
TodayAcknowledgement
{
  localDate,
  sourceIdentity / occurrenceIdentity,
  acknowledged
}
```

它不应等同于：

```text
ScheduledItem.completed
Track.completed
Series.completed
```

循环 occurrence 使用 `SeriesID + OriginalOccurrenceKey` 可以与 acknowledgement 自然衔接。

### Finding

Today acknowledgement 本身不会自动形成第二 truth；只有当它反向驱动 Plan / Track 生命周期或长期统计时才会。

### Recommendation

**Adopt。** 跨当天重启保留；V0 不建立 streak / 完成率 / 长期行为库。

---

## 4.3 Today 信息密度

成熟 planner 的共同信号是 Today 应尽量窄，把 backlog / someday / future / all projects 分离。

当前 Today 只展示：

- Current Vector；
- Today's Schedule；
- 今日 Reminder；
- 今日 Memo；

并排除：

- Unscheduled；
- 全部 Tracks；
- 未来预告；
- 完成率 / streak / scoring。

### Recommendation

**Adopt。** 参考图只能影响层级与视觉密度，不能把 Dashboard / Habit / Analytics 重新带回 V0。

# 7. Windows Desktop Host

## 7.1 Electron

官方能力覆盖：

- system tray；
- window show / hide；
- close event interception；
- app lifecycle；
- Windows packaging / update；
- per-user data path。

因此 `close → hide → tray restore → real exit` 是官方能力，不是第三方 workaround。

## 7.2 Tauri

Tauri v2 同样官方支持：

- system tray；
- tray menu / click event；
- window show / focus；
- CloseRequested interception；
- MSI / NSIS packaging；
- updater。

## 7.3 Windows Native

WinUI 3 / Windows App SDK + Win32 `Shell_NotifyIcon` 也完全可行，但没有证据表明仅为“更原生”值得承担更高开发与维护成本。

## 7.4 Web + Local Host

纯 Web/PWA 对 notification-area tray 需求不够直接；加入 native local host 后实际上变成双层 runtime + IPC，并未显示比 Electron / Tauri 更简单。

### Recommendation

- **Reject Web + Local Host as primary V0 candidate。**
- Electron / Tauri 进入短名单。
- Native 保留为理论可行方案，但除非出现明确 Windows-native 价值，不作为默认首选。

# 9. Local Persistence

## 9.1 SQLite 与当前 Workbench 高匹配

SQLite 的特征与 Personal State V0 高度一致：

- 单文件 application database；
- atomic transaction；
- crash / restart durability；
- relational references；
- schema / migration；
- backup API；
- 长期格式稳定。

当前对象关系：

```text
Track
Plan Item
Track Link
Series
Exception
Today Ack
Vector
Reminder
Memo
```

明显已经不是“一个 JSON 配置文件”级别的数据模型。

### Finding

SQLite 并不是为了完整而引入的大型数据库；相反，它可以避免 Workbench 自研 transaction / journal / relational integrity / migration 基础设施。

### Recommendation

**SQLite = preferred G0.5 persistence candidate。** 仍不等于 Architecture Freeze。

# 10. Crash / Restart Durability

Personal State 一旦真实使用，restart recovery 是 First Usable 的基础能力，而不是 polish。

### Recommendation

- canonical write 必须 transactional；
- 异常退出后已提交 state 可恢复；
- restart behavior 在 Route Freeze 前用最小 Spike 实测。

---

# 11. Backup / Restore

SQLite 在 runtime 中可能存在 rollback journal / WAL state；因此不能把“运行中直接复制 `.db` 文件”当作可靠 backup contract。

### Recommended V0 Backup

```text
Manual Backup
↓
consistent SQLite snapshot operation
↓
one standalone backup file
↓
validation
```

单文件 backup 是合理且低维护的 UX。

## Restore Contract

建议最小流程：

```text
选择 backup
↓
验证是合法 Workbench DB
↓
integrity check
↓
读取 schema version
↓
验证 migration path
↓
创建当前 live DB safety snapshot
↓
临时位置执行必要 migration
↓
再次 integrity check
↓
替换 canonical DB
↓
重新打开
```

### Scope Addition Proposal

**Restore 前自动 safety snapshot。**

这是低成本 recovery guardrail，不属于复杂 recovery framework。

### Recommendation

**Adopt。**

# 12. Schema Migration

### Recommended Minimum

```text
schema version
+
ordered migration runner
+
migration fixture test
```

不建设复杂 migration platform。

### Recommendation

**Adopt。**
